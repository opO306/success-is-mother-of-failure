# GPU_ONE_STEP_V1 — GPU 힘 + CPU KDK 한 걸음이 CPU E2 상태와 끝점까지 같은가

상태: **결과 기록 (2026-10-07)**. checker **EVIDENCE OK**, 판정 **ONE_STEP_PROMISING**.
- 공식 측정: Vast 52763629, Ryzen 9 5950X + RTX 3090(정정2).
- 데스크톱에서 독립 재검사·재분석한 결과가 JSON까지 같았다.
- 데스크톱 RTX 4060 교차 확인: 60개 실행의 모든 검사 지점 hash가 같았다.

증거 수준 = 실행 + 독립 checker. 실제 상태 12개와 경계 시험 8개에서의 **한 걸음** 비트 일치다. 증명이 아니고, **한 걸음 정확성이 장기 궤적 정확성을 뜻하지 않는다.**
분업: GPU는 힘 F만 계산한다(GPU_PAIR_VECTOR_V1 커널을 수정 없이 사용). 운동량·위치 갱신(kick, drift)은 CPU가 mpmath로 한다.
브랜치 `claude/gpu-one-step-v1`(부모 `464c69e`, 메인 checkout, worktree 없음, push 없음).
커밋: protocol `96eaaa9` → 상태 봉인 `f8bd809` → 코드 봉인 + 정정1 `f7b5d98` → 정정2(호스트) `34cedbd` → 증거·문서.

## 0. 한 줄 결론

**완료된 한 걸음 54번(실제 상태 12개 × 배치 4–6가지 + 정상 시험 2개)이 모두 모든 검사 지점에서 CPU와 끝점까지 같았다.**
- 검사 지점: F0 → 첫 kick(p_half) → drift(q1) → F1 → 둘째 kick(p1) → 최종 상태 키.

**영역 정지 6번은 같은 단계, 같은 쌍, 같은 종류에서 멈췄고, 멈춘 뒤 아무것도 실행하지 않았다.**
- 종류: F0 VIOLATED, F1 VIOLATED, F1 UNPROVEN.

**속도**: 정상 걸음(이미 가진 힘 F_s를 재사용하고 새 힘은 한 번만 계산)에서 GPU_HYBRID가 측정한 6개 조건 모두 CPU_W6를 이겼다.
- N=40: 7.7 vs 84.5 ms (11배)
- N=64: 8.8 vs 216.6 ms (25배)
- N=128: 12.9 vs 883.5 ms (68배)
- N=12(p=163): 7.8 vs 8.2 ms로 **근소한 차이**다. W6의 회별 흔들림(7.5–8.8 ms) 안에 있다.

## 1. 무엇을 했나 (쉬운 말)

비유: 지난 단계에서 공장(GPU)이 "원자마다 받을 힘"을 장인(CPU)과 똑같이 만드는 것을 확인했다. 이번에는 그 힘으로 원자를 실제로 한 걸음 움직여 봤다.
- 움직이는 일(kick, drift)은 장인이 하고, 힘 계산만 공장이 한다.
- 그렇게 움직인 결과가 장인 혼자 한 결과와 끝자리까지 같은지 확인했다.

실제 의미(기존 E2 순서 그대로):

```
F0 = forces(q0)          (GPU)
p_half = p0 + F0         (CPU)
q1 = q0 + p_half * CDT   (CPU)
F1 = forces(q1)          (GPU)
p1 = p_half + F1         (CPU)
```

- F는 이미 반 걸음 충격량(h·G·d, h = DT/2)이다. 1/2를 또 곱하거나 식을 합치지 않았다.
- **GpuForceExecutor**: CUDA 컨텍스트, 모델·상수, 위치·쌍·원자 버퍼를 한 번 만들고 매 힘 계산에 재사용한다.
- **정상 걸음과 준비(INIT)를 나눠 쟀다.**
  - 정상 걸음 = 가진 F_s로 kick → drift → **새 힘 한 번** → kick.
  - INIT = 실행기 생성 + 모델 업로드·할당 + 첫 힘 F(q0).
- **상태 묶음**: 실제 궤적 4개에서 T/10, T/2, 9T/10 걸음의 (q, p, F)와 그다음 걸음 상태를 기록했다.
  - 기록 방법: `stream.run` 소스에 관찰 한 줄을 넣은 복제본을 실행 중에 만들었다. 파일은 바꾸지 않았다.
  - 네 궤적 모두 검증된 Vast 기준과 같았다. 코드보다 먼저 봉인했다(`50b8ebac…`).
- **경계 시험**: N=3 상태를 운동량 탐색으로 찾았다(p=109, 163 각각).
  - 정상, F0에서 VIOLATED, F1에서 VIOLATED, F1에서 UNPROVEN(위치 하나가 구간).

checker는 실행기를 import하지 않는다. 계산 방식도 다르게 했다.
- 실행기는 mpmath의 원시 구간 함수(mpi_add, mpi_mul)로 kick과 drift를 한다.
- checker는 mpmath iv 객체 연산으로 자기 forces 루프와 KDK를 따로 계산한다.

결함 주입(잡힌 지점):
- 1 잘못된 F0 → C1
- 2 첫 kick 누락, 3 첫 kick 두 번 → C2
- 4 drift 구조 변경 (p·DT)/MASS, 5 drift에 옛 p → C3
- 6 옛 q로 F1, 8 F1 원자 순서 바꿈 → C4
- 7 둘째 kick 누락 → C5
- 9 q 끝점 1ulp, 10 p 끝점 1ulp → C0
- 11 정지 뒤 계속 진행 → C4·C5(정지 상태 자체는 기록돼 있어 상태 비교만으로는 같았고, 이후 값으로 잡혔다)
- 12 p 변조(109 상태에 128 모델) → C1
- 13 GPU 거부를 완료로 위장 → C1
- 14 배치에 따라 다른 결과 → 배치 비교 / C1

참고: 지시의 "CDT·p로 바꾸기"는 탐지할 수 없다. mpmath의 구간 곱셈 한 번은 피연산자 순서를 바꿔도 비트까지 같기 때문이다. 그래서 구조를 바꾸는 (p·DT)/MASS로 봉인했다(protocol 기록).

## 5. 쉬운 말 정리

1. **한 걸음 전체도 CPU와 똑같았나?** 예. 측정한 54번의 한 걸음과 6번의 정지가 모든 검사 지점에서 끝점까지 같았다. 다만 한 걸음뿐이다.
2. **어디부터 GPU가 이기나?** 측정한 점에서는 모두 이겼다. N=40 이상(p=109)에서는 11–68배로 분명하다. 작은 N=12에서는 거의 비긴 것과 같다.
3. **새 병목은?** 정상 걸음에서 파이썬 변환(encode·decode)은 이제 작다(N=128에서 2 ms). 시간의 대부분은 GPU 커널이다.
   - 쌍·G·J 커널의 바닥 지연이 약 5.3–7.8 ms다. G 계산 하나를 스레드 하나가 순서대로 하기 때문이다.
   - 합산 커널은 N에 비례해 길어진다(N=128에서 2.7 ms).
   - CPU kick·drift는 N=128에서도 약 2.3 ms다.
4. **"이전 단계 결과를 재사용한다"는 성능 모델을 지켰나?** 예. 정상 걸음은 새 힘을 한 번만 계산한다. INIT은 따로 기록했다.

## 6. 한계·공개

- **한 걸음만**이다. 여러 걸음에서 오차가 쌓이는지, 정지가 어디서 나는지는 다음 단계(GPU_SHORT_TRAJECTORY_V1)의 질문이다.
- **증명이 아니다.** 봉인된 상태 20개에서의 비트 일치다.
- mpmath 1.3.0(순수 파이썬) exp 알고리즘을 재현한 결과다(G0부터 같다). 다른 버전·백엔드에서는 깨질 수 있다(추론).
- **GPU INIT에서 CUDA 컨텍스트 생성이 빠져 있다**(위 설명). 진짜 cold 시작 비용은 이번에 재지 않았다.
- **N=12 결과는 근소하다.** 중앙값으로는 GPU_WIN(0.956)이지만 W6 회별 7.5–8.8 ms 범위 안이다. GPU 쪽이 확실히 이긴다고 말하지 않는다.
- block 32를 공식 기본으로 썼다(이전 관측 근거). 보편 법칙이 아니다.
- Linux에서는 기존 E2 W6 작업자의 Windows 전용 CPU 측정 때문에 V2 Linux 측정 장치를 실행 스크립트에서 켰다(정정2). W6 시간은 메인의 perf_counter로 쟀으므로 이 장치와 무관하다.
- Vast 서버는 증거를 받은 즉시 정지했다(exited 확인). 공식 실행 자체는 약 30초였다.
- LOCAL FULL은 생략했다(새 실험 파일만 추가, 기존 실행 코드·동결 계약·이전 GPU 파일 불변). 관련 시험 18개(데스크톱)와 18개(Vast Linux)로 대신했다.
- 기존 evidence와 이전 단계 코드는 수정하지 않았다.
