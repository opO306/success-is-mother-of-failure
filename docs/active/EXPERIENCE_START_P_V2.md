## 4. 13개 질문

1. **큰 N에서도 FAMILY_MIN은 첫 시도에 성공했나?**
   아니다. 0/4 요청, 0/12 실행이다. T=100에서 106, T=1000에서 145가 모두 부족했다.
   - 작은 N(V1)에서는 106·145로 충분했다. 큰 N에서는 더 높은 p가 필요했다.
   - 관측값: N=40·64(T=100)는 highest_observed_failure_p 106, lowest_observed_success_p 109. N=12·16(T=1000)은 145 실패, 161·163 성공.
2. **FAMILY_MAX는?**
   4/4 요청, 12/12 실행 모두 첫 시도에 성공했다(109와 163).
3. **MAX도 실패한 요청이 있었나?**
   없다. 다만 **여유가 거의 없다.**
   - N=16(T=1000): 관측된 가장 낮은 성공 p가 163, 곧 MAX 값 그 자체다.
   - N=40·64(T=100): 106은 실패했고 MAX 109가 성공했다. 그 사이(107·108)는 시험하지 않았다.
   - 그래서 반례 A(큰 N에서 MAX도 부족)는 이번에 **관측되지 않았다**. 하지만 다음 크기에서 나올 가능성이 있다(추론, 미측정).
4. **p를 높인 추가 비용은 얼마나 됐나?**
   직렬 기준으로, 같은 요청에서 p를 106→109 또는 145→163으로 올렸을 때 한 pass CPU는 0–1.7% 늘었다.
   - N=40: 41.9 → 41.9
   - N=64: 108.6 → 107.1(측정 흔들림 범위)
   - N=12: 36.7 → 37.4
   - N=16: 66.1 → 67.2
   - 이번 범위(p 64–171)에서 한 pass 비용은 p에 거의 무관하고, 쌍 수 × 걸음 수로 정해졌다. W6 기준 쌍·걸음당 약 6×10⁻⁴ CPU초였다.
5. **실패 재시도 한 번의 비용과 비교하면 얼마나 작은가?**
   재시도 한 번은 pass 하나를 처음부터 다시 계산하는 일이라 거의 +100%다. p를 높이는 추가 비용(0–2%)의 약 50배 이상이다.
   예외: T=1000에서 p=64는 995·917걸음에서 일찍 멈춰 조금 쌌지만, 그래도 pass 하나의 90% 이상이 들었다.
6. **BASE64 대비 MIN/MAX의 전체 wall/CPU 절감률은?**
   - MAX: 시간 −57.4%, CPU −57.1%
   - MIN: 시간 −14.8%, CPU −14.0%
   - MIN의 절감은 전부 T=1000에서 나왔다. BASE64가 재시도 2번이고 MIN은 1번이었기 때문이다.
7. **요청 균등 평균에서도 같은 결론인가?**
   예. 요청별 비율 평균은 MAX 0.43 / 0.43, MIN 0.85 / 0.86이다. MAX ÷ MIN은 합계도 0.50, 요청 평균도 0.50으로 같다.
8. **MIN vs MAX 최종 판정은?**
   **MAX_WIN**. 근거: 합계 0.50·0.50 ≤ 0.95, 요청 평균 0.50·0.50 ≤ 1.02.
9. **판정이 특정 비싼 요청 하나에 의해 뒤집혔나?**
   아니다. 4개 요청 모두에서 MAX가 MIN의 약 절반이었다(0.49–0.50). V1의 "한 요청이 합계를 좌우한 모양"과 다르다.
10. **N이 커지면서 필요한 p 패턴이 바뀌었나?**
    예(관측 범위 안에서).
    - T=100: N≤32에서는 106–109로 성공했다(N=5·7·10·20은 106). N=40·64에서는 106이 실패하고 109가 필요했다.
    - T=1000: N=5·7은 145로 충분했지만, N=12·16은 145가 실패하고 161·163이 필요했다.
    - 필요한 p가 N과 함께 천천히 오르는 모양이다. 하지만 N=8(T=1000)은 152 실패, N=10은 159 성공처럼 단조롭지 않은 점도 V1에서 이미 있었다.
    - **반례 D**: T에 따라 모양이 달랐다. T=1000에서는 BASE64가 재시도를 2번 했고(64가 걸음 도중 DOMAIN_UNPROVEN, 그다음 73·78도 실패), T=100에서는 1번이었다. 그래서 MIN의 이득도 T=1000에서만 생겼다.
    - **반례 E**: 같은 p에서도 N이 커지면 pass 비용이 쌍 수에 비례해 커졌다. 다만 쌍·걸음당 비용(약 6×10⁻⁴ CPU초)은 N과 T에 거의 무관했다.
11. **현재 단순 experience table로 충분한가?**
    이번 범위(T=100 N≤64, T=1000 N≤16)에서는 **FAMILY_MAX 표 하나로 충분했다**. 첫 시도 실패 0이었다.
    - 반례 C(MIN이 계속 성공해서 MAX 보험이 필요 없음)는 **나오지 않았다**. 오히려 MIN이 모두 실패했다.
    - 반례 B(MAX가 p를 너무 올려 비용 급증)도 **나오지 않았다**. 추가 비용은 0–2%였다.
    - 한계: 여유가 0에 가깝다(질문 3). 다른 T는 표에 없고, 다른 시나리오 계열도 없다. 표 밖의 요청은 64로 시작한다.
12. **지금 회귀/신경망을 만들 정보 가치가 생겼나?**
    아직 아니다(추론 포함).
    - 단순 표가 이번 범위에서 첫 시도 실패 0이었다. 모델이 더 나을 여지는 "표가 틀리는 곳"뿐인데, 그런 사례가 아직 하나도 관측되지 않았다.
    - 표가 틀려도 손해는 재시도 한 번이고, 정확성은 P2가 지킨다.
    - 모델을 만들 근거는 "MAX도 실패하는 사례가 반복해서 쌓일 때" 생긴다. 그때의 목표도 최소 p 예측이 아니라 기대 비용 최소 시작 p다.
13. **아니면 precision 연구를 여기서 동결하고 GPU로 넘어가는 것이 더 싼가?**
    봉인 규칙으로는 **종료 후보 A**다.
    - FAMILY_MAX가 정확성 통과, 큰 N에서 12/12 첫 시도 성공, 합계 −57%였다.
    - 따라서 단순 경험표(FAMILY_MAX)를 유지하고, 회귀·신경망은 보류하고, 다음은 GPU Pair Pilot이다.
    - 남는 위험(여유 0)은 정확성 위험이 아니라 비용 위험(가끔 재시도 1번)이다. 그래서 precision 축을 계속 파는 것보다 동결하는 쪽이 싸다고 본다(추론).
    - 동결할 때 같이 기록할 것: 새 요청 결과를 검증 뒤 표에 넣는 절차(V2와 같은 봉인 방식).

  - 시간 수치는 노트북 V1과 직접 비교하지 않는다. 같은 크기의 pass가 노트북보다 약 2배 빨랐다.
  - 정책끼리의 비교는 모두 같은 서버, 같은 시간대, 순서를 돌려가며 했다.
- **CPU 측정 방식이 다르다.** 기존 실행기의 Windows 전용 CPU 측정(QueryProcessCycleTime)이 Linux에 없어서, V2 폴더의 측정 장치(`linux_shim/sitecustomize.py`)로 두 함수만 바꿨다.
  - `cycles`는 CLOCK_PROCESS_CPUTIME_ID 나노초로, `_mem`은 최대 RSS로 바꿨다.
  - 실행기 파일과 물리·수치 코드는 그대로다(hash 봉인). 서버에서 자식 프로세스까지 장치가 켜졌는지 확인했다(`cpu_clock.json`).
- **공유 서버의 한계.** 컨테이너에서는 다른 손님의 부하가 다 보이지 않는다.
  - 보이는 프로세스 기준으로 오염은 0/16이었다. 참고값으로 기록한 steal은 전 구간 0이었다.
  - loadavg는 우리 작업 중 5–6이었는데, 이것은 우리 작업 자체가 만든 값이다.
- **반복이 적다.** 3회 반복이다. 다만 회별 시간 흔들림은 1% 안팎으로 작았다.
- **사전 공개(정정1)**:
  - 봉인 전에 데스크톱 시험과 Vast 시험 실행이 N=6, T=100(평가 요청 아님)과 기준점을 돌렸다. 결과는 V1 정정1과 같았다.
  - 비용만 보는 짧은 smoke(N=64, T=3)를 돌렸다. 결과(성공/실패)는 보지 않았다.
  - 시험 실행에서 찾은 CPU 배치 점검 결함을 봉인 전에 고쳤다.
- **비용**: 실행 전 추정은 노트북 기준 CPU 약 10,600초였다. 실제 Vast CPU는 5,821초로 상한 20,000초 안이었다. 실행 시간은 약 37분(01:21–01:58 UTC)이었다.
- **서버 전원**: 증거를 가져온 직후 내가 직접 정지시켰다(정지 확인함).
  - 서버는 사용자가 켠 시점부터 약 1시간 켜져 있었다. 요금은 약 $0.19/시간이다.
  - 작업 스크립트의 자동 정지(유예 30분)도 함께 걸려 있었다.
- 이번 candidate 경험(레코드 66개, 샘플 36개)은 checker를 통과했지만 표로 승격하지 않았다.
- `true_minimum` 류 정답 표는 만들지 않았다.
- 기존 실험 evidence는 바뀌지 않았다.
