## 0. 한 줄 결론

**N이 커지면 두 이득은 함께 남았다.** N≥12에서는 PAR_E2 W6가 직렬 E1보다 전체 시간 2.9–4.1배 빠르면서, 같은 W의 E1보다 CPU를
6–8% 덜 썼다. **작은 N(100걸음, N=4·6)의 W6에서는 E2의 CPU 이득이 사라졌다**(0.0–1%). 원인은 7개 프로세스의 시작 비용이
E1·E2에 똑같이 들어 E2가 줄이는 힘 계산 몫이 작아지기 때문이다. 결과는 모든 작업자 수·반복에서 비트 동일했다(E1 120/120, E2 120/120).
결합 효과는 단순 곱과 ±10% 안에서 맞았고, 벗어난 경우는 **E2 자체가 아니라 W6의 반장·작업자 CPU 공유 배치** 때문으로 보인다(§4).

## 1. 무엇을 했나 (쉬운 말)

비유: 지난번에는 ① 일꾼 한 명의 손을 빠르게 하는 방법(E2)과 ② 일꾼을 여럿 두는 방법(쌍 병렬)을 따로 시험했다. 이번에는 빠른 손을
가진 일꾼 여럿을 동시에 썼다. 둘을 곱하면 될 것 같지만, 일꾼을 부르는 시간(시작 비용)과 반장이 정해진 순서로 합치는 시간은
E2로 줄어들지 않으므로 실제로 재야 한다.

실제 의미:
- 바꾼 것은 작업자 안의 계산기(E1 algebra ↔ E2 rw:R1+R2)뿐이다. 물리, 모든 쌍, 컷오프 없음, KDK, dt, 질량, 도메인, 반올림, p=128,
  초기조건 규칙은 그대로다(봉인 전 diff 확인: 해당 파일 변경 0).
- 구성 8개: SER_E1, SER_E2, PAR_E1_W3/W4/W6, PAR_E2_W3/W4/W6. W4는 실행 전에 넣었다(MULTIATOM에서 wall×CPU 최적이 W4였던 구간 확인용).
- N ∈ {3,4,6,12,24,48}(3은 경계가 잘리지 않게 실행 전 추가), T=100 전부 + T=1000은 N≤12. 3회 반복, 중앙값. CPU는 주기 계수 기준.
- 외부 부하 규칙(봉인): 매 (T, N) 묶음 전에 1초 스냅숏, 다른 프로세스 합 ≥1코어 또는 python/roblox/codex/node가 ≥25%면 오염.
  노트북 32개 스냅숏 전부 깨끗(제외 0).

## 4. 꼭 답할 10개 질문

1. **E2의 5–8% CPU 이득이 W3에서도 남나**: 남는다. N≥12와 T=1000 전부에서 5–8%(0.924–0.950)였다. T=100의 작은 N(3–6)에서는
   3–4%로 줄었다(0.962–0.970).
2. **W6에서도 남나**: 큰 N에서는 남는다(N 12/24/48: 6–8%, T=1000 N 4–12: 5–8%). **T=100 N=4·6에서는 사라졌다**(1.010, 1.002).
   N=3도 2%뿐이다.
3. **병렬의 3–4배 시간 이득이 E2에서 유지되나**: 유지된다. W6 루프 speedup(같은 계산기 직렬 대비)은 E2 2.2–4.1배, E1 2.3–4.0배로
   같은 범위였다. 직렬 E1 대비 전체 시간은 PAR_E2_W6가 N=24 4.05배, N=48 3.97배였다.
4. **E2 때문에 overhead 몫이 커지나**: 그렇다, 작게. E2는 작업자의 힘 계산만 줄이고 시작·통신·합산·KDK는 그대로라 그 몫이
   0–4%p 늘었다(§3). 이것이 작은 N W6에서 E2 이득이 사라진 이유다. 고정 시작 CPU(프로세스 7개 × import·준비)는 E1·E2가 같다.
5. **최적 작업자 수가 E1과 E2에서 다른가**: 거의 같다. 전체 시간 기준 N≥12(T=100)와 N≥4(T=1000)는 둘 다 W6, 작은 N은 둘 다 W3다.
   T=100 N=6만 E1 W6 / E2 W4로 달랐다. 그 차이는 반복 간 흔들림 수준(1–2%)이다.
6. **CPU 최소는 여전히 직렬 E2인가**: 예, 10개 (T, N) 전부.
7. **시간 최소가 PAR_E2가 되는 N**: T=100 **N=6부터**, T=1000 **N=3부터**, 이후 모든 N에서 유지된다.
   T=100 N=4는 PAR_E1_W3이 최소였다(PAR_E2_W3과 0.1% 차이, 반복 간 흔들림 안).
8. **시간×CPU 최적의 변화**: T=100은 N≤6 직렬 E2 → N=12 PAR_E2_W4 → N≥24 PAR_E2_W6. T=1000은 N=3·4 PAR_E2_W3 → N≥6 PAR_E2_W6.
   MULTIATOM(E1만)의 모양(작은 N 직렬 → 중간 W4 → 큰 N W6)에서 계산기만 E2로 바뀐 형태다.
9. **결합이 단순 곱보다 작거나 큰 이유**: 실제/곱 비율은 루프 0.90–1.11, 전체 0.82–1.07, CPU 0.98–1.08이었다.
   - **곱보다 작은 경우**(작은 N, 특히 W6 전체 시간 0.82–0.90): E2는 작업자 힘 계산만 줄인다. 시작 비용·통신·순서 고정 합산은
     줄지 않으므로 E2의 몫이 희석된다(E2 이득에 대한 Amdahl 효과).
   - **곱보다 큰 경우**(T=100 N=12·24, T=1000 N=4·6의 W6, 루프 1.08–1.11): 반복 3회 모두 나타났다. 작업자별 계산 시간을 보면,
     E1 W6에서는 반장과 같은 CPU 0번을 쓰는 6번째 작업자가 늘 가장 느렸다(N=24: 6.55초, 나머지 5.5–5.9초). E2 W6의 N=12·24에서는
     이 지연이 사라졌다(5.18초, 나머지 4.98–5.17초). N=48에서는 E2에서도 남았다(25.1초, 나머지 21.6–22.8초).
     즉 차이는 E2 자체가 아니라 **CPU 공유 작업자가 반장의 합산과 시간상 겹치는 정도**에서 왔다. 왜 E2에서 겹침이 줄었는지는
     측정하지 않았다(**추론**).
10. **모든 작업자 수에서 비트 동일한가**: 예. 같은 계산기 안에서 직렬·W3·W4·W6·3회 반복이 모두 같다(E1·E2 각 120/120).

## 5. 판단 갈래 (설계자 결정용, 제 분류)

- **A에 해당하는 부분**: 시간 최소는 T=100에서 N≥6, T=1000에서 N≥3부터 PAR_E2가 일관되게 이겼다. 큰 N에서는 E2 CPU 이득도 남았다.
- **B에 해당하는 부분**: T=100 N=4·6의 W6에서 E2 CPU 이득이 사라졌다. 원인은 시작 비용(프로세스 7개의 고정 CPU, 전체 시간의
  58–81%)으로 분리됐다. 통신·합산 몫 증가는 0–4%p로 부차적이었다.
- **C 신호**: W6에서 반장과 작업자 하나가 CPU 0번을 공유하는 배치가 가장 느린 작업자를 만들고, 그 효과가 E2 여부에 따라 바뀌었다.
  canonical reduction보다 **작업자·반장 배치**가 먼저 볼 후보로 보인다(추론). 이번 단계에서는 재설계하지 않았다.

## 6. 데스크톱 — 측정하지 못함

계획(N 3/4/6/12, 깨끗한 Ryzen 5 5600)은 실행하지 못했다. dry run 시점에 Roblox 2.3–2.8코어가 돌고 있었다. 이후 확인에서도
Roblox를 빼고 Windows 검색 색인 약 1코어, Chrome 약 0.9코어, 화면 합성 약 0.5코어 등이 남아, 봉인 규칙(외부 1코어 이상이면 오염)으로는
전부 제외될 상황이었다. Codex는 끌 수 없었다. 설계자 결정으로 노트북만 측정했다.

XREPRO_RESOURCE_V1에서 두 기기는 **계산 결과가 비트 단위로 같았고**, 요청 묶음 병렬의 확장 모양도 비슷했다. 그러나 **이번 쌍 병렬
경계(N=4/6)와 E2 상대 이득이 데스크톱에서도 같은지는 측정되지 않았다(UNRESOLVED)**. 데스크톱은 SMT가 있어 반장이 작업자와 같은
물리 코어의 다른 스레드를 쓰므로 §4-9의 CPU 공유 효과가 다르게 나타날 수 있다(추론).
