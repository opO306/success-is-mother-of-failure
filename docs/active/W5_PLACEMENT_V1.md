# W5_PLACEMENT_V1 — 반장 전용 코어 W5가 반장과 같은 코어를 쓰는 W6보다 나은가

상태: **결과 기록 (2026-10-06)**. checker **EVIDENCE OK**, 비트 불일치 0(노트북 실행, 데스크톱에서 독립 재검사·재분석 동일).
**판정: B (N=12, 24, 48 모두)** — 공유 비용은 실제로 있지만 여섯 번째 작업자의 계산 이득이 더 크다. 기존 W6 유지 가능.
증거 수준 = 실행 + 독립 checker, 노트북(Ryzen 5 4500U) 1대, 각 조건 5회. formal 아님.
브랜치 `claude/w5-placement-pilot-v1`(부모 `38f2dee`, 메인 checkout, worktree 없음). protocol `c5dbaf6` → 정정1 `22df677` → 코드 `024c984` → 노트북 원본 `ac62a46`.

## 0. 한 줄 결론

W6에서 반장과 같은 코어(CPU 0)를 쓰는 작업자는 **큰 N에서 실제로 늘 가장 느렸다**(N=24·48에서 5회 모두, 다른 작업자보다 약 10–11% 느림).
그런데도 그 작업자를 빼고 반장에게 코어를 비워 준 W5는 **15번의 짝 비교 모두에서 W6보다 4–8% 느렸다**. W5가 아낀 것은 CPU 4–6%다.
결과는 모든 배치·반복에서 비트 동일했다.

## 1. 무엇을 했나 (쉬운 말)

비유: 6명이 일할 책상이 6개뿐이라 반장이 한 일꾼과 책상을 같이 썼다. 그 일꾼이 제일 느렸으니, 일꾼을 한 명 빼고 반장에게 책상을
따로 주면 더 빨라질까? 대조로 일꾼 4명(반장도 자기 책상)도 함께 쟀다.

실제 의미:
- 실행 전 확인: 노트북은 물리 코어 6개, 각 코어에 논리 CPU 하나(0–5), SMT 없음. 따라서 "CPU 0 공유"는 반장 프로세스와 6번째 작업자가
  **한 물리 코어를 시간으로 나눠 쓴다**는 뜻이다. 캠페인은 시작할 때 같은 구조를 다시 확인했다.
- 계산기 E2(R1+R2)만, p=128, T=100, N=12·24·48, 5회. 구성: SER_E2(정확성 기준), W4(반장 CPU 0, 작업자 1–4),
  W5(반장 CPU 0, 작업자 1–5), W6(반장 CPU 0, 작업자 1–5 + 0). 병렬 알고리즘·물리는 이전 단계 코드를 그대로 불러 썼다.
- 각 실행은 `ExecutionPlan{evaluator, precision, backend, worker_count, main_cpu, worker_cpus}`로 기술된다. CPU_SERIAL·CPU_PARALLEL만
  구현했고 GPU는 예약 이름(실행하면 거부)이다.
- 외부 부하: 17개 스냅숏 전부 깨끗(제외 0).

## 4. 질문별 답

1. **W5가 W6보다 빠른가**: 아니다. 15번의 짝 비교 모두 W6가 빨랐다(전체 4–8%, 루프 5–17%).
2. **W5의 CPU 절감**: W6 대비 4–6% 적다(N=12 5.8%, N=24 4.3%, N=48 4.4%).
3. **W4 → W5 → W6 증가가 정상인가**: 정상이다. 세 N 모두 작업자가 늘수록 wall이 줄었고, 효율은 0.78–0.85 → 0.64–0.74 → 0.63–0.65로
   천천히 떨어졌다. 튀는 값은 없었다.
4. **W6의 CPU 0 공유 작업자는 여전히 가장 느린가**: 큰 N에서는 그렇다. N=24·48에서 5회 모두 가장 느렸고 다른 작업자 중앙값보다
   약 10–11% 느렸다. N=12에서는 5회 중 3회, 초과량 중앙값 2.7%로 작았다.
5. **W5에서 작업자 간 편차가 줄어드나**: N=24·48에서는 줄었다(11–13% → 2–4%). N=12에서는 오히려 W5가 컸다(10% vs 5%).
   원인은 배치가 아니라 **쌍 분할**이다. 66쌍을 5명에게 나누면 14,13,13,13,13이라 0번 작업자가 7.7% 더 많이 맡고, 실제로 W5에서
   늘 0번이 가장 느렸다. 6명이면 66/276/1128쌍이 모두 정확히 나눠떨어진다. 그래서 **N=12에서 W6가 앞선 몫의 일부는 배치가 아니라
   분할 균형 덕분**이다(교란 요인, 아래 공개).
6. **반장의 송신·합산 시간이 W5에서 달라지나**: 달라진다. W6 N=48의 송신 3.76 s는 W5에서 0.09 s로 사라졌다. 반장이 CPU 0의 작업자에게
   보낼 때 그 작업자와 코어를 다투는 효과로 보인다(추론). 합산은 W5가 W6보다 약 6% 짧았다.
7. **여섯 번째 작업자가 계산 기여보다 경합 비용을 더 만드는 구간이 있나**: 이번 범위(N=12–48)에서는 없다. 모든 N에서 W6 루프가 W5보다
   짧았다. 다만 6번째 작업자가 이론상 줄일 수 있는 몫(작업량 5/6, 약 17%)과 비교하면 N=24·48에서는 실제로 5–6%만 줄었다.
   기대 이득의 약 2/3–3/4를 경합이 먹었다(17% 대비 실제 4.4–5.7%).
8. **전부 비트 동일한가**: 예(60/60, 이전 증거와도 15/15).

## 5. 판정과 해석

- 봉인 규칙상 **B**: W6가 중앙값 3% 이상 빠르고 짝 비교 4/5 이상에서 빨랐다. 실제로는 세 N 모두 5/5였다.
- E2_PAIR_PARALLEL_V1에서 본 "CPU 0 작업자가 가장 느리다"는 관찰은 **재현됐다**(N=24·48). 그러나 "그래서 W5가 낫다"는 반례 가설은
  **이 노트북·이 범위에서는 성립하지 않았다**.
- 공개해야 할 교란: W5는 N=12·24·48 모두에서 쌍이 5로 나눠떨어지지 않아 한 명 이상이 한 쌍 더 맡는다. W6는 세 N 모두 균등하다.
  N=24·48에서는 그 차이가 0.4–1.8% 작업량이라 판정을 뒤집을 크기는 아니다(추론). N=12에서는 7.7%라 W6 우위의 상당 부분일 수 있다.
- 추가로 볼 만한 후보(이번에 하지 않음, 별도 protocol 필요, 추론): W6에서 CPU 0 작업자에게 **쌍을 조금 덜** 주는 분할. 블록은 여전히
  연속·정해진 순서라 합산 순서와 비트 동일성은 그대로다. 공유 작업자가 약 10% 느리다는 이번 측정치를 그대로 쓸 수 있다.

## 6. 한계·공개

- 노트북 1대(SMT 없음). 데스크톱은 SMT라 "같은 코어 공유"의 뜻이 다르고, 이번 범위 밖이라 측정하지 않았다.
- 캠페인 프로세스도 CPU 0에 고정돼 있다. 실행 중에는 기다리기만 한다.
- 사전 비용 추정(1,600 CPU 초)이 실제(3,096 초)의 절반이었다. 상한 5,000초는 넘지 않았다.
- 사전 공개(정정1): 데스크톱 dry run(N=3, T=5)에서 checker가 이전 증거를 다른 T로 비교하는 결함을 다시 찾아 봉인 전에 고쳤다.
  이전 단계에서 고친 결함을 새 checker에 옮기지 않은 실수다.
- 기존 E2_PAIR_PARALLEL_V1 코드·증거는 바뀌지 않았다(protocol에 시작 시점 해시 기록).
