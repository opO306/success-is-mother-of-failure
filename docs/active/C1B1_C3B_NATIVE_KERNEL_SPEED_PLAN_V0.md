## 0. 한 줄 요약

C++ 트랙(`c1b1_native/track.cpp`)이 걸음 하나에 쓰는 약 120 µs를 줄인다. 먼저 어디에 시간이 드는지 잰다(C3b-0). 그다음 **계산 결과가 중간값까지 한 비트도 바뀌지 않는** 정리만 한다(C3b-1). 계산 방식 자체를 바꾸는 것(C3b-2)은 설계자가 따로 정한다.

## 1. 쉬운 설명

- **비유:** 기계 라인(C++)을 들였는데 생각보다 느리다(손작업의 5배). 라인을 멈추지 않고 어느 공정이 오래 걸리는지 초시계로 잰다(C3b-0). 부품 모양은 그대로 두고 동선만 줄인다(C3b-1): 같은 나사를 같은 순서로 조이되, 공구를 매번 창고에 반납하지 않는다. 부품 설계를 바꾸는 일(C3b-2)은 따로 승인받는다.
- **실제 의미:** C3b-1은 같은 정수 연산을 같은 순서로 하되, 큰 정수 구조체 복사, 작은 수 나눗셈의 일반 경로, 반복 계산 같은 낭비를 줄인다. 그래서 jet·kick 값이 C3a 실행 파일과 **모든 비트에서 같아야** 한다. 이전 C3a 실행 파일이 그대로 독립 기준(검사원)이 된다.

**C3b-0 프로파일:**
- 빌드 두 가지를 쓴다.
  - (가) `-O2 -pg`: 실제 빌드에 가까운 시간이다.
  - (나) `-O1 -fno-inline -pg`: 함수별 시간 배분을 본다. 인라인 때문에 시간이 엉뚱한 함수로 몰리는 것을 피한다.
- 작업량: 개발 패널 G1 시작, 레벨 0과 레벨 4에서 각각 1,000틱(Chin). B6 시작, 레벨 4에서 1,000틱. 트랙 하나 = 프로세스 하나, 파이썬 래퍼로 init 후 `to 1000`.
- 출력: gprof flat profile, call graph 상위. 두 빌드의 결과 raw가 C3a 기준 빌드와 같은지도 본다(같아야 함, `-pg`는 계산을 바꾸지 않는다).
- 새 도구 `tools/c1b1_native_profile.py`(survey_only)와 결과 `docs/active/C1B1_C3B0_PROFILE_V0.txt`(+ `.json`). 실행 전 커밋한다. C3b-0은 소스를 바꾸지 않는 정보용 측정이라 LOCAL FULL 문제(아래 D)와 무관하다.

**C3b-1 정확한 정리(후보, 0 결과로 확정):**
- 큰 정수 연산을 제자리(출력 인자) 방식으로 바꿔 구조체 복사를 줄인다.
- 작은 정수 곱셈·나눗셈 전용 경로를 둔다(64비트 한 칸). 몫과 나머지는 일반 경로와 수학적으로 같아야 한다.
- jet 안에서 매번 다시 만드는 상수(ONE, 계수 곱 c·m, c·m(m−1), `from_i64` 값)를 미리 만든다.
- `zero()`·`trim` 호출 정리.
- **하지 않는 것:** 연산 순서·반올림 위치·테일러 항 수·범위 축소 방식 변경(그것은 C3b-2), 부동소수점 사용, 금지 플래그(-ffast-math, -Ofast, -march=native).
- 새 소스는 `c1b1_native/track.cpp`를 직접 고친다. **C3a 기준 소스는 봉인 사본** `c1b1_native/reference_c3a/track_c3a.cpp`(sha256 `e71293f2…` 고정, 시험이 확인)로 보존해 차등 시험 기준으로 쓴다.
  - 래퍼(`track.py`)와 통신 규약은 바꾸지 않는다.
- **해시 규칙(검토 지적 B1):** 이 Windows 작업 사본은 줄바꿈이 CRLF라 파일 해시가 원격(LF)과 다르다. 루트 `.gitattributes`는 규칙상 고치지 않는다. 그래서 C++ 소스 해시는 **줄바꿈을 LF로 바꾼 바이트**의 sha256으로 정의한다(`e71293f2…`는 LF 기준). 패널 도구의 기존 track.cpp 해시 검사도 같은 규칙으로 고친다(원격에서는 결과가 같다).
- **"정확한 정리"의 정의(검토 지적 M1, m6):** 봉인 C3a 빌드와 비교해 다음이 모두 같아야 한다.
  - 정상 응답 문자열
  - 거부·오류 응답 문자열과 **오류가 나는 경계**. C3a는 칸 수로 넘침을 판정한다(`mul`은 a.n + b.n > 28, `shl`은 정리 전 n > 29·정리 뒤 n > 28, `mag_add`는 28칸). 작은 정수 경로나 미리 계산한 곱이 이 판정을 없애면 C3a의 오류가 성공으로 바뀐다. 그래서 같은 경계에서 같은 오류를 내도록 검사를 남기고, 경계 입력(칸 수 합 27·28·29, 28칸 근처 shl)으로 시험한다.
  - 계약 밖 동작(음수 X의 `exp_neg`, `roundguard` s = 0, 음수의 큰 shr)도 그대로 둔다. 시험에 넣어 "무해한 보호 장치 추가"가 생기면 드러나게 한다.
- 실제 트랙이 쓰는 최대 칸 수를 C3b-1의 디버그 검사 빌드(`-DCHECK_INVARIANTS`)가 기록한다(넘침 경계까지의 여유를 보이기 위함). C3b-0은 C++ 소스를 바꾸지 않으므로 이것을 재지 못한다.

## 4. 시험과 판정 (C3b-1, 실행 전 고정)

**부품 시험(원격 PC):**
1. **기존 C3a 부품 시험 26개 + 패널 도구 순수 시험 15개**가 새 소스로 모두 통과해야 한다.
2. **차등 시험(새 시험 파일 `c1b1_native/tests/test_c3b_diff.py`):** 봉인 C3a 빌드와 새 빌드에 같은 명령을 넣고 응답 문자열이 완전히 같아야 한다.
   - `calc` 전 연산(add, sub, mul, divmod, shl, shr, isqrt, halfeven, expneg, exitcheck, roundguard). 무작위 입력 각 2,000건(시드 고정). 음수, 0, 경계 크기(1칸, 27칸), 정확한 절반 포함.
   - `jet`: r = 2 … 40(로그 61점) × 작업 정밀도 60·68·77·80자리 해당 W.
   - `kickval`: 개발 패널 G1·B2·B6 시작 상태, 레벨 0·4, 기울기 항 있음/없음.
   - 트랙: G1·B6 시작, 레벨 0·2·4, `to 300` 뒤 상태 줄 전체(틱, 걸음, 바퀴, raw, kick 수; cpu_ns 제외).
   - 거부·오류 응답(나눗셈 0, 음수 제곱근, 출구 띠, 넘침 경계)도 같은 문자열이어야 한다.
   - **명령을 섞은 순서(검토 지적 M3):** init → to 100 → kickval → jet → to 200 → 다시 init → to 300. 작은 MAX로 to_exit("no exit") 뒤 to. kick 거부가 난 뒤의 상태. 모든 상태 줄을 비교한다. **KDK 트랙**도 같은 순서로 비교한다.
   - **별칭(검토 지적 m7):** 출력이 입력과 같은 변수인 경우(`sum = mul(sum, sum)`, 제자리 shr에서 잘린 비트 판정 전 덮어쓰기)를 전용 calc 입력과 트랙 비교로 확인한다.
   - **음의 0(검토 지적 M2):** `to_hex`는 n = 0이면 부호와 무관하게 "0"을 찍으므로 응답 비교로는 음의 0을 못 잡는다. 그런데 `cmp`, 출구 판정, 바퀴 세기는 부호를 본다. 그래서 디버그 빌드(`-DCHECK_INVARIANTS`)에서 모든 연산 뒤 "n = 0이면 양수, 맨 위 칸 ≠ 0"을 검사하고, 그 빌드로 차등 시험 전체를 한 번 더 돈다. 0이 결과인 calc 입력도 넣는다.
3. **결함 주입 6종**(기존 `-DINJECT`)이 새 소스에서도 시험에 잡혀야 한다.
4. **봉인 사본 확인:** `track_c3a.cpp` sha256 = `e71293f2…`. 다르면 시험 실패.
5. **정적 시험:** 새 소스에 `float`·`double`·`<cmath>` 없음(기존 시험 그대로).

**재현(R):**
- 개발 패널 14개를 새 C++ 빌드로만 돌린다. 각 입력의 새 C++ 세계를 C3a-4 결과 파일(`C1B1_C3A4_PANEL_V0.jsonl`)의 **파이썬 줄에 들어 있는 세계 전체**와 기존 `classify`로 직접 비교한다(검토 지적 M5. 압축본의 `world_sha256` 직렬화 규칙에 기대지 않는다). 파이썬 쪽은 다시 돌리지 않는다(C3a-4에서 이미 C3a C++와 같음을 보였다).
  - 비교 도구 `tools/c1b1_c3b_compare.py`(survey_only)를 새로 쓴다.
  - 패널 도구의 track.cpp 해시 강제는 **허용 목록**으로 바꾼다: C3a(`e71293f2…`)와, 커밋된 C3b-1 소스 해시 하나(검토 지적 m2). 임의 해시는 받지 않는다. 패널 도구를 고치면 그 도구 자신의 해시도 C3a-4 manifest와 달라진다. C3a-4 증거는 그대로 유효하고, 이 사실은 결과에 적는다.
- **T7 봉인 51건(검토 지적 m1):** 차등 시험과 패널이 모두 통과한 **뒤에 한 번만** 돌린다. T7에서 다르면 T7을 보며 고치지 않고, 멈추고 설계자에게 보고한다(T7이 개발 자료가 되지 않게).
  - 재현 도구에 manifest(track.cpp LF 해시, 실행 파일 경로)를 추가해 결과를 소스에 묶는다(검토 지적 m3).

**속도(S, 정보용):** C3a-5 도구(`tools/c1b1_native_speed.py`)를 새 빌드로 단독 실행해 C3a-5와 비교한다.

**판정:**
- 차등 시험·패널 sha256·T7 51건이 모두 같으면 C3b-1 통과.
- 하나라도 다르면 실패. 원본 보존, 원인·영향·반례 관문. 3회 규칙(이 계획의 실패 횟수는 0부터 센다. C3a 실패 1회는 별도).
- 거부(UNRESOLVED)가 나오면 C3a와 다른 거부인지 본다. C3a에서 거부가 없던 입력이므로 새 거부는 실패로 센다(정확한 정리라면 거부도 같아야 함).

**예측(실행 전, UNCONFIRMED):**
- C3b-0: `exp_neg`와 그 안의 `mul`·`floordiv`가 걸음 시간의 절반 이상. 구조체 복사(`zero`, 반환값)가 눈에 띄는 몫(10–30%).
- C3b-1: 걸음당 1.5–3배 빨라짐(120 µs → 40–80 µs). 계산 순서를 바꾸지 않으므로 큰 배수는 기대하지 않는다. 더 큰 이득은 C3b-2(exp 방식) 쪽일 가능성이 크다.

- G1 레벨 0, B6 레벨 4에서도 같은 모양이다(exp_neg 49–54%, mul 43–48%).
- **예측 대조:** "exp_neg와 그 안의 mul·floordiv가 절반 이상" 맞음(exp_neg 54%). "구조체 복사 10–30%" 대체로 맞음(trim·zero만 약 9%, 값 반환 복사는 mul 등의 자체 시간에 섞여 따로 안 보임).

**C3b-1 대상 확정(정확한 정리, 순서·반올림 위치 그대로):**
1. `mul`: 결과를 출력 인자에 직접 쓰기(구조체 값 반환·0 채우기 줄이기). 작은 쪽이 한 칸이면 한 칸 곱 경로. **넘침 판정(`a.n + b.n > 28`)은 그대로 둔다**(검토 지적 M1).
2. 작은 양의 정수로 나누는 `floordiv(x, from_i64(n))`(exp 테일러 항, jet 급수 항): 한 칸 전용 floor 나눗셈. 음수 x의 floor 의미를 Python과 같게.
3. `shr`·`mag_shr`·`add`·`sub`: 제자리 버전, `trim`·`zero` 호출 정리.
4. jet 안 `std::vector` → 고정 크기 배열.
5. 상수 미리 만들기(`from_i64(m)`, ONE 등). 값이 같으므로 결과 불변.
- **예측(실행 전, UNCONFIRMED):** 걸음당 1.5–2.5배(117 µs → 50–80 µs). 계산 횟수 자체(곱 764번/jet)는 그대로이므로 그 이상은 C3b-2(지수 함수 방식) 몫이다.

## 자기반박

- **가장 약한 곳:** "정리만으로 1.5–3배"는 근거 없는 추정이다. C3b-0 결과가 exp 알고리즘 자체(항 수·제곱 횟수)를 주된 비용으로 보이면, C3b-1의 이득은 작고 실제 이득은 C3b-2에 있다. 그 경우 C3b-1을 작게 끝내고 C3b-2 결정을 바로 올린다.
