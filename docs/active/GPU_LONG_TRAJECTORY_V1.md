## 0. 한 줄 결론

**GPU 혼합 경로가 1000걸음을 연속으로 가도 CPU E2와 끝점까지 같았고, 처음 갈라진 걸음은 한 번도 없었다.**
- 고정 p 1000걸음 11 pass에서 매 걸음(다섯 검사 지점) 비교한 걸음 10,914개 중 불일치 0.
- 장기 정지(N12 p64, N16 p64)는 CPU와 같은 state, 같은 pair, 같은 종류에서 멈췄다.

**P2가 실제로 만드는 정밀도 73, 78, 161, 166을 GPU가 모두 정확히 처리했다.** GPU가 지원하지 못한 정밀도는 없었다. 정밀도 위장(요청 73·장치 78 등)은 검출된다.

**정밀도 재시도 서비스도 CPU와 같은 결과**를 냈다.
- BASE64: N12 [64, 73, 161], N16 [64, 78, 166]. 기존 V2 CPU 서비스와 같은 순서다.
- FAMILY_MAX: 둘 다 [163] 첫 시도 성공.
- 모든 재시도 pass는 원래 초기 상태에서 다시 시작했다. 서비스 5개의 pass 22개가 checker 계산과 같았다.

**속도(이 호스트, T=1000, p163)**: N12 GPU 6.2초 대 CPU W6 15.2초(0.41), N16 6.6초 대 28.9초(0.23). 둘 다 GPU_WIN이다.

**판정: GPU_V1_READY.** GPU 실행 경로를 다음 단계의 정식 실행 후보로 동결한다(§6).

## 1. 무엇을 했나 (쉬운 말)

비유: 지난 단계에서 공장(GPU)이 만든 힘으로 장인(CPU)이 100걸음 움직여도 같았다. 이번에는 세 가지를 더 시켰다.
1. **1000걸음**을 쉬지 않고 이어서 움직인다.
2. 낮은 정밀도(p64)로 달리다가 900걸음 넘어서 "증명 불가"로 멈추면, **기존 규칙(P2)이 정한 더 높은 정밀도로 처음부터** 다시 달린다. 이 규칙이 만드는 숫자(73, 78, 161, 166)를 공장이 정확히 다룰 수 있어야 한다.
3. 공장이 모르는 정밀도가 나오면 몰래 가까운 숫자로 바꾸지 않고, **그 정밀도 그대로 장인이 대신** 하게 한다.

**GPU가 아는 정밀도는 원래 64, 109, 128, 163, 192뿐이었다.** 그런데 실제 재시도는 73, 78, 161, 166을 만든다. 그래서 이번 단계에 관문 P(정밀도 지원 관문)를 먼저 두었다.
- 기존 `gpu_host.py`는 수정하지 않았다.
- 새 파일 `support.py`가 기존 올리기 함수를 호출하는 동안에만 목록에 그 p 하나를 더한다. 반올림, limb, exp 알고리즘, 작업 정밀도는 그대로다.
- 정확하지 않으면 "지원하지 않음"으로 기록하고 수치 의미를 바꿔 맞추지 않는 규칙이었는데, 새 정밀도 4개 모두 정확해서 이 규칙을 쓸 일이 없었다.

실제 의미(`stream.run`과 같은 순서, 1000걸음):

```
F_0 = forces(q_0)                    (GPU)
for s = 0 .. 999:
    p_half  = p_s + F_s              (CPU)
    q_{s+1} = q_s + p_half * CDT     (CPU)
    F_{s+1} = forces(q_{s+1})        (GPU)
    p_{s+1} = p_half + F_{s+1}       (CPU)
```

- 힘 계산은 통과한 pass에서 정확히 1001번(앞 걸음의 F를 재사용), 정지한 pass에서는 정지 state+1번이다.
- 한 pass 안에서는 CUDA 컨텍스트, 모델 업로드, 메모리 할당이 0번이다. checker가 매 pass 확인했다.
- 서비스: 첫 p는 BASE64가 64, FAMILY_MAX가 163이다. 그 뒤 p는 **기존 P2(`precision_pilot_a1.policies`, 수정 없음)**가 정한다. 모든 pass는 원래 (q0, p0)에서 시작한다.

**궤적 묶음(코드보다 먼저 봉인, `e993112f…`)**
- `stream.run` 복제본(수정 없음)으로 N12 p64/73/161/163, N16 p64/78/166/163, N40 p109를 T=1000까지 돌려 기록했다.
- N12·N16의 8개는 **V2 Vast 기준(원본 증거)과 모두 같았다.**
- 장기 정지의 state는 요약 문서가 아니라 V2 원본에서 다시 읽었다. N12 p64는 state 996, N16 p64는 state 918이다. V2는 정지한 pair를 기록하지 않았다. 표본기가 정지 state의 위치에서 직접 구해 봉인했고, checker가 따로 다시 구했다. 둘 다 pair 0이다.

## 3. 정밀도 재시도 서비스

| 서비스 | 순서(pass별 결과) | V2 CPU 서비스 |
|---|---|---|
| N12 BASE64 | 64 DOMAIN_UNPROVEN(995걸음) → 73 UNDECIDED → 161 DECIDED | 같음 |
| N16 BASE64 | 64 DOMAIN_UNPROVEN(917걸음) → 78 UNDECIDED → 166 DECIDED | 같음 |
| N12 FAMILY_MAX | 163 DECIDED | 같음 |
| N16 FAMILY_MAX | 163 DECIDED | 같음 |
| N12 BASE64, 73을 GPU 미지원으로 가정한 시연 | GPU 64 → **CPU E2 p=73** → GPU 161 | 같은 순서, 표시 `GPU_WITH_CPU_PRECISION_FALLBACK` |

- 실행 방식 표시: 모든 pass가 GPU에서 돈 서비스는 `GPU_FULL_RETRY`, CPU 대체가 한 번이라도 있으면 `GPU_WITH_CPU_PRECISION_FALLBACK`이다.
- 시연에서 CPU 대체 pass는 p를 바꾸지 않았다(요청 p 73 = 실제 p 73).
- 서로 다른 정밀도의 끝점은 비교하지 않았다. 같은 p에서만 CPU와 끝점으로 비교했고, 정책 사이에서는 최종 DECIDED cells만 비교했다.

## 6. GPU V1 동결 계약 (ADAPTIVE_EXECUTION_V1이 GPU를 후보로 등록할 때의 계약)

- **의미**: GPU가 원자별 힘 F를 계산하고(쌍 → G → J → 원자별 정해진 순서 합산), CPU가 kick/drift를 한다(KDK 소유 = CPU). 모든 상태는 E2와 비트까지 같다.
- **정밀도 p**: 지원 집합 `{64, 73, 78, 109, 128, 161, 163, 166, 192}`.
  - 근거는 이전 단계(109, 128, 192), 이번 관문 P(73, 78, 161, 166), 기준 p(64, 163)이다.
  - 이 집합 밖의 p는 `REFUSED_DEVICE_PRECISION`이다. 그 요청은 **그 p 그대로 CPU E2가 실행**해야 하고, 가까운 p로 올리거나 내리면 안 된다(결과 표시 `GPU_WITH_CPU_PRECISION_FALLBACK`).
  - 새 p를 지원 집합에 넣으려면 관문 P와 같은 쌍 단위 검사를 새로 통과해야 한다.
  - 이번에 확인하지 않은 p(예: 100, 162)는 미지원이다.
- **N 증거**: N=12, 16(p163/166 등)에서 T=1000, N=40(p109)에서 T=1000, N=40/64/128(p109)과 N=64(p163)에서 T=100(이전 단계).
- **CPU/GPU 교차 증거(이 호스트)**: 측정한 N=12, 16(p163, T=1000)에서 GPU_WIN.
  - 이전 단계(3090/5950X 호스트, 100걸음)에서는 N=12가 동률(TIE), N=16은 GPU 우세였다.
  - 즉 **교차점은 호스트에 따라 다르다.** 절대 시간을 섞지 않고 분류만 보면 N=12 근처가 경계다. N=13–15와 N<12는 UNKNOWN이다.
- **CUDA 소스**: `pv1.cu` sha256 `840d5037…`, `g0.cu` `dc519a9c…`, 호스트 코드 `gpu_host.py` `dd255cb3…`, `pv_host.py` `bded5b8e…`, `compile_plan.py` `cc63a1e5…`(모두 LF 정규화 해시, env.json에 전체값). 빌드한 라이브러리 해시 `9af84a87…`, 아키텍처 sm_89.
- **mpmath**: 1.3.0, 순수 파이썬 백엔드. 이 exp 알고리즘 재현에 의존하며, 다른 버전·백엔드에서는 깨질 수 있다(추정).
- **기본 블록**: 32. 보편 법칙이 아니며 이번에도 다시 학습하지 않았다. 32/64/128/256에서 결과는 같았다.
- **장치 폭**: 가수 6 limb(최대 192비트 p), 작업 16 limb, 레지스터 16개, 프로그램 221연산. 폭을 넘으면 `REFUSED_DEVICE_WIDTH`다.
- **오버플로·거부**: 거부는 상태로 보고되고(값 없음, 불일치로 세지 않음), 조용히 넘어가지 않는다. 측정 격자 범위 초과는 `OUT_OF_RANGE`로 별개다.
- **모델 업로드 규칙**: p가 바뀔 때만 모델·상수·exp 표를 다시 올린다(약 30 ms). 한 pass 안에서는 업로드·할당·컨텍스트 생성이 0번이다.
- **힘 재사용 규칙**: 앞 걸음의 F_{s+1}을 다음 걸음의 F_s로 쓴다. 완료 pass의 힘 계산은 T+1번이다.
- **서비스 의미**: 첫 p는 정책이 정하고, 이후 p는 동결 P2가 정한다. 모든 pass는 원래 (q0, p0)에서 시작한다.

## 8. 한계·공개

- **T=1000까지다.** 그 이상, 장시간 누적, 다른 N 구간의 1000걸음은 확인하지 않았다. N64/N128의 T=1000은 CPU 기준 계산만 30–65분이 들고 이번 질문(N12/16의 정밀도 재시도)에 필요하지 않아 하지 않았다.
- **증명이 아니다.** 봉인된 궤적 9개와 서비스 5개에서의 비트 일치다.
- **N40 p109 T1000은 최종 DECIDED가 아니다**(UNDECIDED_AT_PRECISION). 궤적이 정확하다는 것만 확인했다. 외부 검증 기준이 없고, 기준은 복제본과 독립 checker 두 가지다.
- **다른 정밀도 사이의 끝점은 비교하지 않았다**(규칙). 정책 사이에서는 최종 DECIDED cells만 비교했다.
- **관문 P의 d**는 장치 출력이 아니라서 r²와 J로 간접 확인했다.
- **결함 2(힘 재계산)류는 값으로 잡을 수 없다**(결정론). 이번에는 서비스·pass에서 힘 계산 횟수로 확인했다. 결함 13은 +1이 아니라 "다음 지원 p로 올림"으로 구현했다(검출 방식은 같다, 정정1).
- **호스트 잡음**: 공유 노드라 CPU W6 수치가 흔들린다(N12 첫 회 18.1초 등). GPU 수치는 1% 이내였다. 또 이번 N12 GPU_WIN(0.41)은 이 호스트에서의 결과다. 이전 호스트의 100걸음 TIE와는 다른 호스트·GPU·CPU 조합이라 직접 비교할 수 없다.
- **로컬 PC 사용에 대한 공개**: 코드 봉인 전에 궤적 묶음 생성, 사전 점검, 시험을 설계자의 PC에서 돌렸다. "Vast가 필요하면 요청하라"는 지시를 어기고 PC를 과부하시켰다. 이후 제 프로세스를 모두 종료했고, 공식 실행과 시험 전체는 Vast에서 했다(정정1에 기록). 데스크톱에서 시험 파일 전체를 한 번에 통과시킨 기록은 없고, Vast에서 25/25를 통과했다.
- **서비스 서버 정지**: 증거를 받은 즉시 정지했고, exited를 확인했다. 공식 job은 약 58분이었다(시험 7.5분, 관문 P 0.3분, 고정 p 약 16분, 서비스 약 17분, 성능 약 17분).
- **LOCAL FULL은 생략했다.** 새 실험 파일만 추가했고, 기존 실행 코드·동결 계약·이전 GPU 파일은 바꾸지 않았다. 관련 시험 25개(Vast Linux)로 대신했다.
- 기존 evidence와 이전 단계 코드는 수정하지 않았다.

## 9. 쉬운 말로 답하는 14가지

1. **1000걸음에서도 CPU와 끝자리까지 같았나?** 예. 11 pass, 걸음 10,914개, 불일치 0.
2. **처음 갈라진 걸음이 있었나?** 없다. 갈라진 걸음을 찾는 장치(첫 불일치 기록)는 결함 시험에서 정확한 걸음·원자·성분·끝점을 짚는 것을 확인했다.
3. **p64 장기 실패가 같은 state/pair에서 났나?** 예. N12 state 996 pair 0, N16 state 918 pair 0이다. V2 원본의 stop_step과 같다.
4. **P2가 같은 다음 p를 골랐나?** 예. 64 → 73 → 161, 64 → 78 → 166이고 V2와 같다.
5. **재시도가 항상 처음 상태에서 다시 시작했나?** 예. 22 pass 모두 원래 q0, p0에서 시작했다.
6. **73, 78, 161, 166을 GPU가 정확히 지원했나?** 예. 모두 쌍 단위로 정확했다.
7. **지원 못 하는 p가 있었다면?** 없었다. 가정 시연(73을 미지원으로 둠)에서 그 p 그대로 CPU가 실행하고 표시를 바꾸는 것을 확인했다.
8. **FAMILY_MAX p163은 첫 시도 성공했나?** 예, N12와 N16 모두.
9. **N12 T1000은 누가 유리한가?** 이 호스트에서는 GPU(0.41). 이전 호스트의 100걸음에서는 동률이었다. 경계는 호스트에 따라 다르다.
10. **N16 T1000은?** GPU(0.23).
11. **실패 pass가 전체 비용을 얼마나 먹었나?** BASE64 서비스 전체 시간의 GPU 53–55%, CPU W6 63–68%.
12. **정밀도가 바뀔 때 GPU 재업로드 비용은?** 약 20–30 ms로, pass 시간의 1% 미만이다.
13. **GPU 경로를 정식 후보로 동결해도 되나?** 예(§6의 계약 조건으로).
14. **ADAPTIVE_EXECUTION_V1에서 쓸 수 있는 GPU 지원 영역은?** p는 `{64, 73, 78, 109, 128, 161, 163, 166, 192}`, N은 증거가 있는 12–128 범위(그 사이는 UNKNOWN)이며, 지원 밖은 CPU 대체다.
