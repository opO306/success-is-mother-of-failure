# GPU_FORCE_FEASIBILITY_V1 (G0) — E2의 G(R²) 구간을 GPU에서 의미를 바꾸지 않고 계산할 수 있나

상태: **결과 기록 (2026-10-07)**. checker **EVIDENCE OK**, 판정 **G0_PROMISING**.
- 공식 측정: Vast 52763685, Threadripper PRO 3975WX + RTX 3090.
- 데스크톱에서 독립 재검사·재분석한 결과가 JSON까지 같았다.
- 데스크톱 RTX 4060 교차 확인: 29개 실행의 출력 바이트가 모두 같았다.

증거 수준 = 실행 + 독립 checker. 샘플 11,928개에 대한 비트 일치이며 formal 증명이 아니다. 승격 아님.
범위는 **스칼라 G(R²)만**이다. 벡터 충격량·축약·KDK·궤적은 GPU로 옮기지 않았다.
브랜치 `claude/gpu-force-feasibility-v1`(부모 `1a73d95`, 메인 checkout, worktree 없음, push 없음).
커밋: protocol `8ca0b2f` → 샘플 봉인 `dd55c41` → 코드 봉인 + 정정1 `b6a77ba` → 정정2(호스트 변경) `98aadcf` → 증거·문서.

## 0. 한 줄 결론

**GPU가 계산한 G(R²) 구간 11,928개가 모두 CPU E2(mpmath)와 끝점까지 비트 단위로 같았다(EXACT 100%, UNSOUND 0, 거부 0).**
- 블록·그리드 12가지 배치, 두 GPU(4060·3090), 두 OS(Windows·Linux)에서 출력 바이트가 모두 같았다.

**속도는 같은 호스트의 CPU W6보다 7–14배 빨랐다.** 2016쌍(N=64 한 걸음 분량)에서 GPU 전체 23.6 ms, W6 246–339 ms였다(p=109).
- 단, 이제 시간의 대부분은 GPU 계산이 아니라 **파이썬에서 구간을 바이트로 바꾸고 되돌리는 일(encode/decode)**이다. 32768쌍에서 351 ms 중 kernel은 11 ms, encode·decode가 339 ms였다.

## 1. 무엇을 했나 (쉬운 말)

비유: CPU라는 장인이 손으로 하던 계산 한 단계를, GPU라는 수천 명 공장에 맡겨도 **똑같은 물건**이 나오는지 본 것이다.
- 공장 작업자에게는 장인의 작업 지시서(계산 순서)를 그대로 베껴 주었다.
- 같은 반올림 규칙도 그대로 지키게 했다.
- 완성품은 장인이 직접 만든 것과 하나하나 대조했다.

실제 의미:
- **기준(CPU E2)**: `rewrite_pilot_a3/rwforce.RwForce`(rw:R1+R2)를 mpmath 1.3.0 구간 산술로 p비트에서 계산한다.
- **mpmath 소스를 먼저 읽었다**(정확한 반올림 여부가 설계를 결정하기 때문이다):
  - 덧셈·곱셈은 정확한 결과를 지정 방향으로 반올림한다.
  - 나눗셈은 여분 비트와 sticky 비트를 써서 정확히 반올림된다.
  - 제곱근은 isqrt/sqrtrem으로 정확히 반올림된다.
  - **exp는 정확히 반올림되지 않는다.** 정해진 정수 알고리즘(작업 정밀도 wp = p + 14, ln2로 나눈 몫과 나머지, 테일러 급수 + 제곱 반복)의 결과를 반올림한다.
  - 따라서 GPU가 **같은 정수 연산을 한 단계씩 똑같이** 하면 끝점까지 같아질 수 있다. 그렇게 만들었다.
- **계산 순서는 추적으로 얻었다**: 동결된 `RwForce.__call__`을 기호 값으로 한 번 실행해 연산 순서를 기록했다(메모리 안에서만 바꾸고 복원했으며 파일은 수정하지 않았다).
  - 결과는 221개 연산이다: 곱셈 110, 덧셈 85, 부호 반전 10, exp 9, 나눗셈 2, 제곱근 1, 뺄셈 1, **영역 의무 2개**(R² > 0, den > 0).
  - 상수 98개, 동시에 살아 있는 값은 7개다.
  - 이 순서를 mpmath로 재생하면 RwForce와 같았다.
- **상수**: 동결 객체가 p비트에서 만든 구간 상수와 ln2_fixed 표를 그대로 GPU에 올렸다("model upload").
- **GPU 코드**: `experiments/gpu_force_feasibility_v1/g0.cu`. 스레드 하나가 샘플 하나를 끝까지 계산한다.
  - 32비트 limb 정수 기본연산은 `a_physics_native/ar2_b2.cu` 44–256행에서 복사했다(출처와 hash 기록, 원본 파일은 수정하지 않음).
  - 넘침은 poison으로 표시해 **거부**한다(잘라내거나 몰래 감지 않음).
  - mpf/mpi 계층, exp 재현, 해석기는 새로 썼다.
- **샘플**: 실제 E2 궤적 4개(N=40·64 T=100 p=109, N=12·16 T=1000 p=163)를 돌리며 0, T/10, T/2, T 걸음의 모든 쌍 R²를 채취했다.
  - 네 궤적 모두 V2 Vast 직렬 기준과 최종 결과가 같았다.
  - 11,928개를 GPU 코드보다 먼저 봉인했다(`6c4c73a3…`).
  - 직렬화는 (부호, 가수 hex, 2진 지수, 비트 수)로 정확하게 했다. float도 10진 문자열도 쓰지 않았다.

## 4. 12개 질문

1. **GPU 구간이 CPU E2 구간을 100% 포함했나?**
   예. 11,928 / 11,928이다. 단순히 포함한 정도가 아니라 끝점까지 같았다.
2. **끝점 완전 일치 비율은?**
   100%다(본 샘플 11,928, 시험 전용 768).
3. **구간 폭은 얼마나 넓어졌나?**
   넓어지지 않았다. 폭 비율이 모든 샘플에서 1.0이다.
4. **p=109와 163에서 차이가 있나?**
   정확성은 둘 다 100% 일치했다. 속도는 p=163이 kernel 기준 약 1.45배 느렸다(7.5 vs 5.2 ms).
   전체 시간에서는 encode·decode가 커서 차이가 작았다(2016쌍 27.5 vs 23.6 ms).
5. **넘침·거부가 있었나?**
   본 측정에서는 0이다.
   - 작업 폭을 일부러 줄인 시험(8 limb)에서는 정상 코드가 모두 **거부**했고, 몰래 틀린 값을 내지 않았다.
   - 지원하지 않는 p(예: 100)는 실행 전에 거부한다.
6. **GPU 결과가 블록·그리드 크기에 따라 달라지나?**
   아니다. 12가지 배치, 두 GPU, 두 OS에서 출력 바이트가 같았다.
7. **warm GPU 배치는 CPU 직렬보다 언제 빨라지나?**
   측정한 가장 작은 배치(128쌍)부터 빨랐다(약 15배). 큰 배치에서는 약 60배다. 128쌍보다 작은 배치는 측정하지 않았다.
8. **W6보다는 언제 빨라지나?**
   역시 128쌍부터 빨랐다(p=109에서 2.7배, p=163에서 1.7배). 780쌍 이상에서는 6–14배였다.
9. **전송·encode·decode를 포함해도 이기나?**
   예. 위 표의 GPU 시간이 이미 전부 포함한 값이다.
   다만 **포함하면 encode·decode가 GPU 시간의 대부분**(2016쌍에서 약 78%, 32768쌍에서 약 96%)이다. kernel만 보면 이득이 훨씬 커 보이지만, 그렇게 보고하지 않는다.
10. **작은 배치에서는 GPU가 손해인가?**
    측정 범위에서는 아니다. 다만 작은 배치에서는 kernel 시간이 4.5–7.5 ms에서 줄지 않는다(바닥 지연).
    - GPU 스레드 하나가 G 하나를 계산하는 데 수 ms가 걸린다. 같은 계산을 CPU 한 코어는 약 0.7 ms에 한다.
    - 쌍이 아주 적은 요청(N=12, 66쌍 등)에서는 이 바닥 지연이 W6과 비슷해질 수 있다(추론, 측정 안 함).
11. **실제 N=40·64 규모에서 의미 있는 이득이 있나?**
    G 계산 부분만 보면 그렇다. N=40(780쌍)은 W6 94 ms 대비 GPU 11.9 ms, N=64(2016쌍)는 W6 246–339 ms 대비 GPU 23.6 ms다.
    - 다만 이것은 한 걸음의 **G 계산만**이다. 한 걸음의 나머지(차이 벡터, 충격량 곱, 축약, KDK)는 아직 CPU에 있고 이번에 재지 않았다.
    - 그래서 궤적 전체가 몇 배 빨라지는지는 **모른다(UNRESOLVED)**.
12. **vector impulse까지 GPU로 옮길 가치가 있나?**
    봉인 규칙으로는 **G0_PROMISING → 다음 단계 GPU_PAIR_VECTOR_V1**이다. 단 이번 결과가 다음 설계에 주는 경고가 있다(추론).
    - **병목은 이미 GPU 계산이 아니라 파이썬 encode·decode다.**
    - 다음 단계에서 쌍마다 충격량 3성분을 받아 오면 decode가 3배로 늘어 오히려 손해일 수 있다.
    - 입력은 원자 위치(N×3)만 보내고, 출력도 원자별 합(N×3)으로 줄이는 방향이 유리해 보인다. 다만 축약을 GPU로 옮기는 일은 이번 금지 범위(축약 변경)와 겹치므로 설계자 판단이 필요하다.
    - 또 다른 길은 encode·decode 자체를 빠르게 만드는 것이다(벡터화). 이것도 측정하지 않았다.

## 6. 한계·공개

- **증명이 아니다.** 비트 일치는 봉인 샘플 11,928개(+시험 전용 768개)에 대한 확인이다.
  - 모든 R² 입력에서 같다는 증명은 없다.
  - mpmath의 다른 분기(mpmath가 무한대를 내는 경우, |x|가 아주 작은 exp, p > 192)는 지원하지 않고 **거부**한다.
- **mpmath 버전에 묶여 있다.** GPU는 mpmath 1.3.0(순수 파이썬 백엔드)의 정수 알고리즘을 그대로 따라 한다.
  - gmpy2 백엔드나 다른 mpmath 버전에서는 exp 결과가 달라질 수 있고, 그러면 비트 일치가 깨질 수 있다(추론).
  - 이번에 쓴 mpmath 파일들의 hash는 protocol에 봉인했다.
- **공유 호스트다.** Vast 52763685는 다른 손님과 같은 물리 기계를 쓰는 것으로 보인다.
  - 실행 중 loadavg는 4.3–6.4였고(10초 간격 기록), 시작 직전에는 15.6에서 내려오는 중이었다.
  - W6 회별 시간이 2016쌍에서 249–339 ms로 흔들렸다. GPU 시간은 1% 안에서 안정적이었다.
  - 그래서 W6 대비 배수는 대략 범위로 읽어야 한다.
- **호스트 변경(정정2).** 공식 호스트를 52763629(5950X, 자원 없음)에서 52763685(3975WX)로 바꾸었다(설계자 결정). 모든 기준선은 새 호스트에서 새로 쟀고, 호스트 사이의 절대 성능은 비교하지 않는다.
- **W6 기준선의 형태.** 작업자 6개가 R² 구간 튜플을 pipe로 받아 G 튜플을 돌려준다. E2 실제 작업자는 위치를 받아 충격량까지 계산하므로 완전히 같은 일은 아니다.
- **순서 공개(정정1).**
  - 샘플 봉인 전에 GPU 코드를 썼고, 합성 입력 7개로 smoke 시험을 돌렸다.
  - 샘플 선택은 protocol에 미리 정해져 있었고, GPU 결과를 보지 않았다.
  - 데스크톱 성능 시험 실행 중 Windows multiprocessing 제약으로 멈춘 내 프로세스 1개를 직접 종료했다.
- **시험 비용.** Vast 작업은 약 5분(02:59–03:04 UTC)이었고, 증거를 받은 뒤 바로 정지시켰다(정지 확인). LOCAL FULL은 생략했다(새 실험 파일만 추가, 기존 실행 코드·동결 계약 불변). 관련 시험 18개(데스크톱)와 18개(Vast Linux)로 대신했다.
- 기존 evidence와 기존 CUDA 실행기는 수정하지 않았다.
