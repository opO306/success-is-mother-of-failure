- 공식 측정: Vast 52763629, Ryzen 9 5950X + RTX 3090(정정2).

## 0. 한 줄 결론

**관문 A: GPU가 만든 쌍별 3차원 충격량 J(x·y·z, 각 위·아래 끝점)가 13,502쌍 모두 CPU E2와 비트 단위로 같았다.**
- d, R², 영역 판정(K.domain), G, 영역 의무 2개까지 전부 같았다.

**관문 B: GPU 안에서 CPU와 같은 순서로 더한 원자별 힘 F가 1,842개 성분 모두 끝점까지 같았다.**
- atomic도 트리 합산도 쓰지 않았다.

**속도(같은 서버, 힘 한 번 계산)**: GPU B(원자별 합까지 GPU)가 CPU W6보다 빨랐다.
- N=40에서 13배(6.5 vs 82 ms), N=64에서 30배(7.3 vs 218 ms), N=128에서 82배(10.6 vs 874 ms).
- 다만 **작은 N(12·16, p=163)에서는 이득이 없었다**(7.7 vs 7 ms, 7.9 vs 13 ms). GPU에는 약 6–7 ms의 바닥 지연이 있기 때문이다.

## 1. 무엇을 했나 (쉬운 말)

비유: G0에서는 공장(GPU)이 "두 원자 사이 힘의 세기" 하나만 만들었다. 이번에는 두 가지를 더 맡겼다.
- **관문 A**: 원자 위치를 받아 방향까지 붙인 힘(충격량 x·y·z)을 쌍마다 만든다.
- **관문 B**: 그 충격량들을 원자별로 모아 최종 힘을 만든다.

모으는 순서는 장인(CPU)과 똑같이 했다. 구간 계산에서는 덧셈 순서가 바뀌면 끝점이 달라질 수 있기 때문이다.

실제 의미:
- **기준**: `exact_expression_gate_v1.stream.run`의 `forces(q, step)`(E2 힘)다.
  - 쌍 (i<j)을 사전순으로 돈다.
  - d[k] = q[j][k] − q[i][k]
  - r² = (d0·d0 + d1·d1) + d2·d2
  - K.domain(r²)가 PROVEN이 아니면 멈춘다.
  - g = G(r²)
  - k마다 t = (h·g)·d[k]를 만들어 F[j][k] += t, F[i][k] −= t
- **GPU**: G0의 `g0.cu`를 **수정 없이 포함**하고(G0 장치 산술과 G 프로그램 재사용) 커널 4개를 새로 썼다(`pv1.cu`).
  1. 쌍마다 d, r², 영역 판정. R_MIN²는 유리수 a/b로 올려 정확히 비교한다.
  2. 쌍마다 G.
  3. 쌍마다 J = (h·g)·d[k]. 소스와 똑같이 k마다 h·g를 다시 계산한다.
  4. 원자 a·성분 k마다 스레드 하나가 쌍 (i,a), i<a에 대해 +J, 그다음 (a,j), j>a에 대해 −J를 차례로 더한다. 이것이 CPU 루프가 F[a][k]를 건드리는 순서와 정확히 같다.
- **입력**: 원자 위치 구간 전체(N×3)를 정확한 dyadic 워드로 보냈다. GPU 안의 위치 버퍼를 되돌려 받아 봉인 묶음과 비교했다.
- **샘플**: G0와 같은 실제 궤적 4개, 0·T/10·T/2·T 걸음의 위치와 그때 계산된 힘을 기록했다.
  - 기록 방법: `stream.run` 자신의 소스에 관찰 한 줄을 넣은 복제본을 실행 중에 만들었다. 파일은 바꾸지 않았다.
  - 네 궤적 모두 검증된 Vast 직렬 기준과 최종 결과가 같았다.
  - GPU 코드보다 먼저 봉인했다(`bd8c8a2d…`).
- **B1을 고른 이유(실행 전에 protocol에 기록)**:
  - B1: 쌍 결과를 GPU 메모리에 두고 합산한다. G를 쌍마다 한 번만 계산하고, 검증이 끝난 A의 결과를 그대로 쓴다. 메모리는 O(N²)다.
  - B2: 원자별 스레드가 자기 쌍을 다시 계산한다. 메모리는 O(N)이지만 G를 쌍마다 두 번 계산하고, 스레드 하나가 G를 N−1번 연달아 계산해야 한다.

## 4. 12개 질문

1. **GPU가 실제 x/y/z 힘까지 CPU와 똑같이 만들었나?**
   예. 쌍별 충격량 13,502개와 원자별 힘 1,842개 성분이 모두 끝점까지 비트 단위로 같았다. 블록·그리드 12가지, 두 GPU, 두 OS에서도 같았다.
2. **쌍별 결과를 전부 CPU로 가져오면 얼마나 느려지나?**
   N=64에서 GPU 안 합산(B)은 7.3 ms인데, 쌍별 결과를 가져와 CPU에서 합치면(A) 33.1 ms로 약 4.5배 느리다.
   - 늘어난 시간은 decode 11.1 ms와 CPU 합산 16.2 ms다.
   - N=128에서는 B 10.6 ms 대비 A 112.3 ms로 약 11배 느리다.
3. **GPU 안에서 합치면 반환 데이터가 얼마나 줄었나?**
   N=64에서 6,048개 구간(2016쌍 × 3)이 192개(64원자 × 3)로, 31.5분의 1이 됐다. N=128에서는 24,384개가 384개로, 63.5분의 1이 됐다.
   decode는 11.1 ms에서 0.31 ms로 줄었다(N=64).
4. **GPU 합산 결과도 끝점까지 같았나?**
   예. 1,842 / 1,842다.
5. **atomic 없이 같은 순서를 재현할 수 있었나?**
   예.
   - 원자·성분마다 스레드 하나가 정해진 순서로 더했다: (0,a), (1,a), …, (a−1,a)에 +, 그다음 (a,a+1), …, (a,N−1)에 −. CPU 루프와 같은 순서다.
   - 순서를 일부러 바꾼 결함(10)과 배치마다 순서가 달라지는 결함(11)은 checker가 잡았다. 순서가 실제로 결과를 바꾼다는 확인이기도 하다.
6. **N이 커질수록 메모리는 얼마나 늘어나나?**
   쌍 수에 비례한다(O(N²)). 합계는 N=64에서 3.0 MB, N=256에서 47 MB, N=1024에서 759 MB다. RTX 3090(24 GB)에서는 N=1024도 충분하다(계산값, 실제로 N=1024를 돌리지는 않았다).
   - 지금 버퍼에는 검증용 전체 기록(쌍마다 r²·G·J)과 압축 기록이 둘 다 들어 있다. 실제 서비스에서는 빼서 약 절반으로 줄일 수 있다(추론).
7. **계산을 두 번 하는 방식(B2)이 메모리 면에서 이득인가?**
   메모리만 보면 크게 이득이다(N=1024에서 0.6 MB vs 759 MB). 하지만 이번 크기에서는 이득이 필요 없고, 계산 면에서는 크게 손해로 보인다(추론, B2는 구현하지 않았다).
   - G 하나에 GPU 스레드가 약 4.6–6.6 ms 걸린다. B2에서는 원자 스레드 하나가 G를 N−1번 연달아 계산해야 한다.
   - N=64라면 약 63 × 5 ms ≈ 0.3초가 될 것으로 추정한다(B1은 7 ms).
   - 메모리가 문제가 될 N(수천 이상)에서는 쌍을 묶음으로 나눠 처리하는 등 다른 방법을 따로 시험해야 한다.
8. **N=40/64 실제 규모에서 CPU W6보다 얼마나 빠른가?**
   GPU B 기준으로 N=40에서 12.7배(6.5 vs 82 ms), N=64에서 30배(7.3 vs 218 ms)다.
   - 이것은 힘 한 번 계산이다. KDK 한 걸음 전체(운동량·위치 갱신 포함)의 배수는 아직 모른다.
9. **p=109/163 차이는?**
   GPU는 p가 클수록 G 커널이 느려졌다(N=64에서 4.6 → 6.6 ms, B 전체 7.3 → 9.8 ms). CPU W6는 거의 같았다(218 → 223 ms).
   - 그래서 같은 N에서 GPU의 이득은 p=163에서 조금 작다(30배 → 23배).
10. **가장 큰 새 병목은 무엇인가?**
    - **GPU B**: 이제 GPU 계산 자체다.
      - G 커널의 바닥 지연(약 4.6–6.6 ms)이 거의 일정하다. 스레드 하나가 G 221개 연산을 순서대로 계산하기 때문이다.
      - 합산 커널은 원자·성분당 스레드 하나라 일거리가 적다. N에 비례해 길어진다(N=128에서 3.1 ms).
    - **작은 N**: 이 바닥 지연 때문에 N=12·16(p=163)에서는 GPU가 CPU W6보다 빠르지 않았다.
    - **GPU A**: 여전히 파이썬 decode와 CPU 합산이다.
11. **적은 block/grid 자원에서 더 효율적인 후보가 있었나?**
    있었다. 블록 32가 가장 빨랐다(N=64에서 블록 256보다 약 12% 빠름: 6.62 vs 7.53 ms). N=128에서는 차이가 3%로 작았다. 출력은 모두 같았다.
    규칙은 바꾸지 않았고 기록만 했다.
12. **다음 GPU 한 걸음 전체 시험으로 갈 가치가 있나?**
    봉인 규칙으로는 **GPU_PAIR_PROMISING → 다음 GPU_ONE_STEP_V1**이다.
    - 관문 A·B가 모두 끝점까지 같았고, N=40·64에서 B가 W6의 절반 이하였다(0.079, 0.033).
    - 같이 기억할 점(추론):
      - 작은 N 요청(T=1000의 N=12·16)은 GPU로 보낼 이유가 없다. 실행 계획(GpuExecutionPlan) 데이터가 그 경계를 보여 주기 시작했다.
      - 한 걸음 전체로 가면 운동량·위치 갱신은 N×3 구간이라 계산은 작다. 다만 그것까지 GPU에 두어야 매 걸음 위치를 주고받는 비용이 사라진다.

- **증명이 아니다.** 봉인된 실제 상태 16개와 시험 상태 8개에서의 비트 일치다.
- **mpmath 1.3.0(순수 파이썬)의 exp 정수 알고리즘을 재현한 결과다**(G0와 같다). 다른 mpmath 버전이나 gmpy2 백엔드에서는 일치가 깨질 수 있다(추론).
- **힘 한 번만 쟀다.** 운동량·위치 갱신과 KDK는 하지 않았다. 궤적 전체의 속도 배수는 모른다(UNRESOLVED).
- **정정2(호스트 변경)**: 52763685가 켜지지 않아 공식 호스트를 52763629(5950X + 3090)로 바꾸었다(설계자 결정). 모든 기준선을 새로 쟀고, G0(52763685)의 시간과 비교하지 않는다.
- **정정3(첫 실행 폐기)**: 첫 실행에서 CPU W6 기준선의 변경되지 않은 E2 작업자가 종료할 때 Windows 전용 CPU 측정 함수를 불러 멈췄다.
  - 그 실행의 프로세스는 번호(PID)로 종료했고, 결과는 상태 개수 외에는 보지 않고 버렸다.
  - EXPERIENCE_START_P_V2의 Linux 측정 장치(측정 함수 두 개만 교체)를 실행 스크립트에서 켜고, 빈 폴더에서 처음부터 다시 실행했다.
  - W6 시간은 메인 프로세스의 perf_counter로 쟀으므로 이 장치와 무관하다.
- **순서 공개(정정1)**:
  - 상태 묶음을 봉인하기 전에 GPU 코드를 썼다. 묶음 상태를 GPU로 계산한 것은 봉인 뒤다.
  - 관문 A와 B는 같은 GPU 실행 안에서 계산된다. 판정은 A를 먼저 하고, A가 정확할 때만 B를 본다.
- **W6 기준선의 형태**: 위치 메시지는 미리 만든 원시 튜플로 넘겼다. E2 메인이 ivmpf에서 메시지를 만드는 비용은 빠졌지만 작다(추론).
- **Vast 서버는 증거를 받은 즉시 정지했다**(exited 확인). 공식 실행 자체는 약 40초였다.
- LOCAL FULL은 생략했다(새 실험 파일만 추가, 기존 실행 코드·동결 계약·G0 파일 불변). 관련 시험 18개(데스크톱)와 18개(Vast Linux)로 대신했다.
- 기존 evidence와 기존 CUDA 코드는 수정하지 않았다.
