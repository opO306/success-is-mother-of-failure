## 1. 쉬운 설명

- **비유:** 공장에서 손으로 하던 계산 공정(파이썬)을 기계 라인(C++)으로 바꾼다. 같은 설계도에서 같은 부품이 나와야 한다. 검사원(파이썬 기준 계산·검증 층)은 그대로 둔다.
- **실제 의미:** 지금 걸음 하나에 0.79 ms가 든다. 대부분은 파이썬이 큰 정수 연산 하나하나를 해석하는 부담이다. 같은 정수 연산을 C++로 하면 그 부담이 사라진다.
- **왜 비트가 같아야 하나:** 프로젝트 원칙(수치 실행 계층 7.1절)이 충격량을 "참값을 계산한 뒤 한 번만 반올림"으로 정의한다. 그래서 계산 방법이 달라도, 충분히 정확하면 반올림 결과는 같다. 같은 원칙으로 C1(정수 jet)이 T7 10/10 비트 동일을 냈다.

## 3. 설계

**3.1 범위(C3a):** 트랙 하나 = `c1b1_method_bench.fixedpoint.FxTrack`(+ `FxTrackP` 정밀도, `c1b1_t7.ladder.FxTrackX` 정확 질량)과 같은 의미다.
- 시작: 기본 격자 raw를 트랙 격자(fp, fm)로 옮긴다(정확, 짝수 규칙 그대로).
- 한 걸음: Chin 4A다.
  - kick h/6 → drift h/2 → 기울기 보정 kick 2h/3 → drift h/2 → kick h/6
  - 첫 kick은 앞 걸음의 마지막 값을 재사용(`_J` 캐시와 같음)
- kick: J_k = round(c·q_k·2^fm), c = (−V′/r + h²V′V″/(24μr))·coef.
  - **μ 구분(검토 지적 3):** kick의 μ는 파이썬과 같은 **60자리로 반올림한 mpf 값**이다(`fixedpoint.py` `self.mu`). 파이썬이 (가수, 지수)로 넘긴다. drift의 μ는 정확한 분수다.
  - 작업 정밀도 W도 C++가 다시 계산하지 않고 파이썬이 넘긴다.
  - 파이썬의 `_round_mpf`와 같은 규칙: 가장 가까운 값, 반올림 경계 1e-30 격자 단위 안이면 **거부**(Undecided)
- drift: q_raw += 2·half_even(p_raw·d·2^fp/(2^fm·2μ)). μ는 정확한 분수(정수 분자·분모), 계산은 정확 정수다.
- 틱: 2^j 걸음.
  - 걸음마다 휩쓴 각에 signed_angle(앞 위치, 뒤 위치)를 더한다.
  - 출구 = r ≥ 20이고 p_r > 0인 첫 틱. C++에서는 q·q ≥ 400·2^(2fp), q·p > 0의 **정확 정수 비교**로 판정한다(파이썬은 60자리 mpf. 4절 C 참조).
- 사다리(`pen_state`), est 계산, 출력 사전 구성은 **봉인된 `c1b1_t7.ladder.pen_state`를 그대로** 쓴다.
  - 실행 중에 모듈 속성 `c1b1_t7.ladder.FxTrackX`를 C++ 트랙 래퍼로 바꿔 끼운다. `pen_state`가 호출 때 이 이름을 찾기 때문이다(`ladder.py` 41행).
  - 파일은 바꾸지 않는다. 그래서 사다리 사본이라는 새 코드가 생기지 않는다(검토 지적 4).
- 래퍼는 `FxTrackX`를 상속하고, 정수 상태·틱·휩쓴 각만 C++에서 받는다. `q_mpf`, `r()`, `pr()`, `state()`의 r·time 문자열은 상속한 파이썬 코드가 같은 정수에서 계산한다. 따라서 이 값들은 **정확히 같아야** 한다.

**3.2 수 표현:**
- 고정폭 다중 정밀도 부호 있는 정수(64비트 limb 8개 = 512비트, `unsigned __int128`로 곱셈)를 쓴다.
- jet 작업 정밀도는 C1.1과 같은 규칙: P = W + 96비트, W = kick 자릿수에 해당하는 비트(fm·0.30103 + 40자리 → 비트). 가장 큰 fm은 136(레벨 6 확인 트랙)이고, 그때 P는 약 365비트다(검토 지적 10).
- 512비트를 넘으면 실행 전에 거부한다.
- **부동소수점(double·float)을 커널에 쓰지 않는다.** 정적 시험으로 강제한다.

**3.3 초월함수:**
- **exp:** floor(exp(−X/2^P)·2^P)를 구한다.
  - 정수 인자 축소(2의 거듭제곱 + ln2 상수)와 Taylor 급수를 쓰고, 보호 비트는 64 이상이다.
  - ln2 상수는 파이썬 mpmath 200자리에서 만든 정수를 소스에 넣는다. 시험에서 다시 계산해 비교한다.
  - 마지막 비트가 파이썬 `mpf_exp`와 다를 수 있다. 세계 비트에는 영향이 없을 것으로 본다(이유는 아래).
- **sqrt:** 정수 제곱근(floor, 뉴턴)
- **atan(휩쓴 각):** 걸음당 각이 작으므로(약 3e-3 rad 이하) atan 급수로 계산한다. |각| > 0.5 rad이면 **거부**한다(실제로 생기지 않을 것으로 예상, 미확인). 결과는 2^-256 정수로 누적한다.

**3.4 비트 동일의 논증(증명 아님, 검토 지적 2로 고침):**
- 파이썬의 충격량 값 자체의 오차는 jet의 P가 아니라 **kick 작업 정밀도 W**가 정한다. r, −V′/r, 계수(h/6은 이진 분수가 아님), c·x가 모두 W비트로 반올림되기 때문이다. 그래서 격자 단위로 약 2^-130이다.
- 1e-30 안전장치는 약 2^-99.7 격자 단위다.
- 두 계산의 오차가 모두 안전장치 폭의 절반보다 작으면 결론이 나온다. 파이썬이 안전장치를 통과한 값에서는 두 반올림이 **반드시** 같다(확률 논증이 아님).
- 남는 차이는 "C++만 거부"하는 경우뿐이다. 그래서 C++ 쪽 오차 상한을 시험으로 확인한다(6절 시험 8).
- **휩쓴 각:** 파이썬은 걸음마다 60자리 atan2로 더한다. C++는 그 반올림을 흉내 낼 수 없다(mpmath 내부 알고리즘). 그래서 휩쓴 각 누적은 끝자리가 다를 수 있다. 차이는 1e-54 정도까지로 추정된다(걸음 1e6개 기준).
- 휩쓴 각은 사다리의 수락 판단에 들어간다(`es`, `est`). 래퍼가 판단 직전의 휩쓴 각 차이를 계산할 수는 없다. 대신 결과 행에서 **|est_sweep − tol|과 |es − tol|이 1e-40 미만인 경우를 "판단 근접"으로 표시**하고, 그 행은 비트 비교에서 미확정으로 분류한다.
- **실행 전 확인:** T7 행의 6자리 est 문자열 중 1e-9와 같은 것이 없는지 본다.

**3.5 언어 경계:** 수치 실행 계층 4절 규칙(처음에는 바인딩 없이 실행 파일과 텍스트 경계)을 따른다.
- C++ 실행 파일 하나가 트랙 하나다.
- 표준 입력으로 명령을 받는다: `start`, `to_exit`, `to N`, `state`.
- 표준 출력으로 정수 raw, 틱, 걸음 수, 휩쓴 각(2^-256 정수)을 내보낸다.
- 파이썬 래퍼 `FxTrackNative`는 `FxTrackX`와 같은 속성·메서드(qr, pr_, tick, exit_tick, substeps, sweep, r(), pr(), run_to_exit, run_to, state)를 제공한다.

**3.6 빌드:**
- g++ `-O2 -std=c++17`. `-ffast-math`, `-Ofast`, `-march=native`는 금지한다.
- 정수만 쓰므로 결과는 최적화 수준과 무관해야 한다. 시험으로 `-O0`·`-O2` 두 빌드의 결과를 대조한다.
- 원격 PC와 노트북에서 각각 빌드해 두 기계 결과도 대조한다.
- MSVC(이 PC)는 이번 범위가 아니다. 이 PC에서는 물리 계산을 하지 않는다.

## 4. 대안과 고르지 않은 이유

| 대안 | 왜 아닌가(지금) |

## 6. 시험과 판정 (실행 전 고정)

**부품 시험(노트북):**
1. **jet 값:** r = 3 … 30(로그 41점), 작업 정밀도 60·68·77·80자리. \|C++ − mpmath(+60자리)\| ≤ 2^-(W−5)·max(1, \|값\|)이어야 한다(C1 시험과 같은 기준).
2. **exp·sqrt·atan 단위 값:** 각각 mpmath 고정밀과 대조한다. 오차 ≤ 2^-(P−4) 단위.
3. **200틱 트랙 비트 동일:** T7 O:ordinary 시작, 레벨 0·1에서 파이썬 `FxTrackX(LangForceFX2)`와 qr, pr_, tick이 같아야 한다. 휩쓴 각 차이는 ≤ 1e-50이어야 한다.

## 각도 기록 방식 비교 (정보용, 실행 전 기록 2026-10-12)

**두 방식:**
