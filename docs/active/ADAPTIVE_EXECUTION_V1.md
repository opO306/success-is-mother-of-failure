# ADAPTIVE_EXECUTION_V1 — 검증된 CPU/GPU 계산기를 하나의 적응형 실행 서비스로 연결

상태: **결과 기록 (2026-10-08)**. 독립 checker **EVIDENCE OK**(관문·최종 모두, 오류 0), 판정 **ADAPTIVE_V1_READY**.
- 공식 호스트: Vast 54645489 — RTX 4060 Ti 16GB(sm_89) + Threadripper PRO 3995WX(128 스레드, cgroup 할당 30.7 CPU). 봉인한 52763685는 GPU가 다른 사용자에게 대여 중이라 실행 전 정정 2로 바꿨다.
- 증거 수준: **구현 + 시험 + 같은 호스트 독립 재계산 대조**. 형식 증명이 아니고, 다른 컴퓨터의 성능을 뜻하지 않는다.
- 브랜치 `claude/adaptive-execution-v1`(부모 `436e2ff`, 메인 checkout, worktree 없음, push·merge 없음).
- 커밋: protocol `aa64efe` → 코드 봉인 + 정정1 `26442e8` → 정정2(호스트) `e9557db` → 성능 프로필 봉인 `d3d5f03` → 증거·문서.

## 0. 한 줄 결론

**선택기는 "어떻게 계산할지"만 골랐고, 계산 결과는 한 번도 달라지지 않았다.**
- 서비스 156개(요청 8개 × 방식 4개 × 5회 + 사례)의 모든 pass가 checker의 독립 재계산과 끝점까지 같았다.
- 같은 (N, T, p)는 어느 방식(직렬, W6, GPU, 적응형)으로 돌려도 결과가 같았다.

**측정한 요청에서는 적응형이 가장 빠른 고정 방식과 같은 속도를 냈다.**
- 측정한 7개 요청의 합계: 적응형 63.6초. CPU W6 고정 184.6초, CPU 직렬 고정 933.1초.
- 비율 G_best = 0.345(봉인 기준 0.85 이하).

**측정하지 않은 요청(N=14)에서는 봉인 규칙대로 직렬을 골라 W6보다 5배 느렸다.** 정확성은 유지됐다. 비용 정책의 반례로 남긴다(§5).

## 1. 무엇을 했나 (쉬운 말)

비유: 지금까지 공장에 일꾼이 세 종류 있었다.
- 혼자 일하는 장인(CPU 직렬)
- 여섯 명이 나눠 하는 작업반(CPU W6)
- 기계 공장(GPU)

각자 같은 물건을 같은 품질로 만든다는 것은 이전 단계들에서 확인했다. 이번에는 **배차 담당(선택기)**을 두었다.
- 주문(요청)이 오면 배차 담당은 공장 사정(이 컴퓨터의 CPU·GPU)과 지난 실측 기록(성능 프로필)을 보고 누구에게 맡길지 정한다.
- 배차 담당은 **물건의 설계도(물리 법칙, 정밀도 p, 판정 규칙)를 바꿀 수 없다.** 누구에게 맡길지만 정한다.

실제로 한 일:
- 요청마다 시작 정밀도를 과거 경험 저장소(봉인된 V2 묶음, 읽기 전용)에서 고른다. 순서는 정확히 같은 요청의 성공 기록 → 같은 계열의 최대값 → 64.
- 정밀도가 모자라면 기존 P2 규칙이 다음 p를 정한다. 다음 pass는 항상 **원래 초기 상태에서** 다시 시작한다.
- pass마다 선택기가 실행 방법을 고른다. 연결 계층(adapters)이 실행 직전에 **자기 코드로 다시** 지원 조건을 검사한다.
- GPU가 지원하지 않는 p나 N이면 같은 p 그대로 CPU가 한다.

## 2. 시작 전에 해결한 구조 문제 (코드에서 직접 확인)

| 문제 | 실제 코드에서 확인한 것 | 해결 |
|---|---|---|
| A. CPU 선택기의 하드웨어 가정 | `selector_service_v1`은 "논리 6 = 물리 6, SMT 없음, CPU 0–5"만 받는다. N=8 T=100에서 틀린 규칙(W4)도 들어 있다. | 규칙은 재사용하지 않았다. 배치는 실제 허용 CPU, 물리 코어 번호(SMT 형제 제외), cgroup 할당량에서 계산한다. W 선택은 그 호스트에서 실측한 행으로만 한다. |
| B. GPU 장기 실행기 T=1000 전용 | `long_pass`는 모듈 상수 T=1000에 묶여 있다. 100걸음 실행기 `hybrid_trajectory`는 pass 기록을 만들지 않는다. | 동결 코드는 고치지 않았다. 100걸음은 `hybrid_trajectory` + `long.readout`(같은 판독)으로 pass 기록을 만들고, **연결 관문 gate100**(CPU 직렬 기록과 필드 단위 비교)을 통과한 뒤에만 썼다. |
| C. GPU 지원 정밀도와 전역 상태 | 지원 p는 {64,73,78,109,128,161,163,166,192}다. `ExtPV.upload`가 업로드 중에만 전역 목록을 넓힌다. | 그 밖의 p는 GPU 거부 → 같은 p로 CPU. GPU는 **전용 작업 프로세스 하나**가 맡고, 잠금으로 한 번에 한 요청만 받는다. 전역 목록 변경은 그 프로세스 안에서만 일어난다. |
| D. 호스트별 성능 차이 | 4060 Ti와 3090에서 N12 비율이 0.41과 0.80으로 달랐다. | 성능 표는 환경 식별자(env_id)별로만 쓴다. 다른 env_id의 행은 쓰지 않는다. |
| **E. (새로 찾음) GPU 장치 거부가 "정밀도 부족"으로 읽힘** | `long_pass`가 pass 도중 `REFUSED_DEVICE_*`를 만나면 그 이름을 stop으로 넘긴다. `_readout`은 모르는 stop을 `UNDECIDED_AT_PRECISION`으로 바꾼다. 그대로 두면 P2가 장치 문제 때문에 p를 올린다. | 연결 계층이 GPU 상태를 스스로 분류한다(정상 / 영역 정지 / 장치 거부 / 장치 오류 / 정밀도 불일치). 장치 거부·오류는 P2 입력이 아니고, 같은 p를 CPU 직렬로 다시 하며 사건 기록을 남긴다. |

## 5. 반례와 한계 (먼저 볼 것)

1. **R7(N=14, 측정하지 않은 계열): 직렬을 골라 W6보다 4.97배 느렸다.**
   - 봉인 규칙 "자료 없는 계열 → 직렬"을 그대로 따른 결과다. 결과는 정확하다.
   - W6 배치 자체는 이 호스트에서 유효했으므로, "자료 없음 → 유효한 W6" 같은 대안 규칙이 더 쌌을 것이다(추론, 미검증).
   - 규칙은 평가 중 바꾸지 않았다. 다음 단계(V0의 신규 환경·계열 학습)에서 다룰 문제다.
2. **측정한 7개 요청의 이득은 "표본 안" 결과다.** 교정한 계열이 평가 요청의 계열과 같다. 그래서 G_best 0.345는 "측정한 계열에서 잘 골랐다"는 뜻이지, 처음 보는 요청에서도 그렇다는 뜻이 아니다. 처음 보는 요청은 R7 하나였고, 거기서는 손해였다.
3. **더 싼 대안.** 이번 7개 요청에서는 "GPU 지원이면 GPU, 아니면 W6"라는 두 줄짜리 고정 규칙도 같은 결과를 냈을 것이다(표로 확인 가능). 이 규칙은 R7에서도 W6를 골라 적응형보다 나았을 것이다.
   - 적응형 선택기가 그 규칙보다 나은 점은 두 가지다. 하나는 호스트마다 다른 경계(예: 3090의 N12 0.80, 다른 장비의 TIE)를 실측으로 처리하는 구조다. 다른 하나는 미검증 GPU·환경을 거부하는 장치다.
   - 그런데 **이번 호스트에서는 경계 사례가 실제로 나타나지 않았다.** GPU가 모든 GPU 영역 요청에서 2배 이상 빨랐다. 따라서 이 이점은 이번 실험으로 증명되지 않았다.
4. **N=12 경계 처리는 이 호스트에서 시험되지 않았다.** 4060 Ti 호스트는 N12에서도 GPU가 2.2배 빨라 동률 규칙이 쓰일 일이 없었다. 3090 호스트(0.80)에서의 동작은 측정하지 않았다.
5. **100걸음 정지 변환은 gate100에서 시험되지 않았다.** FCC_N 초기 상태는 100걸음 안에서 멈추지 않는다. 정지가 난 pass는 1000걸음(p64, GPU 경로 `long_pass`)뿐이었다.
6. **검증 비용은 따로 쟀다.** 독립 재계산 16개에 CPU 1,158초가 들었고, 가장 큰 것은 N16 T1000 141초다. 서비스 비용에는 넣지 않았다. 실서비스의 모든 요청에 이 재계산을 붙이면 GPU 이득이 사라진다. 이번 결과는 "평가 중 재계산 대조"이지 3층 계약의 `REPLAY_VERIFIED` 등급이 아니다.
7. **env_id 일치 ≠ 정확성.** env_id는 성능 표를 고르는 열쇠일 뿐이다. 같은 구성의 다른 기계는 같은 env_id를 갖지만 성능이 다를 수 있다.
8. **공유 노드 잡음.** 부하 평균은 1.5–37.7(1분, 128스레드)이었다. 그런데도 반복 간 편차는 대부분 1% 안이었다.
9. **CPU 서비스는 pass마다 새 프로세스를 띄우고, GPU 작업 프로세스는 서비스 사이에 재사용한다.** 기존 실행기 구조를 그대로 쓴 것이다. GPU 첫 시작 0.5–0.6초는 표 밖에서 따로 보고했다.

## 7. 쉬운 말로 답하는 14가지

1. **CPU/GPU를 자동으로 선택할 수 있게 되었나?** 예. 이 호스트에서 봉인한 실측 표가 있는 계열에서는 매 pass마다 직렬·W3·W4·W6·GPU 중 가장 빠른 것을 골랐다. 실측 표가 없으면 직렬로 물러선다.
2. **선택 때문에 정확성이 달라진 사례가 있나?** 없다. 서비스 156개, 재계산 16개 (N, T, p)에서 결과가 모두 같았다.
3. **GPU 지원 정밀도는 지켜졌나?** 예. 162는 GPU에 가지 않고 CPU에서 162 그대로 계산됐다. 107(N8)도 CPU로 갔다. 강제로 GPU에 보낸 3건은 연결 계층과 GPU 작업 프로세스가 각각 거부했다. 정밀도 위장은 0건이다.
4. **CPU 선택기의 하드웨어 제한은 어떻게 처리했나?** "6코어 전용" 규칙을 버렸다. 실제 허용 CPU, 물리 코어(SMT 형제 제외), cgroup 할당량으로 배치를 만들고, 그 배치로 실측한 행만 쓴다. 실행 직전 다시 검사하고, 실행 후 기록된 affinity가 계획과 같은지도 checker가 본다.
5. **고정 실행보다 실제로 빨랐나?** 측정한 7개 요청 합계 기준 W6 고정보다 2.9배(0.345), 직렬 고정보다 14.7배 빨랐다. GPU 고정과는 같았다. 측정하지 않은 R7에서는 W6보다 5배 느렸다.
6. **CPU 사용량은 얼마나 달라졌나?** GPU를 고른 요청에서 CPU 시간이 직렬·W6의 약 1/11–1/23로 줄었다. CPU_MIN 규칙(직렬)은 이 결과로 반박됐지만, 이번에는 바꾸지 않았다.
7. **N=12 같은 경계 요청은?** 이 호스트에서는 경계가 아니었다(GPU 6.95초 대 W6 15.5초). 5% 동률 규칙은 시험으로만 확인했다. 실제 경계 호스트(3090)에서는 측정하지 않았다.
8. **모르는 환경에서는?**
   - 성능 표 없음 → 직렬.
   - 검증 안 된 GPU → CPU.
   - 검증 안 된 mpmath → 계산하지 않고 거부.
   - 실제 데스크톱(표 없음)에서는 8개 요청 모두 직렬을 골랐다.
9. **P2 재시도 중 CPU↔GPU 전환은?** 공식 실행에서는 모든 재시도 p(64, 73, 161, 78, 166)가 GPU 지원이라 전환이 없었다. 전환 경로는 시험에서 확인했다: 장치 거부·오류 → 같은 p를 CPU로, F3. 서비스 안 p별 선택은 R6(162 → CPU)에서 실제로 쓰였다.
10. **경험 저장소에 평가 결과가 섞였나?** 아니다. 저장소 해시가 봉인값(`ec19eda9…`) 그대로다. 평가 기록 225개는 `candidates/`에 UNVERIFIED로만 저장했고, 어떤 정책도 읽지 않는다.
11. **선택기 비용은?** pass당 약 0.14 ms(최대 0.29 ms)다. GPU 작업 프로세스 시작은 따로 약 0.5–0.6초다.
12. **다른 컴퓨터에서 바로 쓸 수 있나?** 정확성 쪽은 검증된 GPU 아키텍처(sm_86, sm_89)와 mpmath 1.3.0(python)이면 같은 규칙으로 안전하다. 성능 쪽은 그 컴퓨터의 성능 표가 없으므로 직렬로 물러선다. 쓸모 있게 쓰려면 그 컴퓨터에서 교정과 봉인이 필요하다.
13. **신규 환경 학습 모드 V0를 시작할 준비가 됐나?** 구조는 준비됐다: 환경 기록, env_id, 교정 단계, 봉인, 선택, checker. 다만 V0에서 먼저 정할 것이 있다.
    - 교정 계열을 무엇으로 할지(R7 같은 빈칸을 어떻게 줄일지)
    - 새 GPU 아키텍처의 수치 호환성 검사(관문 P류)
    - "자료 없음 → 직렬" 규칙을 유지할지
14. **작은 세계 본체에 넣으려면 무엇이 더 필요한가?**
    - 이 서비스는 FCC_N 시험 계열(rw:R1+R2, T=100/1000)만 다룬다. 실제 세계 실행기의 상태 형식, 사건 기록, 3층 계약(CONFIRMED·REPLAY_VERIFIED)과의 연결은 없다.
    - 더 긴 궤적은 증거가 없다.
    - 실서비스 재검증 비용을 어떻게 낼지(표본 감사 vs 전수 재계산)는 설계자 결정이 필요하다.
