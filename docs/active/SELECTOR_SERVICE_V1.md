## 0. 한 줄 결론

서비스 흐름(요청 → Selector → 실행 계획 → 기존 실행기 → P2 → 재시도 → DECIDED)은 6개 새 요청 × 3가지 방식 × 3회 = 54번 모두
정확히 끝났고, 모든 pass가 직렬 결과와 비트 단위로 같았다.
- **시간 목표(WALL_MIN) Selector**는 직렬보다 늘 빨랐다(1.13–3.75배).
- **규칙은 한 곳에서 틀렸다**: N=8(100걸음)에서 규칙은 W4를 골랐지만 W6가 3.8% 빨랐다. 이것은 p 때문이 아니라 p=128 자료에서도
  있던 경계 오류다(아래 6번).
- **정밀도 p가 64→163으로 바뀌어도 가장 빠른 작업자 수는 바뀌지 않았다.**
- **가장 큰 비용은 작업자 선택이 아니라 정밀도 재시도였다**: p=64 첫 시도가 거의 항상 실패해서 전체 비용의 46–66%를 차지했다.

## 1. 무엇을 만들었나 (쉬운 말)

비유: 주문(요청)이 들어오면 ① 접수 직원(Selector)이 "몇 명이 일할지·어느 책상에서"만 정하고, ② 공장(기존 실행기)이 처음부터 끝까지
만들고, ③ 검사원(P2)이 "칸이 확정됐는지" 보고, 확정 안 됐으면 더 정밀한 공구(더 큰 p)로 처음부터 다시 만들게 한다.
접수 직원은 결과를 미리 볼 수 없다.

실제 의미:
- `ServiceRequest{N, T, goal}` → P2가 p를 정함(첫 p=64, 이후 기존 `p2_next`, 1024 상한) → `Selector V1(N, T, p, goal, topology)` →
  `ExecutionPlan` → 기존 W5_PLACEMENT_V1 실행기가 새 프로세스로 한 pass를 처음부터 계산 → 결과 → P2 → …
- Selector 입력은 N, T, p, goal, topology 다섯 개뿐이다. 결과·최소 p·검증 결과·shadow 결과는 입력이 될 수 없다.
- CPU_MIN = 항상 직렬. WALL_MIN = 고정 규칙(T=100: N≤4 직렬, 5≤N<12 W4, N≥12 W6 / T=1000: N=3 W3, N≥4 W6).
  T가 100·1000이 아니면 `UNSUPPORTED_SELECTOR_DOMAIN`. GPU는 이름만 있고 실행하면 거부.
- 평가 요청은 규칙을 만들 때 쓰지 않은 N: T=100 N=5,8,16,32 / T=1000 N=5,8.
- 비교: SEL_WALL(Selector, WALL_MIN), SEL_CPU(Selector, CPU_MIN = 항상 직렬 기준선 B와 같은 계획 — checker가 매 pass 직렬인지 확인),
  FIXED_W6(항상 W6, 기준선 C). 그리고 시도된 모든 (N, T, p)에서 W3·W4도 사후 shadow로 측정했다(Selector에는 보이지 않음).

## 4. 10개 질문

1. **6개 새 요청을 모두 정확하게 끝냈나**: 예. 54개 서비스 실행 전부 DECIDED, 195개 pass 전부 직렬과 비트 동일, 독립 checker EVIDENCE OK.
2. **CPU_MIN은 실제로 직렬이 가장 쌌나**: 예. 6개 요청 모두에서, 그리고 모든 시도한 p에서 직렬이 W3·W4·W6보다 CPU가 적었다.
3. **WALL_MIN Selector는 항상 직렬보다 빨랐나**: 예. 6개 요청 × 3회 = 18번 모두. 중앙값 1.13배(N=5, T=100) ~ 3.75배(N=32).
4. **항상 W6보다 나았나**: 시간으로는 아니다. N≥16과 T=1000에서는 Selector가 W6를 골라 같은 계획이다(차이 0–2%, 흔들림 안).
   - N=5(T=100): W4를 골라 시간은 같고(1.01, 회별 0.90–1.11로 흔들림) **CPU는 24% 적었다**.
   - N=8(T=100): W4를 골라 **3회 모두 W6보다 3–9% 느렸고**(중앙값 4.7%), CPU는 14% 적었다(시간×CPU는 10% 나음).
5. **정밀도가 변하면 최적 작업자 수도 변했나**: 아니다. 시도된 p 범위(64–163) 안에서 모든 요청의 가장 빠른 실행법이 p마다 같았다.
   p가 64에서 106–163으로 커질 때 한 pass 비용은 2–9%만 늘었다.
6. **p=128에서 만든 경계가 다른 p에서도 유지됐나**: 경계가 p 때문에 깨진 곳은 없었다. 다만 **규칙 자체가 N=8에서 틀렸다**.
   p=64에서도(W6가 6.1% 빠름), p=107에서도(W4가 W6와 동률 범위 끝) W6가 가장 빨랐다. 원래 p=128 자료에서도 MULTIATOM의 E1 N=8은 W6가
   최소였다. 그래서 "5 ≤ N < 12 → W4" 구간의 위쪽 경계가 처음부터 너무 넓게 잡혔던 것으로 보인다(추론). 규칙은 이번 실험 안에서 고치지 않았다.
7. **Selector 선택과 사후 최적의 차이**: 시도한 모든 pass의 시간 합 기준으로 N=8(T=100)만 3.8% 손해, 나머지 5개 요청은 0%.
8. **P2가 몇 번 재시도했나**: T=100 4개 요청과 N=5(T=1000)는 2번(64 → 106–145), N=8(T=1000)은 3번(64 → 152 → 163). 상한(1024)에 간 요청은 없다.
9. **비용 구성**:
   - **정밀도 재시도(실패한 pass)**: 2번 시도 요청은 전체 시간·CPU의 46–55%, 3번 시도 요청은 65–66%였다. p=64가 거의 항상 실패하고,
     실패한 pass도 성공한 pass와 거의 같은 비용이 들기 때문이다(p에 따른 비용 차이 2–9%).
   - **병렬 overhead**(같은 p의 직렬 CPU보다 더 쓴 CPU, 병렬 CPU 대비): Selector 기준 N=5 47% → N=8 32% → N=16 27% → N=32 23%,
     T=1000 26–30%. 시작 비용이 pass wall에서 차지하는 몫: N=5 65% → N=32 5%.
10. **다음 Selector에 p를 선택 변수로 넣을 근거가 생겼나**: **작업자 수 선택에 p를 넣을 근거는 없다**(64–163에서 최적이 바뀌지 않음).
    대신 **시작 p 선택(정밀도 정책)이 작업자 선택보다 훨씬 큰 비용을 좌우한다**는 근거가 생겼다. 재시도가 비용의 약 절반이고,
    규칙 오류(N=8)의 손해는 3.8%였다. 시작 p를 바꾸는 것은 P3 재학습 같은 정밀도 정책 문제라 이번 범위 밖이며, 별도 실험 대상이다.

## 5. 한계·공개

- 노트북 1대(SMT 없음). 다른 기기에서는 규칙 자체가 다를 수 있다(Selector는 다른 topology를 거부하도록 만들었다).
- 시도된 p는 64–163뿐이다. p≥200에서 최적 작업자 수가 바뀌는지는 측정되지 않았다(UNRESOLVED).
- 반복 3회. N=5(T=100)의 Selector ÷ W6 시간은 회별 0.90–1.11로 흔들려서 승자를 말할 수 없다.
- 사전 공개(정정1): checker 결함 주입 시험이 데스크톱에서 실제 N=5, T=100 요청을 돌린다(결과는 보지 않음).
  N=3 dry run에서 분석이 깨끗한 반복이 없는 요청에서 멈추는 결함을 찾아 봉인 전에 고쳤다.
- 실행 전 추정(CPU 약 7,300초, 약 50분) 대비 실제는 3,838초, 약 27분이었다. 재시도가 2–3번으로 추정보다 적었다.
- 기존 실험 evidence는 바뀌지 않았다.
