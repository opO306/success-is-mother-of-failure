# GPU_SHORT_TRAJECTORY_V1 — GPU 힘 + CPU KDK로 10걸음·100걸음을 연속으로 가도 CPU E2 궤적과 매 걸음 끝점까지 같은가

상태: **결과 기록 (2026-10-07)**. checker **EVIDENCE OK**(S10, S100 둘 다), 판정 **SHORT_TRAJ_PROMISING**.
- 공식 측정: Vast 52763629, Ryzen 9 5950X + RTX 3090. protocol이 처음부터 지정한 호스트라 호스트 변경 정정은 없다.
- 데스크톱에서 같은 증거를 독립 재검사·재분석했다(결과는 §7).
- 데스크톱 RTX 4060 교차 확인: 49개 궤적 기록의 매 걸음 digest, 체크포인트, 정지 위치가 3090과 모두 같았다.

증거 수준 = 실행 + 독립 checker. 봉인된 궤적 8개와 정지 시험 8개에서 **최대 100걸음**의 비트 일치다. 증명이 아니고, **100걸음 정확성이 1000걸음이나 장기 궤적 정확성을 뜻하지 않는다.**
분업: GPU는 힘 F만 계산한다. GPU_ONE_STEP_V1의 GpuForceExecutor와 GPU_PAIR_VECTOR_V1 커널을 수정 없이 쓴다. 운동량·위치 갱신(kick, drift)은 CPU가 mpmath로 한다(one_step.kick / drift를 수정 없이 사용).
브랜치 `claude/gpu-short-trajectory-v1`(부모 `5511d9f`, 메인 checkout, worktree 없음, push 없음).
커밋: protocol `fb9ceb4` → 궤적 묶음 봉인 `f26ec88` → 코드 봉인 + 정정1 `111f668` → 증거·문서.

## 0. 한 줄 결론

**GPU 혼합 경로로 돌린 정상 궤적 40개(S10 32개 + S100 8개)가 매 걸음 다섯 검사 지점 모두에서 CPU E2 궤적과 끝점까지 같았다.**
- 다섯 검사 지점: F_s → 첫 kick(p_half) → drift(q_{s+1}) → 새 힘 F_{s+1} → 둘째 kick(p_{s+1}).
- 비교한 걸음 1,162개 중 불일치 0이다. 체크포인트 248개의 전체 끝점도 같았다.
- 최종 측정(K.decide, endpoints_key)도 같았다.

**여러 걸음 뒤에 나는 영역 정지 8개가 CPU와 같은 걸음, 같은 쌍, 같은 종류에서 멈췄다.** 멈춘 뒤에는 아무것도 계산하지 않았다.
- 대표 사례: N=12에서 **state 7, pair 30(원자 3–4), VIOLATED**.
- N=3에서는 state 7에서 VIOLATED와 UNPROVEN, state 0에서 VIOLATED로 멈췄다.

**속도(100걸음 전체, warm)**: 측정한 6개 조건 중 5개에서 GPU가 이겼고, N=12(p=163)는 **동률(TIE)**이었다.

## 1. 무엇을 했나 (쉬운 말)

비유: 지난 단계에서 공장(GPU)이 만든 힘으로 장인(CPU)이 원자를 **한 걸음** 움직였을 때, 장인 혼자 한 것과 같은지 확인했다. 이번에는 그 일을 **10걸음, 100걸음 이어서** 시켰다.
- 앞 걸음 결과가 다음 걸음의 출발점이 된다. 그래서 어딘가에서 끝자리 하나만 달라도 그 차이가 뒤로 퍼진다.
- 그런 퍼짐이 정말 없는지 매 걸음 확인했다.

실제 의미(`stream.run`과 같은 순서):

```
F_0 = forces(q_0)                    (GPU)
for s = 0 .. T-1:
    p_half  = p_s + F_s              (CPU)
    q_{s+1} = q_s + p_half * CDT     (CPU)
    F_{s+1} = forces(q_{s+1})        (GPU)
    p_{s+1} = p_half + F_{s+1}       (CPU)
```

- **힘 재사용**: 앞 걸음 끝에서 만든 F_{s+1}을 다음 걸음 시작의 F로 그대로 쓴다. T걸음이면 힘 계산은 정확히 T+1번이다.
  - checker는 이 횟수를 궤적마다 확인했다. 결과는 40/40이 101번 또는 11번, 정지 궤적은 정지 state+1번이다.
- **실행기 유지**: 궤적 하나 동안 CUDA 컨텍스트, 모델, 버퍼를 한 번만 준비한다.
  - 궤적 안의 모델 업로드 0번, 버퍼 할당 0번을 checker가 매 궤적 확인했다.
- **digest**: 매 걸음 다섯 벡터를 정해진 순서로 글자로 적고 sha256을 낸다.
  - 순서: 원자 → x/y/z → 아래·위 끝점. 끝점은 부호.가수.지수.비트수로 적는다.
  - 걸음마다 F_s, p_half, q1, F1, p1, 상태(q,p), 힘의 digest를 기록한다.
  - 정해진 걸음(0, 1, 2, 5, 10, 20, 50, 100)에서는 전체 끝점도 저장한다.
  - CPU와 처음 달라지는 걸음이 생기면 그 걸음의 다섯 벡터 전체를 저장하게 해 두었다(dump). 공식 실행에서는 한 번도 생기지 않았다.

**궤적 묶음(코드보다 먼저 봉인, `2bca7c26…`)**: `stream.run` 소스에 관찰 줄 두 개를 넣은 복제본을 실행 중에 만들어 CPU 기준 궤적을 기록했다. 파일은 바꾸지 않았다.
- 관찰 위치: drift 뒤 한 줄, 둘째 kick 뒤 한 줄.

| 궤적 | 출발 | 검증된 기준과의 대조 |
|---|---|---|
| N12, N16 (p=163) | FCC 초기 상태(s0)와 500걸음 뒤(s500) | 복제본을 1000걸음까지 돌려 V2 Vast 기준과 같음 |
| N40, N64 (p=109) | FCC 초기 상태 | 100걸음 끝이 V2 기준과 같음 |
| N128 (p=109), N64 (p=163) | FCC 초기 상태 | 검증된 기준이 원래 없다. 복제본만 있고, checker가 직접 다시 계산했다 |

**여러 걸음 정지 시험(T=10, p=109·163 각각)**:
- P3_F0_VIOLATED: 원자 하나가 처음부터 너무 가깝다 → state 0에서 정지.
- P3_MULTI_VIOLATED: 원자 하나에 운동량 1050을 줬다 → state 7, pair 0에서 정지.
- P3_MULTI_UNPROVEN: 위치 하나가 구간 [6, 6.5]이고 운동량 650 → state 7에서 UNPROVEN으로 정지.
- N12_MULTI_PAIR: FCC N=12에서 원자 4를 원자 3 쪽으로 밀었다(운동량 910) → state 7, **pair 30**에서 VIOLATED로 정지.

운동량 값은 protocol에 미리 적은 규칙으로 찾았다. 규칙은 "0부터 올리며 state 4–7에서 처음 멈추는 값"이다.

## 5. 쉬운 말 정리

1. **100걸음을 이어 가도 CPU와 똑같았나?** 예.
   - 측정한 8개 궤적 × 최대 100걸음에서 매 걸음 다섯 지점이 끝자리까지 같았다.
   - 여러 걸음 뒤에 나는 정지도 같은 걸음, 같은 쌍에서 났다.
   - 오차가 쌓이거나 갈라지는 걸음은 이 범위에서 한 번도 나오지 않았다.
2. **한 걸음 결과와 100걸음 결과가 같은 그림인가?** 대체로 같다.
   - GPU 걸음당 7.3–12.2 ms는 한 걸음 측정(7.7–12.9 ms)과 비슷하다.
   - W6 걸음당 시간은 한 걸음 측정과 대체로 비슷하다(N=40 84.5 → 85.8 ms, N=128 883.5 → 892 ms).
   - 다만 N=64 p109는 216.6 → 231.7 ms로 약 7% 길다. 원인은 확인하지 않았다.
   - 다만 **N=12는 한 걸음에서 근소한 GPU 우세(0.956)였다가 100걸음에서는 동률(1.006)**이 됐다. 이 크기에서는 둘이 사실상 같다.
3. **병목은?** 여전히 GPU 쌍·G·J 커널의 바닥 지연(걸음당 5.0–7.5 ms)이다.
   - p=163이 p=109보다 느리다. 그래서 N=40(p=109)이 N=12(p=163)보다 빠르다.
   - N이 커지면 합산 커널(N=128에서 2.35 ms)과 파이썬 변환·kick·drift(N=128에서 합 약 4 ms)가 늘어난다.

## 6. 한계·공개

- **최대 100걸음**이다. 1000걸음, 장시간 누적, 장기 정지, 정밀도 재시도와의 결합은 다음 단계(GPU_LONG_TRAJECTORY_V1)의 질문이다.
- **증명이 아니다.** 봉인된 궤적 8개 + 정지 시험 8개에서의 비트 일치다.
- **N128(p=109)과 N64(p=163)에는 검증된 외부 기준이 없다.** 기준은 기존 `stream.run`의 복제본과 독립 checker 두 가지다. 둘은 서로 같았다.
- **digest 비교의 의미**:
  - 매 걸음 비교는 sha256 digest로 했다. 서로 다른 끝점이 같은 digest를 낼 가능성은 무시할 수 있는 수준이다(추론, 암호학적 가정).
  - 체크포인트 걸음에서는 끝점 자체를 비교했다.
  - checker는 기록된 끝점에서 digest를 다시 계산해 기록값과 맞는지도 확인했다.
- **결함 2(F 재계산)는 값으로 잡을 수 없다.** 결정론이라 같은 값이 나오기 때문이다. 힘 계산 횟수로만 잡는다(사전 봉인).
- **정지 시험의 구간 위치 처리**: 묶음 복제본은 구간 위치([6, 6.5])를 그대로 통과시키도록 입력 리프트만 바꿨다(LI.c가 유리수만 받기 때문). 유리수 입력은 `stream.run`과 같게 리프트했다(정정1).
- **성능 측정에서 관찰한 것(원인은 추론)**:
  - GPU 회별 값은 W6 직후에 잰 회(827–831 대 890–908, N=64)가 더 느리다. 첫 힘도 34–57 ms로 정상 걸음보다 길다.
    - W6가 20–90초 도는 동안 GPU가 쉬면서 클럭이 내려갔을 가능성이 있다. 확인하지 않았다.
    - 이 효과는 warm 수치에 포함돼 있고, 분류를 바꾸지 않는다.
  - W6 cold의 궤적 부분(N=64 p109에서 약 22.2–22.5초)이 warm(23.1–23.3초)보다 약 3% 빨랐다.
    - 새 프로세스와 오래 돈 campaign 프로세스의 차이(메모리 상태 등)일 수 있다. 원인은 확인하지 않았다.
    - 이 때문에 N=64 p109에서 W6 cold 합계(22.9초)가 warm(23.2초)보다 짧다. 분류에는 영향이 없다(GPU 비율 0.04 수준).
- block 32는 이전 관측을 근거로 쓴 기본값이다. 보편 법칙이 아니며 이번에 다시 학습하지 않았다.
- Linux에서는 E2 W6 작업자의 Windows 전용 CPU 측정 때문에 V2 Linux 측정 장치를 실행 스크립트에서 켰다(이전 단계와 같음). W6 시간은 메인의 perf_counter로 쟀다.
- 운영 사항:
  - 데스크톱 성능 dry-run 첫 시도가 멈췄다. 원인은 제 임시 스크립트에 `__main__` 보호가 없어 Windows spawn 작업자가 스크립트를 다시 실행한 것이다. 제 프로세스만 종료하고 고쳐 다시 돌렸다(정정1 기록).
  - 공식 실행과는 무관하다.
- Vast 서버는 증거를 받은 즉시 정지했다(exited 확인). 공식 job은 약 30분이었다(시험 → S10 → 관문 → S100 → 관문 → 성능).
- **LOCAL FULL은 생략했다.** 새 실험 파일만 추가했고, 기존 실행 코드·동결 계약·이전 GPU 파일은 바꾸지 않았다. 관련 시험 20개(데스크톱 + Vast Linux)로 대신했다.
- 기존 evidence와 이전 단계 코드는 수정하지 않았다.
