# ADAPTIVE_EXPERIENCE_TABLET_AND_CPU_ROUTE_V0
## 반장의 경험 탭 및 CPU별 실행 경로 설계 구현 계획서

**기준 Git:** `codex/adaptive-execution-real-learning-pilot-a-resume-v1 @ 2fa56010`

**작업 목표:** 반장이 기존 경험을 휴대하면서 현재 CPU에 맞는 계산 경로를 구성하고, 검증된 경험과 미확인 성능을 구별하도록 만든다.

**이번 단계의 범위:** 경험 탭, CPU 실행 경로 후보 생성, 이전 경험의 신뢰 범위 판정, 학습 비용 판단, 제한 오프라인 검증.

**이번 단계에서 금지:** 새로운 물리 알고리즘 작성, 계산기 본체 수정, GPU 확대, 유료 실측 자동 실행, 운영 서비스 연결.

---

## 1. 무엇을 만들려는가?

반장에게 휴대용 **디지털 경험 탭**을 제공한다.

탭은 여러 컴퓨터에서 얻은 계산 경험을 보관하되, 경험마다 다음 정보를 함께 저장한다.

- 어떤 문제를 계산했는가?
- 어떤 CPU와 실행 환경에서 계산했는가?
- 어떤 계산 경로를 사용했는가?
- 실행시간과 CPU 사용시간은 얼마였는가?
- 계산 결과는 어떤 범위까지 검증됐는가?
- 검사관과 관리자의 승인을 받았는가?
- 다른 컴퓨터에서도 사용할 수 있는 지식인가, 참고만 가능한 경험인가?

반장은 새로운 CPU를 만나면 탭에서 유사한 경험을 검색한다.

하지만 과거에 W6가 빨랐다는 이유만으로 새 CPU에서도 W6를 실행하지 않는다.

**기존 경로 중 현재 CPU에서 가능한 것을 구성하고, 새로운 환경에서 필요한 증거를 얻은 뒤 승인한다.**

### 핵심 비유

경험 탭은 완성된 도로를 통째로 옮기는 장치가 아니다.

**어떤 지형에서 어떤 도로를 만들었고 얼마나 효과적이었는지 기록한 설계 자료 저장소**다.

새 CPU의 지형이 다르면 설계 자료를 참고하되, 실제 길은 그 CPU에 맞게 구성해야 한다.

## 2. 현재 구현된 기능부터 재사용

현재 코드에 이미 존재하는 기능을 재구현하지 않는다.

| 기존 기능 | 현재 역할 |
|---|---|
| `environment.py` | CPU 모델, 사용 가능한 CPU, 물리 코어, 실행 제한 등 수집 |
| `selector.py` | SERIAL, W3, W4, W6 후보 배치 구성 |
| `adapters.py` | 배치가 실제 환경과 정확성 계약을 충족하는지 재검사 |
| `ExecutionPlan` | 계산 방법과 CPU 배치를 실행기에 전달 |
| 기존 경험 원장 | 실행 경험 및 증거 보존 |
| 기존 검사관 | 결과·비용·증거 검증 |
| 기존 관리자 | 승인·활성화·복귀 |
| 기존 V2 증거 처리 | 원본 해시, 내용 지문, 저장·재판독 |

새 모듈은 이 기능들 위에서 작동하는 얇은 계층이어야 한다.

**기존 계산기와 선택기를 복제하지 않는다.**

### 현재 기준 실측

프랑스 CPU의 N14/T1000/p163 실측 A에서는 다음을 확인했다.

- 직렬 5회 중앙값: 약 63.514초
- W6 5회 중앙값: 약 13.509초
- 실제 학습 후 요청: 약 79.0% 실행시간 감소
- 전체 교육비 회수: 미완료
- 실제 학습 순환: 검증 완료

이 값은 해당 세션의 증거다. 다른 CPU의 성능을 보장하는 값으로 사용하지 않는다.

## 3. 구현 A: 경험 탭 만들기

새 연구 전용 모듈을 제안한다.

`experiments/adaptive_experience_tablet_v0/`

가급적 다음 기능만 분리한다.

- `catalog.py`: 경험 목록과 검색
- `host.py`: 현재 CPU 환경과 과거 환경 비교
- `routes.py`: 실행 가능한 CPU 경로 후보 생성
- `policy.py`: 신뢰 범위와 학습 가치 판정
- `offline.py`: 제한 시험 및 관문
- `protocol.json`: 변경 전 봉인된 정책

기존 경험 원장과 관리자 권한을 중복 구현하지 않는다.

### A-1. 경험 저장 방식

탭은 두 계층으로 구성한다.

**빠른 색인**

문제 조건과 CPU 환경, 검증 수준, 기록 위치를 담은 작은 목록이다.

반장은 평소 이 색인만 검색한다.

**원본 증거 보관함**

실제 계산 결과, 측정값, 검사관 영수증, 서명 및 원본 해시를 보존한다.

원본은 변경 불가능하게 유지하고, 색인에서 원본을 참조한다.

첫 버전에서는 기존 JSON/원장을 활용한다. 검색량이 커질 때만 SQLite 같은 별도 색인을 검토한다. 색인은 언제든 원본에서 다시 생성할 수 있어야 하며 승인 권한은 갖지 않는다.

### A-2. 경험 기록에 필요한 정보

기록마다 다음 정보를 포함한다.

**문제 정보**

N, T, 시작 정밀도, 실제 사용 정밀도, 목표 WALL_MIN/CPU_MIN, 물리·수치 계약 및 소스 버전.

**CPU 정보**

CPU 모델, 허용 CPU 목록, 물리 코어 배치, SMT, CPU quota, 운영체제, Python/mpmath 환경.

**실행 경로**

SERIAL/W3/W4/W6, 실제 작업자 CPU 배치, placement ID.

**실측 정보**

전체 요청 wall, 누적 CPU 시간, 측정 횟수, 반복 간 변동, 기록된 부하.

**증거 정보**

원본 SHA-256, 세션 식별자, 검사관 영수증, 관리자 승인, 검증 범위, 복귀 이력.

현재 환경 수집 코드가 제공하지 않는 캐시 크기·NUMA·CPU 명령어 지원 등의 정보는 `UNKNOWN`으로 둔다.

필요하다면 별도 읽기 전용 환경 설명 필드를 추가하되, 기존 `env_id`의 의미를 임의로 변경하지 않는다.

### A-3. 보안

탭에 검사관이나 관리자의 개인 서명키를 저장하지 않는다.

탭은 증거를 찾아 보여주는 역할만 한다.

공식 지식 승인 권한은 기존 관리자에게 유지한다.

## 4. 구현 B: CPU마다 가능한 길 구성

**이번 V0에서 가장 중요한 부분이다.**

현재 CPU의 실제 구조를 읽고, 이미 존재하는 계산 경로 가운데 실행 가능한 후보를 만든다.

기존 `selector.placements()`와 `ExecutionPlan`, `adapters.validate_plan()`을 재사용한다.

### B-1. 후보 생성 예시

현재 구현의 물리 코어·CPU quota 조건을 기준으로 한다.

| 사용 가능한 서로 다른 물리 코어 | 구성 가능한 기존 경로의 예 |
|---|---|
| 1~2개 | SERIAL |
| 4개 | SERIAL, W3 |
| 5개 | SERIAL, W3, W4 |
| 6개 이상 | SERIAL, W3, W4, W6 |

이 표는 설명용이며, 실제 자격은 affinity, CPU quota, 코어 식별 및 기존 검증 규칙을 모두 통과해야 한다.

특히 현재 W6 배치는 주 제어 CPU와 여섯 번째 작업자가 CPU 하나를 공유한다. 이를 임의로 7개의 독립 코어가 필요한 구조로 바꾸거나, 반대로 5개 코어면 충분하다고 처리하지 않는다.

### B-2. 반드시 지킬 조건

- OS가 허용하지 않은 CPU에는 작업자를 배치하지 않는다.
- 서로 다른 논리 CPU가 실제로 같은 물리 코어인지 검사한다.
- cgroup CPU quota를 무시하지 않는다.
- 코어 식별이 불명확하면 낙관적으로 병렬 배치를 허용하지 않는다.
- 실제 실행 전 기존 어댑터가 배치를 다시 검사한다.
- 실행한 배치와 기록된 배치가 일치해야 한다.
- 계산 정밀도 p와 P2 정책은 변경하지 않는다.

CPU 코어 수가 많다고 무조건 W6를 선택하지 않는다.

**후보 생성과 최적 경로 판정은 별개의 작업이다.**

### B-3. 처음에는 기존 경로만 사용

V0에서는 다음을 새로 작성하지 않는다.

- 새로운 SIMD 수치 계산기
- 자동 생성된 CPU 기계어
- 캐시 블로킹 계산식
- 새로운 힘 계산 알고리즘
- 임의의 작업 분할 수식

이런 방법은 향후 연구할 수 있지만 정확한 구간 계산과 계산 결과 보존을 별도로 증명해야 한다.

이번에는 **이미 존재하는 길을 현재 CPU에 맞게 배치하는 능력**부터 검증한다.

또한 현재 V1 서비스의 고정 실행 전략은 주로 SERIAL/W6/GPU 경로로 연결돼 있다. `selector.py`에서 W3/W4 배치를 생성할 수 있다고 해서 전체 실제 학습 경로까지 검증됐다고 가정하지 않는다.

W3/W4의 실제 서비스 연결은 별도 계약·시험·승인을 거친 뒤 진행한다.

## 5. 구현 C: 새로운 CPU에서 과거 경험 판정

경험 탭은 과거 정보를 찾은 뒤 다음 상태로 분류한다.

| 상태 | 의미 |
|---|---|
| `CURRENT_SESSION_VERIFIED` | 현재 세션에서 검증·승인된 성능 |
| `TRANSFER_HINT_ONLY` | 다른 환경의 유용한 참고 경험 |
| `NEEDS_CALIBRATION` | 가능한 경로이지만 현재 환경에서 비용 미검증 |
| `INCOMPATIBLE` | 환경 또는 실행 조건이 맞지 않음 |
| `REFUSED` | 증거·서명·정확성 조건 위반 |

이 상태는 새로운 연구용 분류다. 기존 관리자의 `VERIFIED`를 대체하거나 자동 발급하지 않는다.

**가장 중요한 규칙:**

다른 CPU의 `VERIFIED` 성능 프로필을 현재 세션의 `VERIFIED`로 자동 변경하지 않는다.

동일 모델 CPU라도 운영체제, 할당된 코어, CPU quota, 부하, 실행 바이너리 등이 다를 수 있다.

과거 경험은 새로운 CPU에서 어떤 후보부터 살펴볼지 안내할 수 있지만, 검사관이 새로운 환경의 성능을 확인한 것으로 간주하면 안 된다.

### 반장이 판단하는 예

과거 프랑스 CPU에서 W6가 직렬보다 빠름.

새 CPU에서도 W6 배치가 가능함.

→ `TRANSFER_HINT_ONLY`

새 CPU의 W6 배치가 불가능함.

→ `INCOMPATIBLE`

새 CPU에서 관련 비용을 새로 검증하고 관리자가 승인함.

→ 해당 새 세션에서만 `CURRENT_SESSION_VERIFIED`

## 6. 구현 D: 공부할 가치 판단

반장이 매번 모든 경로를 실제 계산해 보면 교육비가 지나치게 커진다.

그래서 과거 경험으로 **무엇을 확인할 가치가 있는지 제안**하게 하되, 실제 유료 실험 허가는 별도로 받는다.

필요한 정보는 다음과 같다.

- 해당 문제의 예상 반복 사용 횟수
- 기존 검증 경로의 실행비용
- 신규 후보 측정비용
- 독립 재현·검사관 비용
- 현재 사용 가능한 시간·예산
- 예상 성능 이익의 불확실성

조건이 불충분하면 `DEFER_INFORMATION_NEEDED` 또는 `DEFER_COST_OR_RISK`로 보류한다.

정보 부족으로 안전한 직렬을 선택한 반장에게 오류 판정을 내리지 않는다.

예상 이익이 크다는 이유만으로 자동 유료 계산을 실행하지 않는다.

### 적은 횟수의 시험에 관한 주의

과거 경험을 이용해 비교 후보 수를 줄이는 것은 검토할 수 있다.

하지만 기존 승인된 실측 반복 기준을 임의로 5회에서 1회로 낮추지 않는다.

짧은 계산 구간에서 얻은 속도도 N14/T1000 전체 계산의 성능으로 그대로 인정하지 않는다.

측정 횟수를 줄이려면 별도 검증된 승격 규약이 필요하다.

## 7. 구현 E: 가벼운 구조 유지

반장이 계산할 때마다 수천 개의 원본을 전부 읽거나 전체 해시를 재계산하면 안 된다.

기본 경로는 다음과 같이 구성한다.

1. 현재 요청에 해당하는 작은 색인을 검색한다.
2. 관련 후보만 불러온다.
3. 필요한 서명과 원본 결합 조건을 검사한다.
4. 기존 배치 기능으로 현재 가능한 경로를 구성한다.
5. 검증된 현 세션 성능이 없다면 안전한 기존 정책을 유지한다.

대량 원본 감사와 새 경험 등록은 별도 경로에서 처리한다.

**이번 V0의 제안 비용 목표**

- 합성 경험 10,000건을 대상으로 검색시간 측정
- 일반적인 색인 검색 중앙값 10ms 이내 목표
- 검색 및 후보 생성 추가 메모리 측정
- 데이터가 10배, 100배 늘어날 때의 증가 추세 기록
- 새로운 상주 검사관이나 GPU 작업자 0개

이 숫자는 새로운 설계 목표이며 아직 측정된 성과가 아니다. 구현 전에 시험 환경과 기준을 봉인한다.

목표를 넘더라도 증거 검증을 삭제하지 말고 자료 구조를 개선한다.

---

## 8. 먼저 작성할 오프라인 시험

새 CPU를 임대하기 전에 모의 CPU 구조로 다음을 확인한다.

### CPU 경로 시험

1. 물리 코어 1개에서 SERIAL만 구성
2. 물리 코어 4개에서 W3 후보 구성
3. 물리 코어 5개에서 W4 후보 구성
4. 물리 코어 6개에서 W6 후보 구성
5. SMT 형제 논리 CPU를 독립 물리 코어로 중복 계산하지 않음
6. 허용 CPU 번호가 연속적이지 않아도 올바르게 배치
7. CPU quota가 부족하면 해당 병렬 후보 거부
8. 허용 CPU 변경 후 이전 배치 재사용 차단
9. 코어 식별 누락 시 안전하게 거부
10. 선택된 배치와 실제 기록된 배치 불일치 검출
11. W6의 주 CPU 공유 규칙 유지
12. 다른 운영체제·혼합형 CPU의 지원 여부를 근거 없이 확대하지 않음

### 경험 탭 시험

13. 과거 서명과 원본 해시가 정상인 자료 검색
14. 원본 변조 또는 서명 변조 탐지
15. 과거 CPU의 성능을 현재 CPU의 공식 성능으로 승격하지 않음
16. 동일 CPU 모델이나 동일 `env_id`라도 다른 세션의 무단 활성화 금지
17. WALL_MIN과 CPU_MIN 지식 혼용 금지
18. 정밀도와 물리·수치 계약 불일치 시 거부
19. GPU 경험을 CPU 전용 후보에 잘못 적용하지 않음
20. 수천 건의 자료 중 일부가 손상돼도 임의로 승인하지 않음
21. 중복 기록으로 경험의 신뢰도를 부풀리지 않음
22. 인덱스가 손상되면 원본을 수정하지 않고 재구성하거나 STOP
23. 이전 snapshot과 복귀 기능 유지
24. 미래 재사용 횟수를 모를 때 실험 자동 실행 0회

기존 254개 관련 회귀 시험도 포함한다.

신규 시험 개수와 최종 전체 합계는 실제 실행 결과로 보고한다.

**모의 CPU 환경에서 후보를 만들었다는 사실을 다른 CPU에서 실제 계산한 증거로 해석하지 않는다.**

## 9. 구현 순서와 승인 경계

### 단계 1. 설계·봉인

새 브랜치를 기준 HEAD에서 생성한다.

기존 소스와 보호 원본을 확인한다.

경험 형식, 신뢰 수준, CPU 후보 생성 범위, 중단 규칙, 비용 목표를 코드 작성 전에 문서화·봉인한다.

### 단계 2. 시험 먼저 작성

모의 CPU, 과거 경험, 잘못된 서명, 다른 세션, 예산 부족에 관한 시험을 먼저 작성한다.

특히 과거 경험을 무단으로 승인하는 최소 반례를 반드시 만든다.

### 단계 3. 최소 구현

새 탭의 색인·검색과 후보 생성만 구현한다.

기존 선택기·어댑터·검사관·관리자를 복제하거나 광범위하게 수정하지 않는다.

### 단계 4. 제한 오프라인 검증

기존 254개 관련 시험과 새 시험을 수행한다.

현재 로컬 동적 시험 금지 규칙을 유지한다.

원격 시험이 필요하다면 CPU/시간/메모리/요금 상한과 외부 종료 절차를 별도로 제출하고 승인을 받는다.

**이 계획서 자체는 서버 임대나 재시작 승인서가 아니다.**

### 단계 5. 결과 보고 및 로컬 커밋

결과를 새로운 문서에 보존하고 로컬 커밋한다.

GitHub push와 master 병합은 하지 않는다.

## 10. 실제 다른 CPU 실험은 별도 단계

V0 오프라인 시험이 통과하더라도 자동으로 새 CPU를 임대하지 않는다.

다음 유료 단계에서는 정확한 CPU 후보와 지원 환경을 먼저 제시한다.

실제로 시험할 수 있는 경로와 예상 비용을 비교하고, 가장 정보 가치가 높은 소수 후보부터 선택한다.

공식 성능 프로필 승격에 필요한 반복 측정 및 별도 CPU 재현·검사·관리자 승인 기준은 유지한다.

다른 CPU에서 확인해야 하는 핵심 질문은 다음과 같다.

**같은 N14/T1000/p163 문제에서 CPU 구조별로 유리한 경로가 달라지는가?**

그리고 더 중요한 두 번째 질문은 다음과 같다.

**반장의 탭을 활용했을 때, 처음부터 모든 경로를 시험하는 방법보다 실제 교육비가 감소하는가?**

새 세션의 검증된 비용 자료 없이 교육비 절감을 성공으로 선언하지 않는다.

## 12. 완료 판정

**`TABLET_INDEX_OFFLINE_VALIDATED`**

과거 원본과 서명에 묶인 경험을 검색·보관하고, 손상·혼입을 거부하는 제한 시험을 통과한 상태.

**`CPU_ROUTE_CANDIDATES_OFFLINE_VALIDATED`**

모의 CPU에서 SERIAL/W3/W4/W6 후보 생성과 기존 배치 검사를 통과한 상태.

**`TRANSFER_HINTS_ONLY`**

과거 성능을 유용한 참고 정보로 분류하지만 새로운 CPU의 공식 성능으로 승격하지 않는 상태.

**`NOT_READY / REFUSED`**

실행 자격 부족, 잘못된 증거, 승인 위반, 검증 비용 과다 등의 이유로 새 경로 적용을 보류하거나 거부한 상태.

위의 어느 판정도 실제 다른 CPU에서 더 빨라졌다는 뜻은 아니다.

완료 보고서는 반드시 다음을 구분한다.

- 구현됨
- 오프라인 시험됨
- 실제 CPU에서 측정됨
- 독립 검증됨
- 아직 미확인
