## 독립 판독에서 발견한 결함

별도 replayer의 새 `(14,1000,163)` CPU 결과가 생성됐다. 각 실행 뒤 메모리상의 기록은 기존
검사기로 대조했고 통과한 뒤 다음 측정으로 넘어갔다. 전체10개를 저장 파일에서 다시 읽는
별도 검사관은 첫 기록에서 **INITIAL_HASH / REFUSED**를 반환했다. 관리자에게 서명 영수증이 전달되지 않았다.

원인은 초기 상태 해시의 JSON 키 순서 불일치다.

1. bridge는 초기 상태를q,p 순서로 만든 뒤 `json.dumps(initial)`로 해시한다.
2. 원본 증거 저장 함수는 canonical JSON으로 키를 정렬해p,q 순서로 저장한다.
3. inspector는 다시 읽힌p,q 순서를 `json.dumps`로 해시하므로 저장된 해시와 다르다.

10개 모두 값은 원래 상태와 같고 저장된 해시는 원래q,p 순서와 같았다.
원래 해시 `e729ee253811914b1ee7d375ea3b8d376a24ef12716dfe0afe6e8bf3ac349dc1`과
재판독 해시 `b6bc3ec28ac29a6bb28796c8d7ea500f905c543fba4cd3a16bd265d7365db4ff`가 달랐다.
실행 중 판독은 메모리 객체를 사용해 이 저장·재판독 결함을 발견하지 못했다.
첫 저장에서 생긴 문제를 마지막 원본 판독에서 발견했다는 검출 시점의 한계도 남긴다.

중단 후 읽기 전용 진단에서는 원본을 수정하지 않고10개 모두 기존 `_check_pass`로 새 replay와 대조했다.

이는 원인 진단이며 실패한 증거를 VERIFIED로 바꾸는 검사관 영수증이 아니다.
RwForce 공유도 그대로이므로 완전 독립 수식 검증이나 형식 인증을 뜻하지 않는다.

오프라인142개 통과는 실제 객체의 저장→재판독 경로를 충분히 검증하지 못했다.
