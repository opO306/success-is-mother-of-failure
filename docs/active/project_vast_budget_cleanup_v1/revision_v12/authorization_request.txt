# A320 원격 실행 안정화 및 최종 검증 계획 V12
## 구현자 전달용 실행 계획서

**작성일:** 2026-10-10  
**기준:** `NEXT_EXECUTION_V10_FAILED_CLOSEOUT.md` 및 `revision_v11`  
**목표:** 서버 연결이 끊겨도 시험 상태와 원본을 안전하게 확인하고, 반장의 경험 탭 A320과 검색 성능 측정을 완료한다.

### 1. 현재 상태와 이번 작업 범위

이미 확인된 성과는 보존한다.

| 작업 | 현재 상태 |
|---|---|
| 원격 관리 시험 176개 | 전부 통과 |
| B95 | 95개 전부 통과, 서버 정리·비용 정산 완료 |
| A320 | SSH 중도 종료, 공식 통과 수 미확정 |
| 검색 속도 측정 | 결과 미확인 |
| V11 원본 보호 수정안 | 정적 검토 완료, 실제 시험 10개 미실행 |
| 현재 Vast 서버 | 인스턴스·별도 볼륨 0개 |

B95를 다시 실행하는 것은 이번 작업의 목표가 아니다.

다만 공통 관리 코드를 수정해 B95 결과의 신뢰성에 영향을 준다면 해당 영향은 별도로 검증한다.

계산기의 물리 법칙, 반올림, 기존 320개 시험과 판정 기준은 변경하지 않는다.

**이번 작업의 핵심은 A320을 끝내는 것이며, 서버 관리 시스템을 새로 만드는 것이 아니다.**

### 2. 첫 번째 구현: SSH 연결과 실제 시험 실행 분리

지난번 A320은 원격 SSH 연결이 중간에 끊겼다.

하지만 SSH 연결이 끊어졌다는 사실만으로 원격 시험 프로그램도 종료됐다고 단정할 수 없다.

이를 해결하기 위해 기존 실행 코드를 최소 수정한다.

**변경할 구조**

```text
서버 준비
    ↓
작업 번호 부여
    ↓
원격 시험 프로그램 독립 실행
    ↓
실제 실행 중인 프로세스 정보 기록
    ↓
SSH 연결과 관계없이 시험 진행
    ↓
실행 상태를 주기적으로 확인
    ↓
프로그램의 실제 종료 확인
    ↓
최종 결과 검증
    ↓
원본 회수 및 서버 정리
```

구현 조건:

- 고유한 작업 번호, 실제 프로세스 ID와 시작 시각을 기록한다.
- 기존 작업이 살아 있으면 동일 시험을 중복 실행하지 않는다.
- SSH가 끊기면 같은 서버에 다시 연결해 기존 작업 상태를 확인한다.
- 재접속에 실패했다고 곧바로 새 서버를 임대하지 않는다.
- 프로그램이 정상 종료했는지, 오류로 종료했는지, 아직 실행 중인지 구분한다.
- 제한시간과 예산을 넘기는 작업은 기존 감시 기능이 중단할 수 있어야 한다.
- 종료 감시를 피하는 숨은 작업이나 고아 프로세스를 남기지 않는다.

기존 운송기와 감시기를 우선 재사용한다. 새로운 상주 관리 시스템은 만들지 않는다.

**성공 조건:** SSH 연결을 의도적으로 끊어도 원격 프로그램이 어떻게 됐는지 다시 확인할 수 있어야 한다.

### 3. 두 번째 구현: 연구 결과 작성 완료 확인

V10에서 발견된 가장 위험한 결함을 수정한다.

기존 코드는 회수한 ZIP 파일의 해시가 일치하면 원본 회수가 완료됐다고 판단할 수 있었다.

하지만 **파일 내용이 정확하다는 것과 모든 파일의 작성이 완료됐다는 것은 별개의 문제**다.

V11의 수정안을 출발점으로 삼되, 다음 조건을 실제 실행 결과로 입증한다.

**원본 작성 완료 확인**

- 시험 프로그램의 실제 종료 상태 확인
- 해당 작업과 하위 프로그램의 작성 종료 확인
- 마지막 결과 기록이 완전히 작성됐는지 확인
- 임시 파일과 완성 파일 구분
- 원격 파일 목록과 개별 해시 확인
- 로컬 회수 파일의 개별 해시 일치
- 다른 작업의 파일이나 과거 결과가 섞이지 않았는지 확인

최종 결과는 임시 파일에 작성한 뒤 완료된 파일로 확정하는 방식 등을 활용한다.

실행 중간에 읽은 파일을 최종 결과로 승격하지 않는다.

`revision_v11/terminal_proof.py`, `lifecycle.py`, `cleanup.py`, `transport/controller.py`, `transport/guest_recover.py` 등 관련 경로를 검토하고, 실제 수정이 필요한 부분만 변경한다.

**정상 완료 판정과 실패 후 회수 판정은 반드시 분리한다.**

정상 완료에서는 A320의 최종 시험 결과와 모든 요구 증거가 있어야 한다.

실패 종료에서는 실패 사실, 종료된 작성 프로그램, 실제로 확보된 파일과 누락된 파일을 별도로 기록한다. 이를 시험 성공으로 처리하지 않는다.

### 4. 세 번째 구현: 안전한 서버 삭제 조건

이번에는 서버를 삭제한 뒤 중요한 결과가 더 작성됐을 가능성이 남는 일을 막아야 한다.

서버 삭제 전 다음을 확인한다.

1. 정확한 인스턴스와 작업 번호가 일치하는가?
2. 원격 프로그램과 관련 작성자가 모두 종료됐는가?
3. 최종 결과 또는 종료된 실패 상태를 실제로 확인했는가?
4. 중요한 원본을 모두 회수하고 개별 해시를 검증했는가?
5. 중요한 누락 자료가 없는가?
6. 승인된 삭제 범위에 해당하는가?

**정상 완료 경로**

시험 완료 → 원본 검증 → 실제 정지 → 정확한 인스턴스 삭제 → Vast 목록 확인 → 장부 정산.

**실패 경로**

원인 확인 → 가능한 원본 회수 → 작성 프로그램 상태 확인 → 실제 정지.

중요 원본이 미회수이거나 작성 상태를 확인할 수 없다면 자동 삭제하지 않는다.

다만 서버를 무기한 보관해서도 안 된다. 정지 상태와 예상 디스크 비용을 보고하고, 추가 회수 또는 확인된 손실 범위의 폐기 승인을 사용자에게 요청한다.

기존에 허용된 준비용 임시 파일 손실 예외를 연구 결과까지 확대하지 않는다.

**삭제 성공의 기준은 실제 공급자 목록에서 해당 인스턴스가 사라진 것이며, 삭제 명령의 반환값만으로 판정하지 않는다.**

### 5. 네 번째 단계: 실제 오류 상황 시험

V11에 준비된 **신규 시험 10개**를 먼저 실행한다.

기존에 작성한 시험을 버리고 비슷한 시험을 다시 만드는 대신, 실제 V11 소스를 활용한다.

핵심 검증 상황:

- 정상 프로그램 종료
- SSH 연결 중도 종료
- 연결 종료 후에도 시험이 실행 중인 경우
- 연결 종료 뒤 이미 시험이 끝난 경우
- 실행 상태를 확인할 수 없는 경우
- ZIP 파일 해시는 맞지만 작성자가 살아 있는 경우
- 최종 결과 파일이 누락된 경우
- 실패 종료와 정상 종료를 혼동하는 경우
- 다른 작업의 완료 표식을 잘못 받아들이는 경우
- 중요 원본이 누락된 상태에서 삭제를 시도하는 경우

추가로 실제 변경의 영향을 받는 기존 관리·회수·종료 시험을 실행한다.

동적 시험은 허용된 원격 환경에서만 수행한다.

**사용자 로컬의 프로젝트 동적 시험은 계속 금지한다.**

실제 원격 검증 결과가 나오기 전에는 정적 봉인이나 동료 검토만으로 통과를 선언하지 않는다.

### 6. 다섯 번째 단계: A320 실제 검증

앞의 안전 검증을 통과한 뒤 A320을 실행한다.

기존 320개 시험의 항목과 판정 조건은 유지한다.

**A320 합격 조건**

```text
실제 시험 수: 320
통과: 320
실패: 0
오류: 0
건너뜀: 0
최종 결과 파일: 확인됨
전체 원본: 회수·해시 검증 완료
```

시험 로그의 점 개수나 중간 출력만으로 통과 수를 계산하지 않는다.

종료가 정상인지 확인하고, 실제 JUnit 및 기존 검증 자료를 읽어 판단한다.

SSH가 중간에 끊겨도 같은 서버에서 실행 상태를 확인하고 이어서 관리한다.

행정 문제는 구현자가 승인된 비용과 시간 안에서 직접 고치고 재검증할 수 있다.

다만 계산 결과의 오류나 기존 검사 기준을 바꿔야 하는 문제가 생겼다면 임의로 성공 처리하거나 수치 기준을 낮추지 않는다.

### 8. 행정 오류 대응 권한

**중요: 이전 계획의 과도한 중단 방식을 반복하지 않는다.**

구현자는 다음 운영 문제를 승인된 서버 사용 범위에서 직접 조사·수정·재검증할 수 있다.

- SSH 연결과 재접속
- 서버 초기화 지연
- 프로그램 설치
- 파일 경로와 권한
- 파일 전달과 회수
- 시험 수집 오류
- 실행 상태 확인
- 준비용 프로그램 오류

이런 문제로 실패했다고 곧바로 서버를 삭제하고 새 서버를 빌리지 않는다.

가능하면 **같은 서버에서 문제를 해결하고 검증을 이어간다.**

수정 전 실패 기록은 보존하고, 수정한 버전을 구분한다.

반대로 다음 문제가 발생하면 안전을 우선한다.

- 계산기 물리·수치 정확성 불일치
- 원본 무결성 훼손
- 서버 신원 불일치
- 권한·봉인 경계 위반
- 실행 중인 작업의 통제 상실
- 중요한 원본의 손실 위험
- 예산·승인 시간 초과 위험

이 경우 추가 계산을 멈추고 실제 상태를 확인한다.

**행정 문제를 고칠 수 있는 자율성과 연구 결과를 안전하게 보호하는 의무를 동시에 유지한다.**
