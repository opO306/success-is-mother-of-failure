## 3. 변경 내용

### (가) 기존 서버 정식 폐기·정산 — `discard_v12_2_owned.py` (신규)
기존 `close_owned`는 V12.2 bridge가 `HOLD_BY_USER`를 강제하고, 원격 probe 폴더를 다시 볼 수 없어 폐기 자격을 만들 수 없다. 기존 `validate_exact_discard_approval`은 "연구 명령 미발행" 상태 전용이라 관리 시험이 돈 이 서버에 맞지 않는다. 그래서 **사람 승인에 묶인 손실 목록(loss packet)** 방식으로 별도 처리한다.

1. 읽기 전용: 서버 신원·정지 상태·볼륨·요금 확인.
2. 로컬 증거 재검사: `startup_raw` 2개 해시, 관리 원본 닫힌 보관 증명, `stage_closeout.json` 원문 6,099개, V12.2 실패 원본.
3. 손실 목록 작성: "원격에만 있을 수 있는 것" = 단절 probe 입력 폴더(발사 의도 없음), 그 밖의 `/workspace` 미검사 범위(UNKNOWN). 패킷 SHA-256 고정.
4. **사람 승인 기록**(패킷 해시에 묶임, 유효시간 있음)이 있어야만 다음으로 진행.
5. STOP 확인 → `destroy_with_disposition`(기존 함수, 3회 한도) → 목록에서 사라짐·볼륨 불변 확인.
6. `reconcile_destroyed`(기존 함수)로 원예약 + V12.2 연장 $0.06 정산. 장부 활성 0 확인.

### (나) V12.3 진입점 — `revision_v12_3/fresh_owned.py` (신규, 얇은 래퍼)
V12 `campaign.main/stage`를 **그대로 호출**하되 시작 전에 다음을 설치한다(V12.2가 쓴 방식과 같은 monkeypatch).
- `campaign.Provider` → 읽기(`show instance/instances/volumes/invoices`)만 `read_retry`로 감싼 하위 클래스. 생성·시작·STOP·삭제는 감싸지 않는다(V12.2 `continue_owned.py:72-88`의 `Reads`와 같은 규칙).
- controller `Transport.show` → `transport_reads.transport_class`. 감시기 supervisor/guardian → `process_bridge.install_dispatch`.
- V12의 관리 단계 뒤, A320 앞에 **V12.2 신규 관리 시험 24개 + 영향 시험 6파일**을 같은 서버에서 실행(V12.2 `continue_owned.py:163-182`와 같은 순서·판정).
- 실제 SSH 단절 시험은 V12 원본 `verify_ssh_disconnect_probe`를 그대로 쓰고, V12.2의 `probe_runner` 경로와 중복이면 하나만 남긴다(§7 G1에서 확인 후 결정).

### (다) 승인·시간 기준
- 새 승인 형식 `V12_3_ACTUAL_BUNDLED_PAID_APPROVAL`: 새 서버 1대, 창 1800초(결정 D2), 예약 상한 $0.20, 총 $2, A320 1회, B95 0, 후보 봉인 SHA에 묶음, 1회 사용 claim.
- 시간 기준은 **실제 생성 시각**(V12 원본과 같음). V12.2처럼 승인 시각에 묶지 않는다.

### (라) 서버 지문 기록 (읽기 전용, 판정에 쓰지 않음)
준비 완료 직후 `/proc/cpuinfo` flags, `nproc`, cgroup `cpu.max`, `/sys/devices/system/cpu` 물리 코어 목록, `uname -a`, Python 버전을 원문 그대로 회수한다. 실패해도 시험 판정은 바꾸지 않되, 실패 사실은 기록한다. 기존 `env_id` 수집기를 그대로 쓸 수 있는지는 G2에서 확인한다.

## 7. A–H 검토

**A. 왜 하는가?** 같은 서버 재개가 공급자 GPU 점유로 실패했다(`api/0004.stdout`: "Required resources are currently unavailable, state change queued."). A320·검색은 한 번도 실행되지 않았다. 가장 단순한 해결은 새 경로를 만드는 것이 아니라 **이미 있는 V12 새 임대 경로**에 V12.2 수정만 연결하는 것이다. 대안 "같은 서버 대기 후 재시도"는 GPU가 언제 비는지 몰라 비용·시간이 불확정이라 택하지 않았다.

**B. 무엇을 당연하게 여겼는가?**
- 새 서버 생성 시 GPU가 즉시 배정된다 — `create ... --cancel-unavail` 사용(`campaign.py:356`), 생성 불가면 공급자가 취소. 확인됨(코드), 이번 기계에서 실제 미확인.
- 다른 하드웨어에서 A320 320개가 같은 판정을 낸다 — **UNCONFIRMED**(G3). 확인 방법: 이번 실행 자체.
- V12.2 수정 모듈이 V12 원본 진입 경로에서도 같은 함수를 감싼다 — V12.2는 `continue_owned` 안에서만 연결됐다. **UNCONFIRMED**(G1). 확인 방법: 호출 경로 대조 + D4 모의 시험.
- 계정에 다른 Vast 자원이 없다 — 06:04 실제 목록 1대(기존 서버)뿐. 폐기 후 0 재확인 필요.

**C. 설계가 틀렸다면?**
- 가장 먼저 깨질 곳: monkeypatch가 V12 `stage` 안에서 새로 만드는 `Provider`(예: `remote_admin`의 `admin_provider`, `campaign.py:125`)를 놓치는 경우 → 그 경로는 여전히 8초 단일 조회. 대책: 클래스 자체를 교체하고 생성된 모든 Provider 인스턴스 유형을 실행 기록에 남겨 검사.
- 정상처럼 보이는 반례: 조회 재시도 중 서버가 실제로 다른 상태로 바뀜 → 신원·상태 검사는 매 재시도마다 다시 수행(V12.2 규칙 유지).
- 위험한 경로: 폐기 스크립트가 잘못된 인스턴스를 지움 → 신원 검사 + 패킷의 owner 고정 + 승인 기록 해시 결합.

**E. 문제가 왜 발생했는가?**
- 최초 실패: V12에서 8초 단일 상태 조회 시간초과(`failure.json`). V12.2에서는 정지 서버 재개 시 공급자 자원 부족.
- 근본 원인: (1) 읽기 실패 복구 경로 부재(V12.2에서 수정, 미실행), (2) "정지 서버는 다시 켜진다"는 가정. Vast는 정지 서버의 GPU를 보장하지 않는다.
- 사전 검토 공백: 정적 검토는 공급자 용량을 볼 수 없었다. 같은 가정의 다른 사용처: V7의 같은 서버 연장 경로(`campaign.py:306-332`, 현재 비활성).

- 수정 후: 원격 실행에서 신규 관리 24 + 영향 6파일 PASS, 실제 SSH 단절 후 작업 생존 확인, A320 320/320, 검색 3×31 완료 증거, 전체 원본 해시 일치, 삭제 확인·정산.
