## 2. INITIAL_HASH의 정확한 결함과 새 지문

이전 producer는 q,p 순서의 `json.dumps` 바이트로 initial_sha256을 생성했다. 저장기는 키를 정렬해 p,q 순서로 원본을 썼다. inspector는 다시 읽힌 p,q 순서로 과거 직렬화를 적용했다. 원자 값이 같아도 직렬화 순서가 달라 거부된 것이다.

새 버전은 원본 raw SHA-256과 INITIAL_STATE_CANON_V2 내용 지문을 분리한다. 원본 지문은 공백·키 순서까지 보존/변조를 판별하고, 내용 지문은 정확히 q,p 필드의 키만 정렬한다. 원자/좌표 배열과 정확한 수치 문자열은 바꾸지 않는다. q는 위치, p는 운동량이며 계산 정밀도 p와 별개다.

과거 initial_sha256의 의미는 LEGACY_QP_JSON_V1으로 유지한다. 중복 키, 필드 누락/추가, 숫자 변환, 배열 순서 변경, 버전 삭제/낮춤은 허용하지 않는다. 실제 초기 운동량의 `-6/7`, `-1/7`도 계산·약분 없이 문자열 그대로 처리한다. 과거 기록은 고정된 원본/세션/소스/replay를 확인하는 historical review에서만 별도로 읽는다. live 자료의 버전 우회 경로는 없다.

구상 일치성은 자동 시험과 별도로 코드·관문·영수증을 대조했다. 기존 검사관을 유지하고 원본 불변, 값 재도출, 명시적 관리자 승인, 다음 고비용 호출 전 검사, 비용 기준 거부를 구현했다. 이 구현자 검토는 별도 기관의 승인이나 수식 인증이 아니다. 세 권한은 코드/파일/서명으로 구별하지만 같은 OS 사용자 권한이다. 별도 계정·신뢰키와 관리자 저장소 접근 통제는 후속 보안 과제다. INDEPENDENT_FORMULA_VERIFICATION_V0도 별도 후속 과제로 남는다.

실제 N14 학습 실측 재개에는 정정 자료 사용에 대한 정당한 관리자 승인, 새 실제 세션의 별도 실행 예산·명시적 허가, 지속 외부 감시·할당/회수/종료 기한 확인, 실제 후보→독립 성능 검증→승인→다음 요청→복귀 흐름의 새 증거가 더 필요하다. 이번 관문을 근거로 유료 N14 재측정을 자동 시작하지 않는다.

## 10. Git 줄끝과 raw 봉인의 재현 조건

최종 행정 대조에서 새 실패/성공/봉인 패키지192개 파일의 작업 바이트와 Git blob은 모두 일치했다. 별도로 기존 소스/옛 Verification 자료75개는 Windows 작업 바이트의CRLF와 Git 저장본의LF가 달랐다. 75개 모두 줄끝만 달랐고 Git blob은 기준62154878과 동일했다. 이 작업에서 생긴 기존 파일 변경은 없다. [파생 Git 바이트 대조](evidence_canonicalization_v0/validated_54815136/git_byte_checks.json)에 경로·줄끝 판독·기준 비교를 남겼다.

원래 봉인은 작업 파일의 raw 바이트를 결합한다. Git checkout의 줄끝 설정과 그 봉인 바이트를 동일하다고 가정하면 안 된다. 이번 제한 관문은 실제 raw 파일을 묶은 봉인 ZIP을 전송해507개 소스 해시를 그대로 확인하고 실행했다. 동일 재현에는 이 ZIP을 사용한다. 기존 보호 파일의 줄끝이나 기존 봉인 규약을 사후 변경하지 않았으며, Git checkout만으로 모든 역사 raw 봉인이 재현된다고 주장하지 않는다. 이 한계는 수치 결과/새 증거 처리 관문의 합격과 구별해 남긴다.
