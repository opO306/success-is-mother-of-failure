# 구현 의문·영향·반례 검토 표준 V1

적용: 이 규칙 도입 이후 작성하는 모든 새 구현·수정·실험 계획서. 기존 역사 계획·결과·봉인은 수정하지 않는다. 근거는 설계자 요청 `ADMIN_TRANSPORT_STATE_CONTRACT_AND_CRITICAL_REVIEW_V1`이다. 새로운 검사 기관이나 승인 권한을 만들지 않는다.

## 계획 전에 확인할 질문

목적: 해결할 실제 문제는 무엇인가? 기능이 필요한가? 기존 기능으로 해결할 수 있는가? 가장 단순한 방법은 무엇인가? 기능을 추가하지 않고 해결할 수 있는가?

가정: 무엇을 사실로 가정했는가? 실제 기록으로 확인했는가? 어느 환경에서 깨지는가? 모르는 정보는 무엇인가? 과거 성공 방식이 현재 환경에도 적용된다는 근거는 무엇인가?

실패: 어떻게 실패하는가? 정상 입력의 다른 형태는? 누락·지연은? 중단 후 남는 원본은? 재실행하면 중복·손상이 생기는가?

대안: 더 단순한 방법은? 검증을 유지하며 비용을 줄일 수 있는가? 기존 코드 조합으로 해결하는가? 선택하지 않은 방법의 이유는?

모든 중요 가정에 **코드 위치·실제 원본·시험 결과**를 연결한다. 근거가 없으면 `UNCONFIRMED`와 확인 방법을 적는다. 답을 길게 쓰는 것보다 근거와 반례를 확보하는 것이 우선이다.

## 새 계획서의 필수 A–H 양식

| 항목 | 반드시 기록할 것 |
|---|---|
| A. 왜 하는가? | 실제 문제·증거·대안·가장 단순한 해결책 |
| B. 무엇을 당연하게 여겼는가? | 환경·자료형·OS·시간·자원·호출 관계의 가정, 확인/미확인 근거 |
| C. 설계가 틀렸다면? | 정상처럼 보이는 반례·가장 먼저 실패할 곳·위험한 경로 |
| D. 다른 곳에 미치는 영향은? | 직접/간접 호출자·예외·시작/종료·저장·정확성·성능·검증·권한·비용·복귀 |
| E. 문제가 왜 발생했는가? | 최초 실패·증상/근본 원인·사전 검토 공백·같은 가정의 다른 사용처 |
| F. 무엇으로 입증하는가? | 수정 전 실패/수정 후 통과 반례, 실제 환경 자료, 다음 단계 차단 검사 |
| G. 무엇을 아직 모르는가? | 미시험 조건·성능/비용·권한·공유 신뢰 기반·근사/미구현/충돌 |
| H. 지금 실행할 권한이 있는가? | 명시적 승인 범위·원본 보존·실제 예산 기록·회수/종료 가능성 |

영향 분석은 `변경 대상 → 영향을 받는 부분 → 필요한 시험 → 미확인 사항`으로 작성한다. 함수 하나를 바꾸면 모든 직접·간접 호출과 예외·시작·종료 경로를 확인한다. Windows/Linux·CPU·API 상태별 입력 차이도 포함한다.

## 오류 발생 후 원인·영향·반례 분석 관문

코드를 바로 고치지 않고 다음 순서로 남긴다.

1. 최초 실패와 실제 오류는 무엇인가?
2. 입력·환경·코드 가정이 어떻게 달랐는가?
3. 왜 사전 검토/시험에서 발견하지 못했는가?
4. 같은 함수·규칙·가정의 다른 사용처는?
5. 수정 영향과 새 실패 가능성은?
6. 수정 전후 판정을 대조할 반례는?
7. 재실행 권한과 남은 시간·자원·비용은?

증상이 같다고 원인을 같다고 단정하지 않는다. 원인을 확인하지 못한 임시 수정으로 합격시키지 않는다. 실패 시험·원본을 삭제하거나 기준을 낮추지 않는다. 수정 후 전체 영향 범위의 관련 시험을 다시 수행한다. 원래 중단/재시도 규칙과 사용자의 실행 제한은 그대로 적용한다.

## 자기반박과 별도 검토

구현자는 가장 먼저 실패할 지점, 가장 약한 증거, 시험 후 남는 실제 환경 위험, 공유 경로와 구조적 원인을 적는다. 별도 검토자는 실제 코드와 원본을 직접 읽고 놓친 반례를 찾는다. 요약의 반복은 검토로 세지 않는다. 동료 검토와 독립 권한·서명 인증을 구별한다.

## 완료 보고 표

| 구분 | 내용 |
|---|---|
| 구현됨 | 실제 변경 파일·작동·구상 일치성 |
| 시험됨 | 실행 환경·명령·입력·예상/실제 판정·PASS/FAIL/error/skip 원본 |
| 독립 검증됨 | 별도 검토/독립 권한이 실제 확인한 범위와 한계 |
| 실패·반례 | 최초 실패·원인·영향·차단/원본 보존 결과 |
| 비용·성능 | 실제 측정 시간·CPU·메모리·비용, 추정/실청구 구분 |
| 미확인 | 실행하지 않은 조건·미구현·인증되지 않은 범위 |
| 다음 행동 | 필요한 승인·보류 사유 |

작성 완료, 정적 통과(`STATIC_READY`), 모의 동작 확인, 실제 원격 기능 통과를 서로 대체하지 않는다. 서버 STOP 요청과 실제 `exited/stopped` 및 외부 종료 영수증도 구별한다. 승인이나 검증되지 않은 추측을 사실로 작성하면 계획 관문을 통과시키지 않는다.
