# XREPRO_RESOURCE_V1 — 노트북 교차 재현 (Resource Evolution V1 최소 재현 세트)

상태: **결과 기록 (2026-10-06)**. 판정 **REPRODUCED** (데스크톱 새 실행·노트북 둘 다, 실패 0).
증거 수준 = 두 기기 실행 + 실행기와 분리된 비교기 확인. formal 아님. 성능 경쟁 아님.
브랜치 `claude/resource-xrepro-multiatom-v1`(부모 `7b09e53` = Resource Evolution V1 run 2 결과).
protocol `8080b0f` → 코드 `48da1f8` → 비교기 수정 `0584323`(증거 실행 전, 아래 공개) → 노트북 원본 `e75f29a`.

## 0. 한 줄 결론

다른 CPU(데스크톱 Ryzen 5 5600 / 노트북 Ryzen 5 4500U)와 다른 Windows 빌드에서, 같은 commit의 같은 코드는
**구간 끝점까지 비트 단위로 같은 결과**를 냈다. 코어 1개와 6개, 다른 코어 번호에서도 같았다. 차이가 하나도 없었으므로
"최초 차이 위치"는 없다.

## 1. 무엇을 했나 (쉬운 말)

비유: 같은 설계도(commit)로 다른 공장(노트북)에서 같은 부품을 만들어, 부품을 현미경(정확한 유리수 끝점)으로 비교했다.
80분짜리 전체 캠페인을 다시 돌리지 않고, 결과를 결정하는 대표 작업만 골랐다.

실제 의미:
- 코드 전달: 처음 시도한 임시 LAN 전송 서버는 자동 권한 검사가 막았다. 설계자 승인으로 **이 브랜치 하나만** GitHub에 push하고,
  노트북이 그 브랜치를 clone했다(전체 history 포함 → commit hash 그대로). master와 다른 브랜치는 건드리지 않았다.
  노트북 결과는 노트북에서 commit 1개(`e75f29a`, 원본 기록만)로 같은 브랜치에 push하고 데스크톱이 fetch했다
  (설계자 승인). 압축본 SHA256 `99328497…229a`는 양쪽에서 같다.
- 노트북 설치: Git 2.55.0(winget), 별도 venv `C:\Users\zun24\ResourceXReproV1\venv`에 mpmath 1.3.0, psutil 7.2.2,
  sympy 1.14.0. gmpy2는 설치하지 않았다(양쪽 모두 mpmath 순수 Python 백엔드 확인).
- 실행기: run 2의 봉인 코드(`orch.py`, `worker.py`, `verifier.py` 등)를 **그대로** 썼다. 바꾼 것은 메모리 안의
  코어 배치표뿐이다(데스크톱 [2,4,6,8,10,0] + 지휘 1, 노트북 [1,2,3,4,5,0] + 지휘 0; 노트북은 SMT가 없어 6코어 때
  지휘 프로세스가 6번째 작업자와 같은 CPU를 쓴다 — 지휘는 50ms마다 확인만 함).
- 비교기(`compare.py`)는 실행기 모듈을 import하지 않고 JSON 기록만 읽는다. 칸(cell)은 끝점에서 A1 checker의
  반올림으로 다시 유도한다.

## 4. 성능 (보조 자료 — 기기 사이 절대 시간은 승패가 아님)

9개 요청 묶음, 3회 중앙값. speedup = 같은 기기 1코어 wall / k코어 wall.

| 기기 | 계획 | k=1 wall · CPU | k=3 speedup · 효율 | k=6 speedup · 효율 | k=6 CPU / k=1 CPU |
|---|---|---|---|---|---|
| 데스크톱 | BASE(E1) | 27.3 s · 25.8 s | 2.87 · 0.96 | 2.84 · 0.47 | 1.07 |
| 데스크톱 | BASE_E2 | 24.8 s · 23.4 s | 3.00 · 1.00 | 2.97 · 0.49 | 1.09 |
| 노트북 | BASE(E1) | 32.1 s · 29.9 s | 2.85 · 0.95 | 2.92 · 0.49 | 1.14 |
| 노트북 | BASE_E2 | 29.8 s · 27.6 s | 2.79 · 0.93 | 2.91 · 0.48 | 1.16 |

- 두 기기 모두 **3코어에서 약 2.85배, 6코어는 추가 이득 없음** — run 2와 같은 모양. 원인도 같다(가장 긴 요청 A3_high@3000이
  끝나야 묶음이 끝남). 즉 이 천장은 기계가 아니라 작업 구성에서 온다.
- E2/E1 CPU 비: 데스크톱 0.88–0.93, 노트북 0.92–0.94. **E2의 작은 순이득은 노트북에서도 남았지만 더 작다**(약 6–8%).
- 노트북은 코어를 많이 쓸수록 같은 일의 총 CPU가 14–16% 늘었다(데스크톱 7–9%). 저전력 칩에서 여러 코어가 동시에 돌 때
  클럭이 내려가는 것과 맞는 모양이지만, 클럭·온도는 측정하지 않았으므로 **원인은 미확인**이다.
- 데스크톱 BASE_E2 k=1 한 번이 39.0 s(다른 두 번 24.4–24.8 s)였다. 부하 스냅숏은 묶음 전후에만 찍혀 원인은 미확인이다. 중앙값에는 영향 없음.

## 5. 공개 사항·한계

- **비교기 수정(증거 실행 전):** 처음 commit한 비교기(`48da1f8`)는 이름이 정확히 `cpu_s`/`wall_s`인 시간 필드를 제외하지
  못했다(시험이 잡음). 시험 실패가 `| tail` 파이프 때문에 commit 명령을 멈추지 못해 결함 있는 상태가 한 번 commit됐다.
  증거 실행 전에 `0584323`으로 고쳤고, 두 기기 증거는 모두 `0584323`에서 실행됐다.
- 노트북 GitHub 인증을 기다리던 git·자격 증명 프로세스를 정리하면서 설계자의 로그인 창을 닫았을 수 있다(재시도로 해결).
- 두 기기, 같은 OS 계열(Windows), 같은 CPU 제조사(AMD). 리눅스·Intel·ARM에서의 동일성은 **미확인**.
  두 기기 비트 동일은 "같은 계산 의미가 유지됐다"는 관측이지 정확성 증명이 아니다.
- 성능은 기기당 3회. 노트북 전력·온도 상태는 통제·측정하지 않았다.
- `CURRENT_STATE.md`는 이 브랜치에서 갱신하지 않았다(master 문서, 이 계통은 미merge).
