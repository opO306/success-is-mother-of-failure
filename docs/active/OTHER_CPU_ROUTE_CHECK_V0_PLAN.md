# 다른 CPU 경로 확인 V0 — 계획 (공통 A–H 검토 포함)

2026-10-10 KST. 브랜치 `codex/adaptive-experience-tablet-cpu-route-v0`, 기준 `94aad8e0`.
설계자 원문: "①하고 너 내용만 따로 추가, 다음은 ②로 ㄱㄱ" (② = 무료 노트북에서 다른 CPU 실측, 계획서부터).

**한 줄 요약:** Vast에서 실제로 돌렸던 계산(입자 14개, 1000걸음, 정밀도 163)을 **바이트까지 같은 코드**로 노트북에서 "혼자 방식(SERIAL)" 5번, "6명 방식(W6)" 5번 돌려 시간을 잰다. 결과가 Vast 결과와 한 글자라도 다르면 즉시 멈춘다. 측정값은 경험 탭 v1 공유 힌트 판정(`transfer.judge`)에 넣어 본다. **장부 등록·승인·운영 적용은 하지 않는다.**

## 비유와 실제

- 비유: 장부에는 "A 공장(Vast)에서 6명이 나눠 하니 4.8배 빨랐다"는 기록 하나만 있다. B 공장(노트북)에서도 그런지, 그 기록을 "먼저 시험해 볼 순서"로만 써 본다.
- 실제: `experiments.adaptive_execution_v1.service.run_request`를 `FIXED_SERIAL` / `FIXED_W6`로 호출한다. Vast A resume V1이 쓴 바로 그 경로다(`experiments/adaptive_execution_real_learning_pilot_v0/bridge.py:46-50`).

## A. 왜 하는가?

- 실제 문제: 경험 탭 V0/V1은 "다른 CPU에서 어느 방식이 빠른가"를 모른다([검증 기록](ADAPTIVE_EXPERIENCE_TABLET_V0_OFFLINE_VALIDATED_2026-10-10.md)의 미확인 표). SERIAL/W6 실측은 Vast Ryzen 9 3900X 한 곳뿐이다([A resume V1 결과](ADAPTIVE_EXECUTION_REAL_LEARNING_PILOT_A_RESUME_V1_RESULTS.md): 중앙값 63.51초 → 13.51초).
- 이 계산이 알려 주는 새 정보: (1) 6코어 노트북에서도 W6가 확실히 빠른가, (2) 공유 힌트 판정이 실제 측정값에서 어떤 답을 내는가(첫 실제 사용), (3) 같은 코드가 다른 CPU에서 Vast와 **비트까지 같은 결과**를 내는가.
- 가장 단순한 방법: 기존 계산 경로를 그대로 부르는 측정 스크립트 하나. 새 계산기·새 검사관·새 승인 장치를 만들지 않는다.
- 선택하지 않은 방법:
  - 기존 실측 runner(`runner.py`) 그대로 사용 — Vast 전용 승인표(ticket)·바깥 감시 장치(armed)가 필수라 노트북에서는 가짜로 만들어야 한다. 금지(가짜 승인 금지)라서 쓰지 않는다.
  - 검사관 서명·관리자 승인까지 거친 정식 장부 등록 — 개인 서명키와 관리자 절차가 필요하고, 이번 질문(어느 쪽이 빠른가)에 필요하지 않다. 후속 과제로 남긴다.
  - 별도 재계산(replay)으로 정답 확인 — Vast 결과 10개와 Vast 재계산 1개가 이미 서로 같다(아래 F). 노트북 결과를 그 정답과 직접 비교하면 재계산 1회(약 1.5분)를 아낄 수 있다.
  - W3/W4 측정 — 기존 서비스 경로가 실제 자격을 주장하는 것은 SERIAL/W6뿐이고(`selector.py` `fixed` 설명, 프로토콜 `methods`), 장부 기록도 SERIAL/W6뿐이다. 범위를 넓히지 않는다.

## C. 설계가 틀렸다면?

- 정상처럼 보이는 반례 1: 결과가 다른데 시간만 비교 → 막음. 매 실행 직후 결과 지문을 Vast 지문(`70897884…`)과 비교하고 다르면 그 기록을 저장한 뒤 **즉시 멈춤**.
- 반례 2: W6를 요청했는데 실제로 직렬로 대체 실행되고 기록만 W6 → 막음. 계획의 backend/작업자 수, `executed_placement_ok`, 재시도·대체 없음(시도 1개), 서비스 이벤트 없음을 확인.
- 반례 3: 정밀도가 163이 아닌 다른 값으로 재시도 → `p_sequence == [163]`, `effective_p == 163`, 1회 통과만 인정.
- 반례 4: 노트북이 뜨거워져 뒤로 갈수록 느려짐(열 제한) → 교대 순서(Vast와 같은 봉인 순서)로 한쪽만 불리해지지 않게 하고, 최대/최소 비율 1.25 초과면 "측정 불안정"으로 표시.
- 반례 5: Windows의 다른 프로그램이 CPU를 씀 → 실행 전후 기록. 판정은 바꾸지 않고 해석에 반영.
- 가장 먼저 실패할 곳: 실행 전 검사(봉인·환경 자격). 예: WSL2의 cgroup이나 코어 식별이 기존 자격 규칙과 안 맞으면 계산 전에 REFUSED → 그것도 유효한 결과로 기록.
- 위험한 경로: 6개 작업자 프로세스가 남아 노트북을 계속 점유 → 기존 계산기가 작업자를 정리함(Vast에서 정상 종료 확인됨). 실행 후 남은 프로세스를 확인한다.

## E. 문제가 왜 발생했는가?

오류 수정 계획이 아니라 새 측정이다. 다만 "다른 CPU 실측 미확인"이 남은 이유: 원래 준비 단계는 이 PC 동적 실행 금지 + 유료 실행 별도 승인 조건이었고, 무료 Linux 노트북은 2026-10-10에야 준비됐다([V12.5 결과](project_vast_budget_cleanup_v1/V12_5_DISCONNECT_CONFIRM_RESULTS.md) 노트북 절).

## F. 무엇으로 입증하는가?

- 정답 지문: Vast 측정 10회의 결과 항목(`outcome, completed_steps, stop, stop_step, cells, endpoints_key, endpoints_scaled, effective_p`) 지문이 모두 `70897884d142404917e8f33dd6ecc6198f600d8ca7e082518c34eecc5c7bac28`이고, Vast 재계산(replay) 결과와도 같다(이 PC에서 저장된 원본 JSON을 읽어 확인). 비교 항목은 기존 검사기 `checker.FIELDS`에 `endpoints_scaled`와 `effective_p`를 더한 것.
- 새 시험(노트북에서 실행): 실제 Vast 기록 10개가 지문·검사를 통과, 결과 한 칸 변조·정밀도 재시도·대체 실행·방식 불일치·이벤트 발생을 각각 거부, 5회 미만 거부, 비율 1.25 경계, 판정 연결(겹치지 않으면 확인 / 겹치면 스스로 찾기 / 결과 다르면 거부), 봉인 번호 고정값 확인.
- 실행 순서: ① 노트북에서 새 시험 → ② 계산 없는 사전 점검(`--phase preflight`) → ③ 측정(`--phase measure`, 별도 백그라운드 작업).
- 다음 단계 차단: 사전 점검이 `TRY_HINT_FIRST / W6`가 아니면 측정하지 않는다. 결과가 하나라도 다르면 나머지를 하지 않는다.

## G. 무엇을 아직 모르는가? (이번 측정 후에도 남는 것)

- 노트북 한 대의 결과는 "이 노트북, 이 시간대"의 사실이다. 다른 CPU 일반화는 아니다.
- WSL2 가상 CPU 배치는 Windows가 정한다. Linux 안의 CPU 지정이 실제 코어 지정과 같다는 보장이 없다.
- 정식 장부 등록(검사관 서명·관리자 승인)은 하지 않는다. 판정이 "확인"이어도 기존 관리자 승인에 제출할 후보일 뿐이다.
- 교육비 절감, 관리자 전체 선택 비용, 원격 PC(SMT 있는 Ryzen 5 5600)의 경로는 이번 범위 밖.
- `RwForce` 공유·OS 격리 부재 등 기존 한계는 그대로.
