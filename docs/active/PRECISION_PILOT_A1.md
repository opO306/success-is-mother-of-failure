# PRECISION_PILOT_A1 — 원래 C_stream에서 정밀도 고르는 순서(P0–P3) 비교

상태: **결과 기록 (2026-10-05)**. 증거 수준 = 실행·독립 checker 확인(numerical validated, 이 9개 요청 범위). formal 아님.
브랜치 `codex/precision-pilot-a1`, protocol 봉인 `09d7a3d`, 코드 봉인 `25b01f6`, checker 강화 `0e49576`(아래 6절).
evaluator = **original만**(Exact Expression V1 `stream.run`, 동결 코드 수정 없음). algebra는 등록만 하고 거부(A2에서 다룸).

## 1. 무엇을 알아보려 했나 (쉬운 말)

비유: 창고에서 물건을 꺼낼 때 "몇 번 사다리"를 쓸지 고르는 문제다. 사다리가 높을수록(정밀도 p가 클수록) 한 번 올라가는 데
오래 걸리고, 너무 낮으면 물건에 못 닿아 다시 내려와 더 높은 사다리로 다시 올라가야 한다(실패 1회 = 처음부터 다시 계산).

실제 의미: 같은 초기상태를 p비트 구간산술로 T step 계산해, 관측 칸(FX 격자)이 하나로 정해지면 DECIDED, 아니면 더 큰 p로
**처음부터** 다시 계산한다. 정답 여부는 어떤 p에서 DECIDED가 나와도 같다(아래 4절 확인). 바뀌는 것은 **총 비용**뿐이다.

- P0: 기존 격자 64→96→128→192→256→384→512→768→1024 순서
- P1: 고정 시작값 110(학습 6건 최소성공의 중앙값)에서 시작, 실패하면 격자 위로
- P2: 학습 없음. 64에서 시작, 실패 구간의 폭/여유로 필요한 비트를 계산(+8), 도중 정지면 p·T/k+8
- P3: 학습 요청(T=200, 2000)으로 시나리오별 직선(필요 p ≈ a + b·T)을 그어 첫 p 추천(+8), 실패하면 P2 규칙

학습 요청(T 200/2000)과 평가 요청(T 100/1000, 3000/5000/10000)은 분리했다. 파라미터는 평가 전에 동결(`policy_hash 6d601462…`).

## 4. 정확성 확인 (비용 비교의 전제)

- 독립 checker(`experiments/precision_pilot_a1/checker.py`, 실행 측 모듈 import 없음): **EVIDENCE OK**,
  incomplete 0 / invalid 0 / conflict 0.
- 모든 pass의 칸을 저장된 정확한 구간 끝점에서 다시 계산해 일치. 요청마다 DECIDED 칸은 어떤 p·정책에서 나와도 **모두 같았다**.
- 같은 (요청, p)를 두 번 계산한 경우 결과와 끝점이 동일(결정론).
- 모든 정책의 다음 p 선택을 기록된 결과만으로 checker가 독자 구현으로 재유도해 일치. 동결 파라미터도 학습 run에서 재유도해 일치.
- 실제 사용된 정밀도(effective_p) = 요청 p, 전 pass. 비격자 p 지원 감사(65, 97, 129, 137, 193, 300, 777) PASS.
- 관측 범위 안에서 "최저 성공보다 높은 p가 실패한" 경우는 0건(모든 요청). 다만 높은 p를 전부 시도한 것은 아니므로 단조성은 증명 아님.

## 5. 해석

확인된 것(이 9개 요청, 이 3개 시나리오 범위):
- 고르는 **순서**만 바꿔도 같은 정답에 드는 CPU가 크게 달랐다. P0 대비 P3 0.24–0.52, P2 0.49–0.99, P1 0.33–0.99.
- 격자(P0)는 T가 길어질수록 낭비가 커졌다. 필요 p가 격자 사이에 있으면(예: 458) 아래 격자를 전부 실패한 뒤 위 격자(512)로 간다.
- P1(고정 110)은 필요 p가 110 근처인 경우(A3_low)만 좋고, 긴 범위의 A2/A3_high에서는 P0와 거의 같았다(0.94–0.99).
- P2(학습 없음)는 모든 요청에서 P0보다 같거나 쌌고, 긴 범위에서 일관되게 0.50–0.71이었다.
- P3는 직선 예측이 맞은 곳에서 1회에 끝나 가장 쌌다. 학습 범위(T≤2000)의 5배인 10000까지 A2_bound·A3_high는 맞았다.

반대 증거·한계:
- **P3 예측이 틀린 사례가 있다.** A3_low 10000에서 직선은 125를 추천했지만 필요 p는 (128,138]이었다. A3_low는 필요 p가
  T에 대해 직선이 아니다(94, 95, ≤104, ≤105, >128). 실패 후 P2 규칙으로 회복했고 비용은 P2와 같았다(0.51 대 0.50).
- P3의 학습 비용(준비 비용) = 학습 run 6건 CPU **187초**. 위 비율에는 들어 있지 않다. 짧은 요청 하나에서 절약은 1–44초라
  짧은 요청만이면 수 개 이상 써야 회수되고, 긴 요청 하나(예: A3_high 10000 절약 508초)면 회수된다.
- 학습과 평가는 같은 3개 시나리오의 다른 T다. 궤적 앞부분을 공유하므로 완전히 독립된 검증이 아니다. **새 시나리오에서의
  P3 성능은 시험하지 않았다(UNRESOLVED).**
- P2·P3의 +8비트 여유값, 직선 모형은 이번에 튜닝하지 않은 첫 설계값이다. 더 나은 값이 있는지 모른다.
- 참 최소를 아는 데 드는 비용(INVESTIGATE)은 서비스 비용과 별개로 컸다: 짧은 6개 요청에 CPU 2016초(전체 실험의 19%).
  예: A3_high 1000은 P0 60초 대비 1057초. 최소 증명은 비싸고, 정답을 내는 데에는 필요 없다.
- 측정 환경: 이 PC 1대, 순차 실행, 요청마다 새 프로세스. 다른 기계·동시 부하에서의 비율은 측정하지 않았다.
- 이 결과는 original evaluator에서만이다. algebra evaluator에서 같은 정책이 어떻게 되는지는 A2에서 본다(미착수).
