## 비용 구조 (추정, 측정값 두 개로 푼 값)

CPU 시간을 `블록 수 × a + 교차 수 × b`로 놓고, shell 17·18 두 실행으로 연립방정식을 풀었다.

| | 블록당 a | 교차당 b |
|---|---:|---:|
| 생성기 | 약 715 µs | 약 45 µs |
| checker | 약 671 µs | 약 256 µs |

- 식 두 개에 미지수 두 개라 오차 추정이 없다. 두 실행은 서로 다른 시각에 돌았다. **대략적인 크기로만 읽는다.**
- 실제로 흔들린다. 같은 계산의 두 번째 실행 시간으로 풀었을 때는 교차당 비용이 생성기 약 60 µs, checker 약 290 µs였다.
- shell 17은 교차가 5.5배로 늘었는데도, 블록이 적어서 생성기 시간은 오히려 약간 줄었다. **checker는 교차당 비용이 커서 CPU 시간이 35% 늘었다.**
- 이 추정을 고정 fixture의 경계 수(shell 16 약 4.7×10⁷, shell 15 약 2.5×10⁸)에 그대로 대입하면 checker CPU 시간은 이렇게 나온다. **측정이 아니라 선형 외삽이다.**
  - shell 16: 약 1.2×10⁴초
  - shell 15: 약 6.4×10⁴초
- 후보 수는 휴리스틱 예상보다 적었다(shell 18: 109/255, shell 17: 827/2,148). superblock별 상한이 shell 전체 상한보다 촘촘하기 때문이다.

## 읽는 방법과 한계

- 이 결과는 "shell 17의 모든 격자점에서 유리식 거리 > G"를 조사로 확인한 것이다. **인증이 아니다.** ④-4c-6과 같은 인증 계약으로 올릴지는 설계자가 판정한다.
- 이전 coverage 값은 driver가 숫자를 적어 두지 않고 ④-4c-6 인증서 fixture에서 읽는다. 첫 실행은 옛 값(11/64·gap 84)을 코드에 박아 두어 틀렸다. 이 실행은 `runs/c1b1_hard_case_shell17_20260928/first_run/`에만 남겼다.
- 두 번째 실행은 인증서 fixture 해시를 원래 바이트 그대로 계산했다. Windows(CRLF)와 리눅스(LF)에서 값이 달라졌고, 원격 리눅스 전체 시험이 이를 잡았다. 저장소 규칙대로 LF로 통일해 계산하도록 고친 뒤 세 번째로 실행했다. 두 번째 실행은 `second_run/`에 남겼다. 세 실행의 결정적 결과(행·비용표·대조·교차·후보·hazard)는 모두 같다.
- `rows_sha256`는 행별 실행 시간까지 해시에 넣는다. 그래서 같은 계산이라도 실행마다 값이 다르다(첫 실행과 재실행에서 다름). 저장된 superblock 1024행 자체는 두 실행에서 완전히 같다. shell 18 조사 driver에서 물려받은 결함이며, 그 driver는 fixture가 소스 해시를 고정하고 있어 이번에 고치지 않았다.
- checker는 동결 P/Q 항등식과 기존 guard를 공유한다. 새 독립 물리 감사가 아니다.
