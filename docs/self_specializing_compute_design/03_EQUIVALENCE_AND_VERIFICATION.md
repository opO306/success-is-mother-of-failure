# 03. 동등성과 검증

## 1. 가장 먼저 정해야 할 것

"원본과 같은 결과"라는 말은 컴퓨터에서는 하나의 의미가 아니다.

다음 수준을 분리한다.

---

## 2. 동등성 수준

### E0 — 수학적 실수 동등성

예:

```text
(a+b)^2
=
a^2 + 2ab + b^2
```

실수 수학에서는 같다.

하지만 실제 부동소수점 계산 결과는 다를 수 있다.

용도:
- 순수 수학 변형
- 상징 계산

---

### E1 — 허용 오차 동등성

```text
|F(x) - G(x)| <= ε
```

근사 계산에 적합하다.

예:
- 그래픽
- ML inference
- 일부 과학 계산

이 프로젝트의 엄격 모드에서는 기본값으로 사용하지 않는다.

---

### E2 — 관측 가능한 결과 동등성

프로그램 외부에서 관측 가능한 상태가 동일하면 허용한다.

예:
- 내부 레지스터 배치는 다름
- 계산 순서는 다름
- 최종 출력과 외부 상태는 같음

컴파일러 최적화에서 중요한 개념이다.

---

### E3 — 타입 규칙 하에서 정확한 값 동등성

정수, modular arithmetic, fixed-point 등에서 정확한 결과가 동일하다.

예:

```text
uint32
```

라면 2^32 모듈러 연산 규칙까지 포함한다.

---

### E4 — 비트 동일성

입력 비트가 같으면 출력 비트도 완전히 같아야 한다.

```text
bits(F(x)) == bits(G(x))
```

가장 엄격한 수준 중 하나다.

---

### E5 — 실행 흔적까지 동일

필요하다면 다음까지 같게 요구할 수 있다.

- 예외 발생 여부
- overflow flag
- NaN behavior
- signed zero
- event ordering
- observable memory writes

다만 너무 강한 기준은 가능한 최적화를 크게 줄인다.

---

## 3. 부동소수점이 어려운 이유

실수 수학에서는:

```text
(a+b)+c = a+(b+c)
```

지만 floating point에서는 중간 반올림 때문에 다를 수 있다.

또한 다음이 문제다.

- NaN
- +0 / -0
- infinity
- denormal/subnormal
- rounding mode
- fused multiply-add
- exception flag

따라서 부동소수점 최적화에서 "대수적으로 같음"만으로는 부족하다.

---

## 4. 권장 초기 정책

첫 프로토타입은 다음 순서를 권장한다.

### 단계 A
- unsigned integer
- signed integer
- bit-vector

### 단계 B
- fixed-point

### 단계 C
- exact rational

### 단계 D
- IEEE-754 strict subset

이유는 정수와 bit-vector가 SMT 검증에 훨씬 다루기 쉽기 때문이다.

---

## 5. 검증 방식

### 5.1 Exhaustive Verification

입력 공간이 작다면 모든 입력을 넣는다.

예:

```text
uint8 x, uint8 y
```

가능한 조합:

```text
256 × 256 = 65,536
```

모두 검사 가능하다.

장점:
- 단순함
- 강력함

단점:
- 입력 폭이 커지면 폭발

---

### 5.2 SMT / SAT

원본과 후보가 다르다고 가정한다.

```text
F(x) != G(x)
```

이를 만족하는 x가 있는지 solver에 묻는다.

- SAT: 반례 존재
- UNSAT: 지정한 의미론 아래 동등

---

### 5.3 Symbolic Execution

입력을 구체적인 값 대신 기호로 유지한다.

```text
x = symbolic
```

계산 전체를 기호식으로 추적한다.

---

### 5.4 Translation Validation

컴파일러 자체를 전부 증명하는 대신, 각 변환 결과마다:

```text
원본
vs
최적화 결과
```

를 검사한다.

이 시스템과 특히 잘 맞는 방식이다.

---

## 6. 후보 채택 규칙

권장 규칙:

```text
후보 생성
   ↓
정적 검증
   ↓
통과?
 ┌─┴─┐
NO  YES
│     ↓
폐기  성능 측정
        ↓
     실제로 더 좋은가?
      ┌────┴────┐
     NO        YES
     │           ↓
    폐기        채택
```

즉:

> 빠르지만 증명 안 됨 → 폐기  
> 증명되지만 느림 → 폐기  
> 증명되고 빠름 → 채택

---

## 7. 증명 범위 계약

전체 입력 공간이 아니라 특정 범위에서만 동등한 후보도 존재할 수 있다.

예:

```text
0 <= x <= 1000
```

에서만 G가 F와 정확히 같다면:

```text
candidate:
  domain: [0, 1000]
```

을 명시한다.

런타임은 반드시 이 조건을 검사하고, 범위를 벗어나면 원본 계산으로 돌아간다.

---

## 8. 검증기 자체 검증

검증기가 틀리면 시스템 전체가 무너진다.

따라서:

- verifier는 가능한 작게 만든다.
- 다중 검증기를 사용할 수 있다.
- 랜덤 differential test를 추가한다.
- proof artifact를 저장한다.
- solver 버전과 설정을 기록한다.
- 검증 결과를 재현 가능하게 만든다.

---

## 9. 적용 시 중요한 교훈

최적화 탐색은 공격적으로 해도 된다.

검증은 보수적으로 해야 한다.

이 둘을 섞으면 안 된다.
