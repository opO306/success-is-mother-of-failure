# [제안서 — 후보] A 실행 증명서 (run-time certificate)

**상태: 장기 후보. 구현·동결 아님.** (설계자 18판 대화, 2026-09-26) 근거: C1-B1 설계 문서 17·18절 — "모든 초기 상태를 한 번에 증명"이 안쪽(R < 20 bohr)에서
어렵다는 문제에 대한 다른 방향.

## 생각

- 전역 증명(모든 E, b에 대해 미리 한 번에) 대신, **실제로 들어온 한 궤적을 따라가며** 걸음마다 힘·반올림·오차의 enclosure를 계산하고 누적 오차 상한을
  증명서로 함께 낸다. 끝에서 누적 상한 ≤ 목표이면 **그 실행은 certified**.
- A는 결정론이므로 `초기 상태 + 실행기 계약 + 증명서`로 언제든 재검증할 수 있다.
- 계층: **Proof Atom**(한 걸음: 입력·출력 범위, 반올림 판정, 국소 오차) → **Proof Segment**(여러 걸음 요약: 누적 오차, 증폭 상한) → **Proof Box**(초기 조건
  범위 전체) → **Proof Domain**(Box의 합). 실행 증명(Run Certificate)이 쌓이면 상태 공간을 Box로 묶어 domain 증명으로 승격할 수 있다.
- 증명 못 하면 정밀도를 올리고, 그래도 안 되면 exact/reference fallback — 어려운 상태만 비싸진다.
- **실행기 ≠ 검증기.** 검증기는 작고 단순하고 정확 산술 중심이며 거의 바뀌지 않는다. 실행기 버그를 검증기가 잡아야 한다.

## 원칙

- 형식(증명서를 담는 표현)은 우리가 설계해도 되지만, **근거는 검증 가능한 수학**(구간 산술, 정확한 반올림, 부등식, 보존량)이어야 한다. "대충 맞으면 증명" 규칙 금지.
- Run certificate는 **그 실행**에 대한 것이다 — "R < 20 모든 상태가 certified"와 다르다. Box/Domain 승격은 별도 증명이 필요하다.

## 열린 질문 (구현 전)

- 걸음마다 증명서를 만드는 비용(힘 평가가 이미 병목), Segment 요약 방법, 되먹임(증폭) 상한을 실행 중 어떻게 계산하는가.
- 비교 대상 정의: "같은 적분기의 반올림 없는 궤적"과의 차이를 한 실행에서 bound하려면 그 궤적의 enclosure도 함께 추적해야 한다.
- 독립 검증기의 범위와 코드 공유 금지 규칙(`audit/`와 같은 원칙).
