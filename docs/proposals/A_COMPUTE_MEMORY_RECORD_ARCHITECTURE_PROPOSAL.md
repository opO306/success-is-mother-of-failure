# [제안서 — 후보] A 세계 계산·메모리·기록 아키텍처

**상태: 장기 계산 아키텍처 제안서. 구현·동결 단계 아님.** (설계자 대화 2026-09-26 정리 + 검토 반영)
이 문서의 어떤 항목도 물리 규칙이나 실행 계약으로 동결하지 않는다. 구현 우선순위는 C1-B1이다 — scheduler·region·학습 관리자 구현은
이 문서를 근거로 시작하지 않는다.

## 0. 현재 우선순위 (먼저 읽을 것)

- **이 문서 대부분은 C2 이후의 장기 후보다.** 지금 A는 두 원자(C1-B1) 단계다.
- **현재 실측 병목은 scheduling·상태 갱신이 아니라 정확 반올림 힘 평가다.** C1-B1 한 걸음(설계 문서 9.2·11절): CPU 약 500 µs 중 상태 갱신
  (drift·Δr·R²·킥)은 약 0.05%, 나머지는 C1-A F(R)의 정확 반올림 평가. GPU 한 걸음 약 2 µs도 같은 구조.
- **가까운 최적화 후보: 검증 가능한 fast path + exact fallback** (6절).

## 1. 문제: 계산량과 저장량은 같이 폭발한다

- A가 커질수록 동시에 관리할 상태 수가 폭발하고, 미시 물리를 직접 계산하면 한 영역만으로도 계산량이 빠르게 늘어난다.
- 검증·재현·원인 분석에는 현재 상태뿐 아니라 과거도 필요하다 — 계산 문제와 저장 문제는 분리되어 있지 않다.
- 목표는 더 좋은 하드웨어가 아니라 **필요한 계산만, 필요한 장치에서, 결과를 바꾸지 않는 방식으로** 수행하도록 조율하는 구조다.

## 2. 하드웨어 역할 (로컬 · 원격)

로컬(Ryzen 5 5600 6코어 12스레드, RTX 4060 8GB)은 개발·짧은 smoke test·분석, 원격 노드는 전체 회귀·장시간 궤적·정밀도 sweep·독립 감사·
다중 world 실행. 로컬 UI와 계산 자원이 서로 싸우지 않게 하는 것이 목적이다. (클라우드 vCPU는 보통 하드웨어 스레드 단위 — 물리 코어 수와 다를 수 있다.)

## 3. CPU와 GPU

- GPU는 같은 종류의 계산을 대량으로 동시에 할 때 강하다. **GPU를 한 개의 빠른 CPU처럼 직렬로 쓰지 않는다.**
- **시간축 바깥은 직렬, 각 step 내부는 최대한 병렬.** 두 원자처럼 작업이 작으면 GPU 호출 오버헤드가 계산보다 클 수 있고, 다입자·다world·
  다region에서 이점이 커진다.
- CPU: 복잡한 판단, 분할, 정밀도 결정, 분기 많은 계산, 예외·실패 복구, 장치 선택, 검증 조율. GPU: 대량 반복·독립 동일 계산.
- 하위 계층이 다시 일을 나눌 수 있으나(Global → Region → Batch → Thread), 계층마다 전달·동기화·복사·디버깅 비용이 붙는다 — **계층 수가 아니라
  각 단계가 충분히 큰 작업 단위를 넘기는 것**이 중요하다. 기술적으로는 Task Graph(입력·출력·선행 조건·예상 비용·장치 선호·메모리·fallback)로 본다.

## 4. 가상 계산 단위(Software Core) · sleep · 적응 해상도 — 후보

- 수백만 개의 가상 작업자(상태는 RAM/SSD, 실제 계산은 필요한 것만 CPU/GPU)는 **계산 능력을 늘리는 것이 아니라 불필요한 계산을 하지 않게
  관리하는 구조**다.
- event-driven(사건이 있을 때만 깨움), region별 해상도(MACRO / MESO / MICRO / SLEEP)는 후보다. **단 아래 7절의 규칙 조건을 만족할 때만.**
- 거시↔미시 전환은 **미해결 연구 문제**다(8절).

## 5. 결정론적 재생 — 기록 구조의 기본 원칙

### 5.1 authoritative history의 정의

**세계의 역사(authoritative history) = snapshot + 모든 외부 입력 + 재생에 필요한 실행기·계약 식별 정보.**

- snapshot: 어느 시점의 정규화한 세계 상태 전체.
- 모든 외부 입력: 세계 밖에서 들어온 것 전부(선언된 탐침을 통한 B의 행동 의도, 설계자가 넣은 외부 에너지 등 — 외부 에너지 장부와 같은 기록).
- 실행기·계약 식별: 계약 판(예: `c1b1-two-atom-v2`), 매개변수 지문, 수 profile, 기준 실행기 코드 해시·커밋.

**조건:** 동일 snapshot과 동일 외부 입력에서 **기준 실행기가 동일한 bit history를 재생**할 수 있어야 한다. 이것은 이미 규칙이다(결정론,
기준 실행기 영구 유지, CPU = GPU = 모든 실행기 비트 동일). 재생에 필요한 옛 실행기 판은 보존한다.

### 5.2 나머지 기록의 격

**event log, 특이 사건 기록, ring buffer는 역사를 보존하기 위한 필수 데이터가 아니다.** 검색·분석·재계산 시간 단축을 위한 **파생 index/cache**다.
언제든 authoritative history로부터 다시 만들 수 있고, 잃어도 역사는 잃지 않는다. 따라서:

- "모든 미시 사건을 영구 기록할 수 없다"는 문제는 **정보 손실 문제가 아니다.** 어느 시점이든 가장 가까운 snapshot에서 재생하면 전체 미시
  해상도로 복원된다.
- 특이 사건을 **나중에** 발견해도 그 이전 과정을 완벽하게 볼 수 있다 — 사건 전 구간을 미리 보관해 둘 필요가 없다.
- 기록 해상도를 영역마다 다르게 하는 것(적응 기록)은 **분석 편의**이며 정확성과 무관하다.

### 5.3 snapshot 간격

snapshot 간격은 정보 손실의 문제가 아니라 **저장 공간과 replay 계산 시간의 trade-off**다. 간격이 길면 저장이 줄고 특정 시점 복원에 재계산이
길어진다. 예: 이벤트 하나 32바이트 기준 초당 10⁶건이면 시간당 약 115 GB — 이런 기록은 파생 cache로만 두고 필요한 구간만 재생해 만든다.

### 5.4 선택적 replay cache (옛 ring buffer)

최근 구간의 상세 상태를 잠시 들고 있는 ring buffer는 **선택적 replay cache**로 남긴다. 정확성이나 역사 보존에는 필요 없고, 최근 구간 재분석 시간을
줄이는 용도로만 가치가 있다. 크기·보관 기간은 비용 최적화 문제다.

### 5.5 메모리 계층

VRAM = 지금 계산하는 작업대, RAM = 현재·근접 상태와 cache, SSD = 최근 snapshot·외부 입력·파생 index, HDD = 장기 archive(snapshot·입력·실행기 판).
세계 전체 크기와 동시에 계산해야 하는 크기를 분리한다. 가상 VRAM(Unified Memory·oversubscription)은 용량 확장이지 성능 확장이 아니다
(PCIe·page migration).

## 6. 가까운 최적화 후보: 검증 가능한 fast path + exact fallback

현재 병목(정확 반올림 힘 평가)에 직접 닿는 후보. **결과 계약을 바꾸지 않는다.**

- fast path: 싼 산술(예: 좁은 구간 산술, 고정 정밀도)로 enclosure를 만들고, **그 enclosure가 하나의 반올림 값으로 결정되면 그 값을 확정**한다.
- exact fallback: fast path가 **최종 결과 bit를 확정할 수 없는 입력만** 기존 exact/high-precision 경로(정밀도를 올려 가며 판정, 못 정하면 거부)로 보낸다.
- 두 경로의 결과 계약은 **동일**하다 — 같은 입력에 같은 bit, 같은 거부. fast path는 "대략 맞는 값"을 내지 않는다.
- 채택 조건: 기준 실행기와 차등 검사(모든 fixture·어려운 입력·경계 사례에서 비트 동일), fast path가 확정하는 비율과 절감 시간 실측, 결함 주입으로
  "fast path가 틀린 값을 확정"하는 결함을 잡는지 확인.

## 7. RULES 호환성

|---|---|---|
| sleep / event-driven | 계산 절약을 이유로 인과를 삭제하지 않는다(과정 보존) | **"변화가 적어 보인다"는 이유로 계산을 생략할 수 없다.** 생략한 구간의 결과를 **정확히 계산**하거나(예: 해석해가 정확한 경우) **결과 동등성이 증명**된 경우에만 허용. 깨우는 시점·관측 간격이 결과를 바꾸면 안 된다(v5 연속 시간). |
| Region | 칸이 물리를 결정하면 안 된다, 물리와 실행 기술의 분리 | **Region은 계산·공간 색인일 뿐 물리 경계가 아니며 물리 결과를 결정해서는 안 된다.** region 분할을 바꿔도 결과가 비트 동일해야 한다. |
| "신기한 사건" 탐지 | "녹았다"·"쪼개졌다"는 관찰자의 해석, 기록기를 켜고 끈 결과가 같아야 한다, B는 선언된 감각·탐침으로만 | **A 외부의 관찰·기록 계층에만 존재**한다. A의 상태 전이에 영향을 주지 않고, B가 관측할 수 있는 정보에도 들어가지 않는다. |
| 캐시·요약 | 캐시는 인과 영향 반경 전체의 정확한 입력이 같을 때만, 손실 요약은 증명 전 금지 | 5.2의 파생 index/cache는 역사에서 다시 만들 수 있는 것만. 계산 결과 캐시는 기존 규칙 그대로. |
| 학습형 관리자 | 외부 분석기는 제안만, 채택은 차등 검사 + 설계자 승인 | 9절. |
| 모든 최적화 | 기준 실행기와 정규화 상태 + 사건 이력 + 인과 결과가 정확히 같아야 채택, 끌 수 있어야 함 | 공통 전제. |

## 8. 거시↔미시 전환 — 미해결 연구 문제

- 미시 → 거시 요약에서 정보가 소실되면, 거시 → 미시로 되돌릴 때 **존재하지 않았던 미시 상태를 만들어야 한다.** 그 순간 물리를 지어내는 것이다.
- 따라서 **현재는 허용된 최적화로 취급하지 않는다.** 무손실 변환 또는 결과 동등성이 증명된 변환이 나오기 전에는 **후보 연구 항목**으로만 둔다.
- 설계자 원칙(이전 대화): 거시 계산은 미시 계산의 대체물이 아니라 **검증된 압축 표현**이며, 오차를 보장할 수 없으면 쓰지 않는다. 해상도는 카메라가
  아니라 물리적 필요성이 정한다. 이 원칙을 만족하는 구체적 방법은 아직 없다.

## 9. 학습형 계산 관리자 — 권한 제한

학습 관리자는 **물리 결과를 결정하는 판사가 아니라 계산 방법을 고르는 작업 관리자**다.

- **최종 결과 bit를 바꾸지 않는 실행 전략만** 선택할 수 있다. 예: CPU/GPU 선택(실행기 비트 동일이 이미 강제됨), batch 크기, 시작 정밀도(판정 결과는
  시작 정밀도와 무관 — 결정된 반올림 값은 하나), 메모리 배치·residency, 작업 순서(결과가 순서와 무관함이 증명된 곳).
- **허용하지 않는 것:** "오차 한계 안이면 계산 생략", 결과를 근사하는 선택, **검증 시험 자체를 줄여 통과 여부를 결정하는 선택**.
- 관리자의 선택이 결과를 바꾸지 않는다는 것은 기준 실행기와의 차등 검사로 확인한다.

## 10. 전체 구조 초안 (후보)

```text
[Global Compute Manager] ── 실행 전략만 선택(9절)
   ├─ [World / Region Graph]  (region = 색인, 7절)
   │     └─ [Task Graph Scheduler] → CPU(고정밀·분기) / GPU(대량 병렬)
   │                                   └─ 힘 평가: fast path + exact fallback(6절)
   └─ [History Manager]
         ├─ authoritative: snapshot + 외부 입력 + 실행기·계약 식별(5.1)
         └─ 파생: event index, 특이 사건 index, replay cache(5.2·5.4)
[RAM cache] → [SSD store] → [HDD archive]
```

## 11. 확정 설계로 보면 안 되는 것

Software Core 상태 구조, region 경계 정의, sleep/wake 조건, event-driven scheduler, 학습 관리자, 거시↔미시 전환 정책, 이상 사건 판정 기준,
파생 기록 반경, snapshot 주기, replay cache 크기, RAM/VRAM residency, archive 정책, Task Graph 깊이 — 전부 후보. 작은 synthetic workload와
실제 A workload로 측정하기 전에는 결정하지 않는다.

## 12. 나중에 검증할 질문

- 계산: region 수에 따른 scheduler overhead, 가상 작업자 상태 크기, 정확한 sleep이 가능한 경우가 실제로 얼마나 되는가, CPU/GPU 분배 경계, GPU batch
  크기, 원격 다중 vCPU scaling, **fast path가 확정하는 입력 비율**.
- 메모리: VRAM resident 필수 상태, RAM↔VRAM 이동 비용 비율, SSD staging 현실성, thrashing.
- 기록: snapshot 간격별 저장량 대 replay 시간, 외부 입력 기록의 최소 표현, 실행기 판 보존 비용, 파생 index 재생성 비용.

## 13. 한 문장

A의 계산 시스템은 세계 전체를 계속 같은 정밀도로 돌리는 기계가 아니라, **결과 bit를 바꾸지 않는 범위에서** 필요한 곳만 적절한 장치·정밀도로 계산하고,
역사는 **snapshot + 외부 입력 + 실행기 식별**로 무손실 보존하며 나머지 기록은 재생으로 다시 만들 수 있는 파생물로 다루는 구조를 지향한다.
