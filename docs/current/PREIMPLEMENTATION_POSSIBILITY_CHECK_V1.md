# 0. 한 문장 정의

> **새 물리를 구현하기 전에 “우리가 예시 하나를 전체 법칙으로 착각하고 있지 않은가?”를 먼저 검사한다.**

이 문서의 목적은 정답을 미리 만드는 것이 아니다.

오히려:

```text
가능한 결과를 먼저 넓게 생각하고
↓
그 결과들을 갈라놓는 실제 물리 정보가 무엇인지 찾고
↓
정보가 부족하면 임의로 결정하지 않고
↓
필요한 자유도를 설계하는 것
```

이다.

---

# 1. 이 문서가 생긴 이유

처음 3개 입자가 한 칸에 모이는 문제를 봤을 때 다음 해결책이 제안됐다.

```text
3개가 모이면
→ 둘씩 골라서 순서대로 처리
```

처음에는 안전해 보였다.

그러나 이 방식에는 숨은 가정이 있었다.

> **모든 다체 상호작용은 어떤 순서의 2체 상호작용으로 환원된다.**

이것은 구현 편의가 아니라 세계 법칙이다.

여기서 설계자가 한 질문이 중요했다.

> **“방에 세 사람이 들어오면 꼭 둘씩 악수해야 하나? 셋이 같이 인사할 수도 있지 않나?”**

이 질문 하나가 문제를 다시 열었다.

가능한 상황은 실제로 훨씬 많다.

```text
셋이 동시에 인사
A와 B만 악수
C는 지나감
A가 B와 C에게 각각 손을 내밂
둘이 부딪힘
셋이 모두 아무 반응 없이 지나감
셋이 함께 해야만 가능한 행동 발생
```

중요한 것은 이 중 하나를 사람이 고르는 것이 아니다.

**어떤 결과가 가능한지는 현재 물리 상태와 선언된 법칙이 결정해야 한다.**

---

# 2. 핵심 철학

새 기능을 볼 때 가장 먼저 물어야 할 것은:

> “무엇을 구현할까?”

가 아니다.

먼저:

> **“이 상황에서 어떤 결과들이 원칙적으로 가능할까?”**

를 묻는다.

그리고 다음 질문으로 넘어간다.

> **“그 결과들이 갈리는 이유는 무엇인가?”**

그 답이 다음과 같아야 한다.

- 실제 위치
- 접촉
- 방향
- 기하
- 사용 가능한 포트
- 에너지
- 운동량
- 물질 종류
- 기존 결합
- 공간 여유
- 도착 시점/위상
- 선언된 물리 법칙

반대로 답이 다음이라면 문제 신호다.

- particle ID
- 배열 순서
- JSON 작성 순서
- thread 실행 순서
- 먼저 순회된 항목
- 사람이 편하게 정한 최대 길이
- `if N == 3`
- 테스트를 통과시키기 위해 추가한 예외

# 3. 5문장 검사

새로운 상호작용을 구현하기 전에 아래 다섯 문장에 답한다.

---

## 질문 1 — 무엇이 실제로 존재하는가?

> **현재 세계 상태에 실제로 존재하는 물리 정보는 무엇인가?**

사람 비유:

```text
세 사람이 방에 있다.
```

그런데 이 한 문장만으로는 부족하다.

우리가 실제로 알고 있는 것은 무엇인가?

```text
각자의 위치
어느 방향을 보고 있는지
손이 몇 개인지
누가 누구와 가까운지
누가 움직이는지
누가 먼저 들어왔는지
```

A에서도 같다.

예:

```text
입자 A, B, C
```

만으로는 부족하다.

현재 표현되는 정보:

```text
kind
position
direction
orientation
ports
energy
momentum
existing bonds
```

등을 먼저 적는다.

### 목적

**존재하지 않는 정보를 코드가 몰래 사용하지 못하게 한다.**

예:

```text
particle_id
```

가 단지 식별자라면 물리 결정에 사용하면 안 된다.

---

# 4. 질문 2 — 어떤 결과들이 물리적으로 가능할 수 있는가?

> **현재 상황에서 결과를 하나로 미리 좁히지 말고 가능한 후보들을 먼저 펼친다.**

사람 비유:

세 사람이 만났다고 해서:

```text
둘씩 악수
```

만 있는 게 아니다.

가능한 후보:

```text
셋이 동시에 인사
A-B 악수, C 통과
A-C 악수, B 통과
A가 양손으로 B와 C에게 동시에 악수
셋 다 그냥 지나감
부딪혀 방향 변경
셋이 함께 해야 하는 집단 행동
```

A 물리 예:

```text
A → B ← C
```

가능한 결과 후보:

```text
A-B만 결합
B-C만 결합
A-B와 B-C가 동시에 결합
아무 결합도 없음
충돌만 발생
임시 중간 구조가 생겼다가 분리
```

### 목적

**예시 하나를 물리 법칙 전체로 착각하지 않는다.**

---

# 5. 질문 3 — 그중 서로 동시에 가능한 것은 무엇인가?

> **가능한 변화 여러 개가 같은 자원을 서로 침범하지 않는다면 동시에 일어날 수 있는지 검사한다.**

사람 비유:

B에게 두 손이 있다.

```text
왼손 → A
오른손 → C
```

라면 A와 C에게 동시에 악수할 수 있다.

하지만:

```text
왼손 하나
```

만 있는데 A와 C가 둘 다 그 손을 잡으려 한다면 둘을 동시에 할 수 없다.

A 물리에서 같은 문제:

```text
A.E ↔ B.W
B.E ↔ C.W
```

는 서로 다른 B 포트를 사용한다면 동시에 가능할 수 있다.

반면:

```text
A.E ↔ B.W
C.E ↔ B.W
```

는 같은 `B.W` 포트를 동시에 사용하므로 충돌한다.

### 같이 검사할 자원

- 같은 포트
- 같은 물질
- 같은 에너지
- 같은 운동량
- 같은 공간
- 동일한 결합 슬롯
- 보존 법칙

### 목적

**동시 가능한 사건을 구현 순서 때문에 억지로 순차화하지 않는다.**

---

# 6. 질문 4 — 둘 다 가능하지만 하나만 일어나야 한다면 무엇이 그것을 결정하는가?

> **경합이 생겼을 때 승자를 고르는 실제 물리 정보가 무엇인지 묻는다.**

사람 비유:

```text
A → X ← B
```

A와 B 둘 다 X의 손 하나를 잡으려 한다.

둘 다 조건이 똑같다면:

```text
A가 이름이 가나다순으로 앞서니까 A 승리
```

는 말이 안 된다.

실제 결과를 결정하려면 예를 들어:

```text
누가 먼저 닿았는가
누가 더 가까운가
상대 속도가 얼마인가
접촉 위치가 어디인가
```

같은 정보가 필요할 수 있다.

A에서도 같다.

금지되는 결정:

```text
particle_id가 작은 쪽
배열 앞쪽
먼저 순회된 rule
먼저 실행된 GPU thread
```

허용되는 결정:

```text
실제 도착 위상
기하
거리
접촉 방향
에너지
운동량
선언된 물성
```

### 목적

**tie-break를 만드는 것이 아니라, tie가 왜 생겼는지 찾는다.**

---

# 7. 질문 5 — 그 답이 ID나 순서라면 어떤 물리 정보가 빠졌는가?

> **임의 순서가 필요해졌다면 현재 상태 표현이 무엇을 잃어버렸는지 찾는다.**

이 질문이 가장 중요하다.

causal v2에서 실제로 발생한 문제:

```text
ports: 4
```

라고 했지만 네 개 포트를 구별할 정보가 없었다.

그래서:

```text
여러 멤버가 모두 결합 가능
↓
누구에게 붙을지 결정 불가
↓
sorted(members)
↓
낮은 ID가 승리
```

가 됐다.

문제의 진짜 원인은:

```text
tie-break 알고리즘 부족
```

이 아니었다.

진짜 원인:

```text
물리 자유도 부족
```

이었다.

그래서 causal v3에서:

```text
ports: ["N", "E", "S", "W"]
```

를 만들었다.

### 앞으로 부족할 수 있는 정보 예시

- sub-cell position
- arrival phase
- contact point
- relative angle
- body-relative orientation
- rotational state
- local deformation
- structure-level momentum
- 실제 접촉면

### 목적

**결정 불가능을 실패가 아니라 모델의 정보 부족 신호로 사용한다.**

---

# 8. 5문장 검사의 전체 흐름

```text
[1] 무엇이 실제로 존재하는가?
        ↓
[2] 어떤 결과들이 가능할 수 있는가?
        ↓
[3] 어떤 결과들은 동시에 가능한가?
        ↓
[4] 하나만 가능하다면 무엇이 결정하는가?
        ↓
[5] 그 답이 비물리 정보라면 무엇이 빠졌는가?
        ↓
필요한 자유도 / 명세 / 검증 설계
        ↓
그 다음에 구현
```

---

# 9. 가장 중요한 금지 패턴

다음 형태가 나오면 구현을 멈추고 다시 검사한다.

## 9.1 participant count switch

```python
if len(group) == 3:
    ...
```

특별한 물리 근거 없이 참가자 수가 법칙 선택 스위치가 되면 경고.

---

## 9.2 ID tie-break

```python
winner = min(particles, key=lambda p: p.id)
```

ID가 이름표라면 물리 결과를 결정해서는 안 된다.

---

## 9.3 loop-order physics

```python
for item in sorted(items):
    if possible(item):
        apply(item)
        break
```

이 결과가 순서를 바꾸면 달라지는지 반드시 검사한다.

---

## 9.4 arbitrary structural ceiling

```python
if chain_length >= 3:
    stop_growth()
```

이 제한이 실제 물리 조건에서 나온 것이 아니라면 금지.

---

## 9.5 forced pairwise decomposition

```text
A, B, C가 동시에 존재
→ A-B 먼저
→ 그 결과로 B-C 검사
```

순서가 결과를 바꾼다면 이 분해는 물리 법칙을 새로 만든 것이다.

---

## 9.6 premature high-level event

```text
MUTATE()
REPLICATE()
GROW_CHAIN()
CATALYZE()
```

고수준 결과를 명령으로 직접 넣지 않는다.

가능하면 낮은 수준의 물리 과정에서 결과가 나오게 한다.

---

# 10. 사람 비유를 이용한 설계법

복잡한 물리 설계가 감이 안 올 때 해당 상황을 사람으로 바꾼다.

예:

```text
입자 세 개가 만난다
```

를:

```text
세 사람이 방에 들어온다
```

로 바꾼다.

그 다음 묻는다.

### A. 우리가 결과를 하나로 고정하고 있나?

```text
"둘씩 악수한다"
```

라고 바로 정했는가?

다른 가능성은?

---

### B. 동시에 가능한 행동이 있는가?

```text
한 사람이 양손으로 두 사람과 동시에 악수
```

같은 게 가능한가?

---

### C. 같은 자원을 두 번 쓰고 있나?

```text
한 손으로 두 사람과 서로 다른 악수를 동시에
```

하려는 건 아닌가?

---

### D. 승자를 이름으로 정하고 있나?

```text
이름이 빠른 사람 우선
```

같은 규칙을 넣고 있지 않은가?

---

### E. 실제 필요한 정보가 빠졌나?

```text
거리
도착 시간
손 위치
몸 방향
```

등이 빠져 있어서 선택을 못 하는 것은 아닌가?

# 11. A 물리 예시 1 — A-B-C 동시 결합

상황:

```text
A → B ← C
```

B는:

```text
W 포트
E 포트
```

둘 다 비어 있다.

A는 B의 W 쪽에서 접근하고,
C는 B의 E 쪽에서 접근한다.

5문장 검사:

### 1. 무엇이 존재?

```text
A, B, C
각 위치
각 포트
각 에너지
```

### 2. 가능한 결과?

```text
A-B
B-C
둘 다
아무것도 없음
```

### 3. 동시 가능?

A-B는 `B.W`, B-C는 `B.E`를 사용.

같은 포트를 먹지 않는다.

에너지/보존 조건도 함께 만족한다면:

```text
둘 다 동시에 가능
```

### 4. 하나만 골라야 하나?

아니다.

### 결론

```text
A-B-C
```

가 한 local update에서 만들어질 수 있다.

`THREE_BODY_BIND` 명령은 필요 없다.

---

# 12. A 물리 예시 2 — 한 포트를 두 입자가 노림

상황:

```text
A → X ← B
```

X의 사용 가능한 포트가 하나뿐이다.

### 가능한 결과

```text
A-X
B-X
```

둘 다 개별적으로는 합법.

하지만 동시에 불가능.

### 질문

누가 이기는가?

현재 상태에:

```text
정확한 도착 시간
sub-tick phase
상세 접촉 위치
```

가 없다면 답할 수 없다.

### 잘못된 해결

```text
낮은 ID 승리
```

### 올바른 처리

```text
contested
→ 현재 물리 정보 부족 보고
→ 필요한 자유도 후보 탐색
```

# 13. A 물리 예시 3 — 변이

예상 경로:

```text
A-B-C
```

그런데 X가 도착한다.

가능한 결과:

```text
A-B-C
A-B-X
A-B + C
다른 방향 구조
아무 결합도 없음
```

`MUTATE()`는 필요 없다.

5문장 검사를 통해 각 결과를 갈라놓는:

```text
도착 위치
포트 경쟁
충돌 에너지
기하
결합 상태
```

를 표현하면 된다.

---

# 14. A 물리 예시 4 — 촉매

잘못된 질문:

> 촉매니까 반드시 세 입자가 동시에 충돌해야 하나?

더 좋은 질문:

> 현재 국소 상태에서 어떤 상호작용 경로들이 가능한가?

가능한 경로:

```text
C + A   → C-A
C-A + B → C-A-B
C-A-B   → C + A-B
```

혹은 실제 물리가 필요하다면 여러 참가자가 동시에 맞아야 하는 전이 상태도 있을 수 있다.

따라서:

```text
항상 pairwise
```

도 미리 정하지 않고,

```text
항상 N-body
```

도 미리 정하지 않는다.

# 15. “가능성을 열어둔다”의 의미

가능성을 열어둔다는 것은:

> 모든 결과를 무조건 허용한다

는 뜻이 아니다.

정확히는:

> **결과를 막는 이유가 실제 현재 상태와 명시된 물리 법칙에서 나와야 한다.**

허용되는 제한:

```text
포트 부족

에너지 부족
기하 불일치
물질 불일치

```

의심해야 할 제한:

```text
길이 3이라서

ID가 커서
목록 뒤에 있어서
코드에서 break를 만나서
```

# 16. “모든 가능성을 구현”하려는 것도 금지

이 검사법은 모든 상상 가능한 현상을 한 번에 구현하라는 뜻이 아니다.

예:

```text
회전
탄성 변형
전자기
sub-cell geometry
각운동량
N-body hyperedge
```

를 당장 모두 넣으면 복잡도만 폭발한다.

원칙:

> **현재 발견된 모호성을 해결하는 데 필요한 최소 자유도부터 추가한다.**

예:

ID 경합의 원인이 포트 구별 불가였다.

따라서 바로 sub-cell 물리를 만들지 않고:

```text
named ports + adjacent cells
```

를 먼저 선택했다.

# 20. 기존 원칙 문서와의 관계


# 21. MINIMAL_LOCAL_GEOMETRY와의 관계

`MINIMAL_LOCAL_GEOMETRY_V1.md`는 실제 사례다.

과거:

```text
ports: 4
```

만 존재.

5문장 검사로 보면:

```text
여러 결합 후보 존재
↓
하나만 선택해야 함
↓
왜 하나인가?
↓
ID가 결정
↓
물리 정보 부족
↓
포트를 구별할 geometry 필요
```

그래서:

```text
ports: ["N", "E", "S", "W"]
adjacent_cells
```

가 만들어졌다.

즉 `MINIMAL_LOCAL_GEOMETRY_V1`은 이 검사법을 적용한 첫 실제 사례 중 하나다.

# 23. 상태를 더 추가해야 하는 시점

다음 신호가 반복되면 새로운 물리 상태 변수를 검토한다.

- 동일한 물리 상태에서 여러 결과가 남음
- 결과가 ID/순서에 의존
- 특정 구조 크기부터 갑자기 동작 중단
- 같은 칸으로 압축하면서 중요한 관계가 사라짐
- 실제 접촉 관계를 구별할 수 없음
- simultaneous event를 결정할 정보가 없음
- 구조 회전/굽힘이 필요한데 표현 불가

# 24. 반드시 구분할 세 가지

## 24.1 불가능

선언된 물리 법칙상 일어날 수 없음.

예:

```text
사용할 포트 없음
필요 에너지 부족
공간적으로 접촉 불가
```

---

## 24.2 미구현

물리적으로 가능할 수 있지만 현재 runtime이 지원하지 않음.

---

## 24.3 결정 불가능

현재 세계 상태 표현만으로 여러 합법 결과 중 하나를 선택할 수 없음.

이 셋을 섞지 않는다.

```text
불가능 ≠ 미구현 ≠ 정보 부족
```

# 27. 최종 원칙

> **우리는 결과를 설계하지 않는다. 결과를 갈라놓는 물리 조건을 설계한다.**

그리고:

> **구현이 결정을 내리기 전에 세계 상태가 먼저 결정을 내릴 수 있어야 한다.**

마지막으로:

> **“다 같이 인사할 수도 있지 않나?”라는 질문은 사소한 비유가 아니라, 예시 하나를 세계 전체 법칙으로 고정해버리는 것을 막는 설계 검사다.**
