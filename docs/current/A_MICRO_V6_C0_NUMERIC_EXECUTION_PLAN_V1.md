# A-MICRO v6 C0 수치 실행 계획 v1 — 숫자에게 무엇을 요구하는가

**상태:** 초안 2판 (2026-09-24) — 설계자 N7(다중 실행기 계약) 추가, **E1을 지금 실측**(9절). **코드 없음, 수 체계 미선택.**
**상위:** `A_MICRO_V6_PHYSICS_CLOSURE_V1.md`(2판 승인, C0 = 반발만 있는 보존적 쌍 상호작용), `A_V6_DEFORMABLE_MATERIAL_ARCHITECTURE_V1.md`
5절(수치 계약 5개, 수렴 두 종류, `energy_balance_residual`).
**목적:** 후보에게 점수를 매기는 것이 아니라, **숫자 체계에게 무엇을 요구하는지를 먼저 못 박는 것.** 구현이 편한 숫자가 물리 법칙을 몰래
정하는 일을 막는다.

**순서 (N7 반영):** ① C0 연산 목록(1절) → ② 탈락 조건 동결(3절) → ③ 수치 backend 인터페이스 → ④ 직렬 CPU → ⑤ 병렬 CPU → ⑥ GPU →
⑦ 실행 경로 간 차등 시험 → ⑧ 고정밀 기준 계산기 비교(5절) → ⑨ 통과자끼리만 비용 비교 → ⑩ 선택 → ⑪ 그 다음에야 C0 구현.

## 1. C0 연산 목록 (operation census)

한 시간 간격(step)에 C0이 하는 일:

| # | 단계 | 연산 | 숫자 체계에 주는 부담 |
|---|---|---|---|
| O1 | 위치 차이 `d = xⱼ − xᵢ` (주기 경계면 최소 상 규약) | 뺄셈, 상자 크기로 감기(wrap) | 감기가 정확한가. 최소 상 선택은 **분기**(4절) |
| O2 | 거리 관련량 | `r² = d·d` (곱·합). 퍼텐셜 모양에 따라 `r`(제곱근), `1/r²`(나눗셈) | 제곱근·나눗셈의 반올림이 플랫폼마다 같은가 |
| O3 | 범위 판정 `r² < r_c²` | 비교 | **분기** — 인과가 켜지고 꺼짐(4절) |
| O4 | 퍼텐셜·힘 평가 | 퍼텐셜 모양에 따라 다항식 / 거듭제곱 / 지수(`exp`) | 초월 함수는 라이브러리마다 결과가 다름 |
| O5 | 두 입자에 ±힘 | 같은 값을 한쪽엔 더하고 한쪽엔 뺌 | 운동량이 **비트 단위로** 보존되려면 두 입자가 받는 양이 정확히 같은 크기 |
| O6 | 한 입자가 받는 여러 힘 합산 | 대규모 덧셈 | **합산 순서가 결과를 바꾸는가** — 바꾸면 재명명 불변성이 비트 수준에서 깨짐 |
| O7 | 시간 진화 | `p += F·Δt`, `x += p·(Δt/m)` | `Δt/m`은 종류별 상수로 미리 계산 가능. 곱셈 반올림 |
| O8 | 에너지 계산 | `Σ p²/2m + Σ U` | 큰 합의 정밀도 — 잔차보다 계산 오차가 크면 잔차가 무의미 |
| O9 | 감사값 | 총 운동량, 총 각운동량 `Σ x × p`, `energy_balance_residual` | 감사가 실행기와 같은 반올림을 쓰면 같은 오류를 못 잡음 → 5절 |

### 1.1 연산 목록은 퍼텐셜 모양에 달려 있다 — 그러나 숫자가 퍼텐셜을 고르면 안 된다

| C0 반발 퍼텐셜 후보 | 필요한 연산 | 물리 근거 |
|---|---|---|
| **P-a** `r²`의 다항식 + 매끄러운 차단 | 곱·합만 (제곱근·나눗셈 없음). 힘 = `−2 U′(r²) d` | 근사 — 모양은 임의, 가파름·범위만 물리 |
| **P-b** 거듭제곱 반발 (`r⁻¹²` 계열, WCA형) | 나눗셈 (`r²`로 쓰면 제곱근은 없음) | 근사 — 역사적 편의. 현실 반발의 모양은 아님 |
| **P-c** 지수 반발 (Born–Mayer형 `A·e^{−r/ρ}`) | 제곱근 + `exp` | 파울리 반발에 더 가까운 모양으로 알려짐 — 그래도 유효 모델 |

**구현자 공개 — 여기가 설계자가 경고한 바로 그 지점이다:** 고정소수점에 가장 편한 것은 P-a다. 숫자 편의 때문에 P-a를 고르면
"구현 편한 숫자가 물리를 몰래 결정"하는 것이다. 그래서 이 계획은 **세 모양 전부로 후보를 시험**하고, 퍼텐셜 모양은 **별도 물리 결정 N3**으로
근거 등급과 함께 정한다. 결과가 "후보 X는 P-c를 못 한다"로 나오면 그것은 후보의 탈락 사유이지 P-c의 탈락 사유가 아니다(설계자가 달리
정하지 않는 한).

**매끄러운 차단(모든 모양 공통 요구):** 유한 범위 퍼텐셜은 차단 거리에서 **값과 기울기가 모두 0**으로 가야 한다. 아니면 쌍이 차단 거리를
넘을 때마다 에너지가 계단처럼 튀고(O3 분기가 에너지를 만든다), 이것은 숫자 체계와 무관한 **물리 쪽 결함**이다.

## 2. 후보 — 재분류 (설계자 수정)

| 역할 | 후보 | 성질 |
|---|---|---|
| **주 실행기** | **F1 고정소수점 정수** | 덧셈이 정확·결합 법칙 성립 → 합산 순서 무관. 범위가 좁음, 나눗셈·제곱근·`exp`는 직접 구현 |
| **주 실행기** | **F2 결정론적 부동소수점** — (a) 하드웨어 IEEE를 엄격 규칙(고정 순서, FMA 자동 합성 금지, fast-math 금지)으로 / (b) 순수 소프트웨어 구현 | 범위가 넓음. 기본 사칙·제곱근은 IEEE가 정확 반올림을 보장하지만 **`exp` 같은 초월 함수는 보장 없음** → 직접 구현 필요. 덧셈 결합 법칙 불성립 → 합산 순서 규약 필요 |
| **주 실행기 (참고)** | **F3a 임의 정밀도 유리수** (v5의 `Fraction`) | 이산 사상을 **정확히** 계산. 그러나 `√`·`exp` 불가(P-a만 가능), 분자·분모가 시간에 따라 폭증할 수 있음 → 측정 대상 |
| **주 실행기 (참고)** | **F3b 임의 정밀도 부동소수점** (정확 반올림 라이브러리) | 결국 반올림 근사. 정밀도를 올려 가며 수렴을 보는 데 유용 |
| **독립 검증기 / 기준** | **V1 구간 산술** | 참값을 감싸는 데 강함. **세계 상태를 구간으로 들고 가면 구간이 계속 넓어져 "여기 있을 수도, 저기 있을 수도"인 세계**가 됨 → 주 실행기 아님 |

## 3. 탈락 조건 — **먼저 동결** (통과/탈락, 점수제 금지)

가중치 점수로 고르지 않는다. 아래 중 하나라도 걸리면 탈락, 전부 통과한 후보끼리만 비용을 비교한다.

| # | 탈락 조건 |
|---|---|
| E1 | 같은 설정에서 **CPU/GPU 비트 불일치** |
| E2 | **재명명·입력 순서**로 결과(비트)가 바뀜 |
| E3 | 넘침을 **조용히 감음**(wrap) 또는 NaN/무한대를 조용히 전파 — 검출되면 반드시 중단 |
| E4 | 시간 간격을 줄이거나 정밀도를 높여도 **수렴하지 않음**(두 종류, 5절) |
| E5 | **운동량 보존 계약 위반** — 계약: 작용-반작용이 같은 크기로 적용되어 총 운동량이 수치 체계가 허용하는 범위에서 정확(고정소수점이면 비트 단위) |
| E6 | 같은 입력 두 번 실행이 비트 불일치 (결정론) |
| E7 | 초월 함수·나눗셈·제곱근 결과가 **플랫폼·라이브러리에 의존** (직접 고정 구현이 없으면 탈락) |
| E8 | **분기 불안정** — 정밀도를 높여도 불연속 분기(4절)의 결과가 안정되지 않음 |

**비교 항목 (탈락이 아니라 측정):** 각운동량 표류, `energy_balance_residual`, 동적 범위, 정밀도당 비용, 실행 시간, 메모리, (선택) 비트 가역성.

**E1 정정 (1판의 잘못):** 1판은 "이 작업 환경에는 GPU 실행 경로가 없다"며 E1을 미판정으로 미뤘다. **확인하지 않고 쓴 틀린 문장이었다** —
실제로는 로컬 RTX 4060이 있고 PyTorch CUDA가 동작한다(9.4). E1은 미루지 않고 **숫자 체계 선택 전에 실측**한다(9절).

**E1의 뜻 (설계자):** 같은 초기 상태 · 같은 Δt · 같은 정밀도 · 같은 퍼텐셜 · 같은 경계 · 같은 상호작용 집합 → 직렬 CPU · 병렬 CPU · GPU의
**정규화된 물리 상태가 비트 단위로 동일.** "오차 범위니까 괜찮다"는 인정하지 않는다.

## 4. 분기 감사 — 숫자 오차가 인과를 켜고 끄는 곳

> **수치 오차가 불연속적인 물리 분기를 결정하는 지점은 특별 감사한다. 정밀도를 높였을 때 분기 결과도 안정화되어야 한다.** (설계자)

C0의 분기 지점:

| 분기 | 결과 | 완화 |
|---|---|---|
| O3 `r² < r_c²` | 쌍 상호작용이 켜짐/꺼짐 | 매끄러운 차단(1.1) → 경계 근처에서 힘이 거의 0이라 **어느 쪽이든 결과 차이가 연속적으로 작음**. 분기는 남지만 인과적 효과가 사라짐 |
| O1 최소 상 선택 | 어느 복사본과 상호작용하나 | 차단 거리 < 상자 절반이면 두 후보가 동시에 범위 안에 들 수 없음 → 효과 없음. 이 조건을 세계 명세 검증으로 강제 |
| 넘침 검출 | 중단 | E3 |

**감사 방법:** 기록된 모든 분기 지점에서 판정값의 여유(`|r² − r_c²|`)를 남기고, 여유가 수치 오차 한계보다 작은 분기 수를 센다. 정밀도를
높일 때 그 수가 줄어들고 결과가 안정되는지 본다.

## 5. 기준 계산기 (reference oracle) — 후보들이 모두 같은 틀린 답을 내는 것을 막는다

```
주 실행기 후보들  ──비교──→  고정밀 기준 계산기 (느림, 작은 입자 수, 짧은 시간)
                                  └─ 가능하면 구간 산술로 참값을 감싸는 독립 감사
```

**두 오차를 따로 잰다 (구현자 추가):**

| 오차 | 무엇과 비교 | 무엇을 알려 주나 |
|---|---|---|
| **반올림 오차** | **같은 Δt**의 이산 사상을 기준 계산기가 초고정밀(또는 F3a 정확)로 계산한 값 | 숫자 체계가 얼마나 틀리나 |
| **이산화 오차** | Δt → 0 외삽 / 해석해(두 입자 산란각) | 적분기가 얼마나 틀리나 — 숫자 체계와 무관 |

두 개를 섞으면 "Δt를 줄였더니 좋아졌다"가 숫자 덕인지 적분기 덕인지 모른다.

**기준 계산기는 A 실행기가 아니다.** 세계를 만들지 않고, 판정에만 쓴다. 독립 감사 원칙대로 `engine`을 import하지 않는다.

## 6. 시험 — 세 층

### L1 산술 단위
`+ − × ÷`, 거리 계산, 세 퍼텐셜 모양의 힘 계산, 대규모 합산(순서 뒤섞기), 반올림, 넘침 경계.

### L2 C0 단일 상호작용
두 입자 정면 산란 · 비스듬한 산란(산란각 vs 해석해) · 질량이 매우 다른 두 입자 · 매우 가까운 접근(가장 큰 힘 = 동적 범위 시험).

**구현자 참고:** 에너지가 보존되면 두 입자가 가까워질 수 있는 최소 거리는 전체 에너지로 제한된다(`U(r_min) ≤ E`). 그래서 세계의 에너지에서
**필요한 동적 범위의 상한을 미리 계산**할 수 있다 — 고정소수점의 자릿수를 정하는 근거. 단, 수치 오차가 에너지를 만들면 이 상한이 깨지므로
넘침 검출(E3)은 그대로 둔다.

### L3 다입자 장시간
입자 16 → 64 → 256 → …, 긴 시간.

| 측정 | 비고 |
|---|---|
| 총 운동량 표류 | E5 |
| 총 각운동량 표류 | 측정 |
| `energy_balance_residual` (± 그대로) | 측정 |
| 직렬 CPU / 병렬 CPU / GPU digest | E1 |
| 입력 순서·재명명 digest | E2 |
| Δt 절반 수렴 (짧은 시간 궤적 / 긴 시간 관측량) | E4 |
| 정밀도 증가 수렴 | E4 |
| 분기 여유 부족 수 | E8 |
| 실행 시간, 메모리 | 비용 |
| (선택) 전진 N → 속도 반전 → N 후 비트 복귀 | 비트 가역성 — 필수 아님 |

## 7. 알려진 사실 (후보 평가 전 참고 — 결론 아님)

- **정수 덧셈은 결합 법칙이 성립한다.** 고정소수점이면 O6 합산 순서가 결과를 바꾸지 않아 E2가 구조적으로 성립하고, GPU의 정수 원자적 덧셈도
  순서와 무관하게 같은 결과를 낸다. 부동소수점 원자적 덧셈은 그렇지 않다.
- **부동소수점도 E2를 통과할 수 있다:** 이름표 순서가 아니라 **값 기준 정렬 후 합산**하면 합산 대상의 모음은 이름과 무관하므로 결과도 이름과
  무관하다. 비용은 입자마다 정렬.
- **운동량을 상태로 두면**(속도 대신) 작용-반작용 충격 `F·Δt`를 두 입자에 같은 정수로 ± 적용해 총 운동량이 고정소수점에서 비트 단위로 정확.
- **정수 위치 + 도약(leapfrog) 적분은 비트 단위 가역이 가능**하다는 선행 연구가 있다(Levesque & Verlet, 1993). 필수 조건은 아니지만 F1의 장점 후보.
- **주기 상자 크기를 고정소수점 단위의 2의 거듭제곱으로** 두면 O1 감기가 정수 나머지 연산으로 정확 — 단, 이것도 숫자 편의가 세계 크기를 정하는
  예이므로 세계 명세 제약으로 쓸지는 설계자 판단.

| **N2** | 후보 재분류(F1·F2a/b 주, F3a/b 참고, V1 구간은 검증기) | 승인 |
| **N3** | C0 반발 퍼텐셜 모양 — 숫자 비교와 **분리된 물리 결정** | 세 모양 전부로 시험. 모양은 근거 등급과 함께 따로 정함. 매끄러운 차단은 모양과 무관한 필수 |
| **N4** | 반올림 오차 / 이산화 오차 분리 측정 | 분리 |
| **N5** | 기준 계산기 도구 | 초고정밀 부동소수점 + 구간 산술(같은 라이브러리에 둘 다 있는 것 우선), 작은 계(≤ 16 입자)·짧은 시간만 |
| **N6** | 상자 크기를 2의 거듭제곱으로 제약할지 | 보류 — 숫자 편의가 세계를 정하는 사례라 비교 결과를 보고 판단 |
| **N7** | 다중 실행기 계약 (설계자 추가) | 9절 — 승인 방향 |
| **N8** | GPU 사용자 정의 커널 도구 (9.4) | 1단계는 설치 없이 PyTorch로 시작, 합산 순서·FMA를 직접 통제해야 하는 시점에 CuPy 설치 여부 결정 |

---

## 9. 다중 실행기 계약 — N7 (설계자 추가)

> C0 숫자 체계 선택 전에 최소 직렬 CPU / 병렬 CPU / GPU 실행 경로를 만들고, 동일한 수치 커널을 세 경로에서 실행해 E1·E2·E5·E6·E7을
> 실측한다. **GPU·병렬화 때문에 물리식이나 수치 정밀도를 바꾸는 것은 금지한다.**

**왜 지금:** 성능 최적화를 일찍 하는 것이 아니다. "하드웨어가 세계 법칙을 바꾸지 않는다"는 원칙을 숫자 체계를 고르기 **전에** 실제로
시험하는 것이다. 나중에 붙이면: CPU에서 F1 통과 → C0~C2 구축 → GPU 구현 → 병렬 합산 불일치 → 숫자 체계·실행 구조 재설계.
가장 먼저 사고가 나는 곳은 O6(한 입자에 모이는 힘 합산) — 직렬은 `((F1+F2)+F3)+F4`, 병렬은 `(F1+F2)+(F3+F4)`가 될 수 있다.

**범위:** GPU용 C0 엔진이 아니라 **수치 backend 시험 틀(harness)**. L1(산술·합산·반올림·넘침·거리)과 L2(두 입자 힘, 여러 쌍의 힘, ± 적용,
다입자 힘 합산)만 세 경로로 돌린다. 살아남은 숫자 체계만 C0 엔진 후보가 된다.

### 9.1 구조

```
                    같은 세계 상태
          ┌──────────────┼──────────────┐
      직렬 CPU        병렬 CPU          GPU
   (가장 단순, 최적화 최소)  (병렬화가 결과를 바꾸나)  (대규모 실행 경로 + CPU/GPU 계약)
          └──────────────┼──────────────┘
          정규 상태 · 보존 감사 · digest 비교
                         +
          고정밀 기준 계산기 (작은 계만 — 셋이 똑같이 틀리는 경우를 잡음)
```

네 역할을 섞지 않는다. 기준 계산기는 세 경로 어느 것과도 코드를 공유하지 않는다.

### 9.2 원인 분리표

| 직렬 | 병렬 CPU | GPU | 먼저 의심할 곳 |
|---|---|---|---|
| A | A | A | (통과) — 그래도 기준 계산기와 비교 |
| A | B | B | 병렬 합산(reduction) 설계 |
| A | A | B | GPU 수치 연산 — FMA 자동 합성, 비정규 수(denormal) 처리, 수학 함수 구현 |
| A | B | C | 둘 다 |

### 9.3 물리가 먼저, 연산은 그 다음

```
물리 모델 → 필요 연산 결정 → CPU/GPU가 그것을 동일하게 계산하는 방법 탐색     (허용)
GPU가 계산하기 쉬운 연산 → 그걸로 물리 법칙 결정                              (금지)
```

예: GPU의 `exp()`가 플랫폼마다 다르다 → 지수 퍼텐셜(P-c)을 지우는 것이 아니라 **세 경로가 공유하는 `exp` 구현을 직접 만든다.** 못 만들면
그 숫자 체계가 탈락이다(E7).

### 9.4 실제 환경 (2026-09-24 확인)

| 항목 | 상태 |
|---|---|
| GPU | NVIDIA GeForce RTX 4060, 8GB, 드라이버 CUDA 13.4 |
| PyTorch | 2.7.1 + CUDA 11.8 — **GPU 동작 확인** (int64 연산 포함) |
| Numba | 0.65.1 — **CPU 병렬 가능, CUDA 불가**(CUDA 툴킷 없음) |
| CUDA 툴킷(`nvcc`) · CuPy | **없음** |
| mpmath | 1.3.0 — 고정밀 부동소수점 + 구간 산술 둘 다 있음 → 기준 계산기(N5) 후보 |
| CPU | 논리 코어 12 |

**이 환경이 주는 제약 (구현자 공개):**
- **PyTorch만으로는 GPU 내부 합산 순서·FMA를 직접 통제할 수 없다.** `torch.sum` 같은 내장 축약은 순서를 우리가 정하지 못한다. 대신 **한 연산씩
  따로 부르는** 원소별 연산(곱 한 번, 더하기 한 번)은 각각 한 번 반올림되어 FMA가 끼어들 틈이 없고, 합산은 우리가 정한 **고정 트리 순서**로
  원소별 덧셈을 반복해 만들 수 있다. 느리지만 시험 틀에는 충분하다.
- **F1(고정소수점)의 곱셈:** 32.32 형식끼리 곱하면 중간값이 128비트가 필요한데 PyTorch에는 128비트 정수가 없다 → 32비트 조각으로 나눠
  곱하는 구현이 필요하다. 이것은 F1의 **실제 비용**으로 측정 항목에 넣는다.
- **진짜 사용자 정의 GPU 커널**(합산 순서·FMA를 커널 안에서 통제)이 필요해지면 CuPy(또는 CUDA 툴킷)를 **설치**해야 한다. 설치는 설계자
  확인 후(N8).
- 병렬 CPU 경로는 Numba 병렬(`prange`)과 PyTorch CPU 다중 스레드 중 하나 — Numba가 루프 구조를 우리가 정할 수 있어 기본 후보.
