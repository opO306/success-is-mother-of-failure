## 0. 한 문장

> **어떤 계산기도 A를 직접 정의하지 않는다.** A의 물리는 명세가, A의 계산 의미는 **A-Numeric VM 명세**가 정의하고, Python·C++·CUDA는
> 모두 그것을 구현하는 실행기다. 실행기가 기준과 다르면 **실행기가 계약을 어긴 것**이다.

환경이 부족하면 환경을 바꾼다 — 단, **특정 환경에서만 우연히 맞는 물리를 만들면 안 된다.** 그래서 여러 실행기를 동시에 유지하며 서로 검증한다.

## 1. 층

```
[L-A] A 물리 언어           물리만: 입자 종류, 질량, 상호작용, 경계, 시간
        ↓ 문법 해석 · 물리 의미 검사 · 금지 규칙 검사
[IR-P] Physics IR           애매함 없는 물리: 쌍 상호작용, 에너지 U(r), 힘 = −∇U, 보존 대상
        ↓ 숫자·결정론 계약 적용
[IR-N] Numeric IR           자료형, 반올림, 넘침 = 중단, 넓은 중간값, 정규 합산 트리, 시간 적분
        ↓
  ┌──────────┬───────────┬──────────┬─────────────┐
 A-VM       Python      C++         CUDA          (미래: HIP 등)
 기준 의미    연구·감사    CPU 직렬/병렬  GPU
```

| 층 | 들어가는 것 | **들어가면 안 되는 것** |
|---|---|---|
| L-A | 물리 | 스레드 수, 블록 크기, `float64`, `parallel_for`, `atomicAdd` — 계산 장치 구조가 세계 언어에 새면 안 됨 |
| IR-P | 물리 의미 | 반올림·자료형 |
| IR-N | 계산 의미 | 하드웨어 배치(스레드·블록) — 그것은 실행기 몫이고 결과를 바꾸면 안 됨(E9) |
| 실행기 | 배치·최적화 | 물리·계산 의미의 변경 |

**B 언어와 별개다.** A 언어는 세계의 물리와 계산을 명세하고, B 언어는 B가 세계를 관측하고 가설·실험을 표현한다. 섞지 않는다.

## 2. 헌법을 집행하는 계층 — 금지는 "검출"보다 "부재"로

설계자 제안: A 컴파일러가 `particle_id`로 결과를 고르는 코드, 조용한 넘침, `random()`을 거부한다.

**구현자 보강:** 임의 코드가 "이름표가 결과에 영향을 주는가"를 일반적으로 **검출**하는 것은 원리적으로 불가능하다(프로그램의 의미 성질은
일반적으로 판정 불가). 그래서 **IR에 그런 기본 연산이 아예 없게** 만든다:

| 금지 | IR에서의 방법 |
|---|---|
| 이름표·ID가 결과에 영향 | IR에 이름표를 읽는 연산이 **없다**. 순서가 필요한 곳은 `CANONICAL_ORDER`(값 기준)만 존재 |
| 난수 | 난수 연산이 **없다** |
| 조용한 넘침·NaN | 모든 산술 연산의 의미에 "넘치면 `HALT(reason)`"이 포함 — 끌 수 있는 옵션이 없다 |
| 벽시계 시간·스레드 번호 | 읽는 연산이 **없다** |
| 비결정 합산 | 합산은 `CANONICAL_SUM`만 존재, 논리 트리가 명세에 고정 |

정적 검사는 L-A → IR-P 단계에서 추가로 한다(상태 층 위반, 보존 대상 누락 등). 그러나 1차 방어선은 **표현할 수 없게 만드는 것**이다.

**실행기 능력 선언:** 각 실행기는 지원 연산을 선언하고(`deterministic_exp_v1 = YES/NO` 등), 물리 명세가 요구하는 연산을 지원하지 않으면
**실행 전에 거부**한다.

## 3. A-Numeric VM — 계산 의미의 기준

### 3.1 무엇인가
A의 숫자 연산이 정확히 무엇인지를 정의하는 **작고 느린 실행 가능한 명세**. `1 + 2`조차 호스트 언어의 `+`를 믿지 않고 "A에서 ADD란 무엇인가"를
먼저 정의한다. 물리 시뮬레이션은 하지 않는다(그것은 나중에 그 위에 얹는 A Physics VM).

```
A Physics VM (나중: DISTANCE_SQUARED, PAIR_FORCE, ACCUMULATE, UPDATE_MOMENTUM …)
      ↓ 전부 아래 연산으로 풀림
A Numeric VM (지금)
      ↓
CPU
```

### 3.2 수 체계에 대해 매개변수화 — 아직 숫자를 고르지 않았으므로

VM은 한 수 체계를 전제하지 않는다. **숫자 프로필**마다 같은 명령어의 의미를 정의한다:

| 프로필 | 뜻 |
|---|---|
| `FX(W, F)` | 폭 W비트, 소수부 F비트 고정소수점. 곱셈은 2W비트 중간값, 자리 이동 시 반올림 = 최근접 짝수, 넘침 = 중단 |
| `A-Binary64-Finite` (0단계 이름 `IEEE64-strict`) | 유한 binary64 값만, 연산마다 한 번 정확 반올림(최근접 짝수), FMA 합성 없음, 비정규 수 보존. IEEE 754와 달리 NaN·무한대를 만들지 않고 **중단** — 그래서 이름에서 IEEE를 뺐다 |
| `EXACT` | 정확 유리수 — 참고·검증용 |

### 3.3 VM은 호스트의 숫자도 믿지 않는다 (구현자 제안)

VM을 Python으로 쓰더라도 **Python 정수(정확한 임의 크기 정수)만** 사용하고, `IEEE64-strict`까지 정수 위에서 직접 구현한다(소프트웨어 부동소수점).
그러면 VM의 의미는 "정확한 정수 산술"에만 기대고, 호스트의 부동소수점·수학 라이브러리·컴파일러에 의존하지 않는다. 느리지만 기준에는 그게 맞다.

**교차 확인:** `IEEE64-strict`의 사칙·제곱근은 하드웨어 IEEE도 정확 반올림을 보장하므로, VM 결과와 하드웨어 결과가 **비트 단위로 같아야**
한다 — 다르면 VM 구현이나 하드웨어 경로 중 하나가 틀린 것. `exp` 같은 초월 함수는 하드웨어 보장이 없으므로 A가 알고리즘을 정의하고
(`deterministic_exp_v1`) 모든 실행기가 그 알고리즘을 그대로 구현한다.

### 3.4 명령어 0단계 (초안)

| 분류 | 명령 |
|---|---|
| 산술 | `ADD SUB MUL DIV NEG ABS` (프로필별 반올림·넘침 의미) |
| 넓은 곱 | `MUL_WIDE`(FX: 2W비트 결과), `SHIFT_ROUND` |
| 제곱근 | `SQRT` (정확 반올림; 음수 = 중단) |
| 비교 | `CMP` → 분기 기록(분기 감사: 여유 `|a−b|`를 함께 남김) |
| 합산 | `SUM` — **표현된 항들의 정확한 합, 마지막에 한 번 반올림**(0.1). 항 순서·스레드 수·블록 배치가 의미에 들어갈 자리가 없다 |
| 벡터 | `DOT` — **정확한 곱, 정확한 합, 한 번 반올림**(0.1). 축 순서와 무관 |
| 오류 | `HALT(reason)` — 넘침, 0으로 나눔, 정의역 밖 |

**없는 것(의도):** 이름표 읽기, 난수, 시간, 스레드 번호, 넘침 무시 옵션.

### 3.5 VM 자체의 검증 — 감사기도 신성하지 않다 (설계자 N5)

기준값의 우선순위: **해석해 → 정확 유리수로 계산 가능한 경우 → 고정밀 독립 계산(mpmath) → 구간 감사.** mpmath를 유일한 진실로 두지 않는다.
구간 감사기는 해석해가 있는 사례로 **"정말 참값을 감싸는가"를 결함 주입으로 먼저 검증**한다.

### 3.6 0단계 구현 결과 (2026-09-24)

- **프로필 3개:** `FixedPoint(W, F)`, `IEEE64Strict`, `Exact`. 모든 연산은 **정확한 값을 먼저 계산하고 규칙대로 한 번 반올림**한다. 호스트의
  부동소수점·수학 라이브러리를 쓰지 않는다(정수와 분수만).
- **명령 11개:** `CONST ADD SUB MUL DIV NEG ABS SQRT CMP SUM DOT` — 시험이 이 집합을 동결한다. 이름표·난수·시간·스레드를 읽는 명령은 없다.
  제어 흐름 없음(직선 프로그램만). `CMP`는 정확한 여유 `|a−b|`를 분기 기록으로 남긴다.
- **검증 3방향:** (1) 하드웨어 IEEE와 비트 비교 — 사칙·제곱근 각 1,507쌍, 비정규 수·넘침 근처·1 근처·작은 정규 수 포함, 전부 일치.
  (2) VM과 **다른 반올림 방법**(이웃 값 사이 중점 비교, Python의 최근접 짝수 반올림)으로 정확 유리수 대조. (3) 손 계산 사례.
  입력은 sha256 카운터로 만든다(난수 모듈 없음).
- **구현 중 잡은 버그 1개:** 반올림 판단에서 확대한 나눗수 대신 원래 나눗수를 비교 — 하드웨어 대조가 즉시 잡았다(비정규 수 곱에서 0 대신 최소값).
- **결함 주입 11종 전부 검출.** 처음엔 2종을 놓쳤다: (a) 제곱근 여유 비트가 60개라 반올림 표시 비트가 사실상 결과에 영향이 없었음 → 여유를
  최소(2비트)로 줄여 표시 비트가 실제로 결정하게 함, (b) `DOT` 순서 시험 값이 순서를 뒤집어도 같은 결과 → 순서에 따라 0과 2로 갈리는 값으로 교체.
- **아직 없음:** `MUL_WIDE`/`SHIFT_ROUND`(3.4 초안의 넓은 곱 — FX의 `MUL`이 이미 2W비트 중간값을 쓰므로 필요해지면 추가), `deterministic_exp_v1`,
  제어 흐름, 구간 산술 기준 계산기(R1), 해석해 대조. 하드웨어 대조는 **이 PC의 CPU 한 대**뿐이다.

### 3.7 VM 0.1 — 설계자 검토 반영 (2026-09-24)

**0단계의 잘못 (설계자 지적):** 문서는 "모든 연산은 정확한 값을 구한 뒤 한 번 반올림"이라고 했지만 `SUM`은 정렬 후 **두 개씩 더할 때마다
반올림**했고, `DOT`은 **곱마다·덧셈마다 반올림하는 왼쪽 접기**였다. 0단계 시험은 `DOT`이 축 순서에 따라 0과 2로 갈리는 것을 **정답 의미로
고정**하고 있었다 — x·y·z 축 순서만 바꿔도 내적이 달라지는 의미다.

| 수정 | 내용 |
|---|---|
| `SUM` | 표현된 항들의 **정확한 합 → 한 번 반올림.** FX는 넓은 정수 합 후 범위 검사 한 번(중간 넘침이 없으므로 순서가 멈춤 여부도 못 바꿈). binary64는 모든 항을 가장 작은 지수에 맞춘 정확한 정수 합. 영(0)의 부호: 모든 항이 −0일 때만 −0 |
| `DOT` | **정확한 곱, 정확한 합, 한 번 반올림.** 축 순서 무관. 0단계의 `[2⁵³, 1, 1, −2⁵³]` 사례는 이제 모든 축 순서에서 2 |
| `CMP` | 기록 이름 `margin` → **`represented_margin`**: 반올림된 **표현값 사이**의 정확한 거리일 뿐, 반올림 전 수학적 값의 거리가 아니다. 반올림이 분기를 뒤집었는지는 R1(고정밀 계산기)의 오차 한계와 함께 봐야 판정 가능: 여유 ≫ 오차 한계 → 안정 / 여유 ≈ 오차 한계 → 위험 / 여유 < 오차 한계 → 그 정밀도에서 인과 판정 주장 금지 |
| 검증기 | 실행 전에 **완전히** 거부 — 인자 개수, 정의되지 않은 레지스터 읽기, `CMP`의 목적지, `DOT` 벡터 길이, 레지스터 형태, 리터럴(float·bool·0으로 나눈 분수), 입력값(FX 범위 밖, binary64의 NaN·무한대 패턴, 64비트 밖). 전부 **한 종류의 거부 `VMRejected(code)`**로 끝나고 호스트 언어 오류(KeyError 등)가 A의 의미를 대신할 수 없다 |
| 판·해시 | `ANVM_VERSION = "0.1"`, 의미 명세 문장 모음 `SPEC`의 해시 `SPEC_HASH`. 모든 결과에 VM 판·명세 해시·프로필(매개변수 포함)·프로그램 digest·입력 digest를 넣는다. 시험이 해시를 동결 → 의미 문장을 바꾸면 시험이 깨져 판을 올리게 강제 |
| 이름 | `IEEE64Strict` → `Binary64Finite`("A-Binary64-Finite") |

**결함 주입 20종 전부 검출** — 0단계 8종 + 새 12종(binary64 SUM 순차 반올림, DOT 곱마다 반올림(binary64·FX), FX SUM 단계마다 범위 검사,
영 부호 규칙, 검증기 4종, 판 표시 누락, 해시 갱신 없이 의미 문장 수정, 능력 검사 생략).

**공개 — 0.1이 새로 떠안은 것:**
- **네이티브 실행기의 비용:** C++/CUDA가 같은 의미를 내려면 **정확 누적기**가 필요하다. binary64의 `SUM`은 지수 범위 전체(약 2,100비트),
  `DOT`은 곱의 지수 범위까지(약 4,200비트) 담는 누적기 — GPU에서 무겁다. FX의 `DOT`은 `2W + log₂(항 수)`비트 정수(W=64면 128비트 이상).
  이것은 숫자 후보 비교의 **비용 항목**으로 들어간다(의미는 바꾸지 않는다).
- `SUM`·`DOT` 안의 중간값은 무한 정밀도라 **넘침은 최종 결과에서만** 판정한다(의미 문장에 명시).
- `ADD`를 여러 번 이어 쓰면 여전히 두 번 반올림된다 — **순서와 무관해야 하는 누적은 반드시 `SUM`/`DOT`으로** 써야 한다. 물리 커널
  명세(IR-N)의 규칙으로 넣을 것.
- `SPEC_HASH`는 **의미 문장**의 해시다. 구현 코드가 문장과 다르게 바뀌어도 해시는 그대로다 — 그래서 구현 소스의 digest(`IMPLEMENTATION_DIGEST`)를
  따로 계산해 두었다. 단 **이 digest는 아직 결과에 기록되지 않고**, 문장과 구현이 같은 의미라는 것은 해시가 아니라 **동작 시험(59개)과 결함 주입**이 지킨다. 해시는 "다른 의미의 결과를 같은 것처럼 비교하지 않기" 위한 표지일 뿐 구현을 증명하지 않는다.
- **아직 IEEE 의미가 "증명"된 것은 아니다.** 하드웨어 대조는 이 PC의 CPU 하나, 무작위 계열 입력 위주다. R1 단계에서 반올림 경계 바로 양옆,
  비정규/정규 경계, 최대 유한값 근처의 **어려운 입력**, 특히 제곱근의 경계 사례를 일부러 만들어 대조한다.
- 구현 중 제 실수 1건: 시험 기대값 손계산 오류(1+1+3−2.5를 1.5로 적음) — VM이 아니라 시험이 틀렸고 즉시 드러났다.

### 3.8 R1-0 — 어려운 입력 감사 (2026-09-24)

3.7의 공개 항목 "하드웨어 대조가 무작위 계열 입력 위주"를 먼저 처리했다. 네이티브 도구 설치 없이 할 수 있는 부분이다.
**mpmath 고정밀 기준 계산기(R1 본체)는 아직 아니다** — 사칙·제곱근은 참값이 유리수(또는 그 제곱이 유리수)라서 정확 유리수로 판정할 수
있고(N5 우선순위 2번), mpmath가 필요해지는 것은 초월 함수·물리 커널의 이산화 오차를 볼 때다.

| 부분 | 내용 |
|---|---|
| 위치 | `audit/independent_numeric/` — `a_numeric`·`engine` import 금지(AST 시험). 실행기는 함수 묶음으로 **넘겨받는다** |
| 판정기 | 반올림을 **계산하지 않는다.** 주어진 결과의 이웃 두 값(비트 패턴 ±1)과의 중점을 정확 분수로 구해 "정확값이 그 구간 안에 있나, 끝점이면 마지막 비트가 짝수인가"만 본다. 제곱근은 구간 끝을 제곱해 피제곱수와 비교(여전히 정확). 넘침 = 정확 크기 ≥ 2¹⁰²⁴ − 2⁹⁷⁰ |
| 입력 15,896건 | ADD/SUB 정확 동점·동점 ±1(모든 지수대, 2의 거듭제곱 바로 아래), MUL 동점(비정규·경계·넘침 근처 결과), DIV·SQRT는 **중점에 가장 가까운 binary64 ± 1~3칸**, 밑넘침 동점(→0, 최대 비정규/최소 정규 사이), 넘침 경계 양쪽, SUM·DOT(순차 반올림이면 틀리는 경우, 중간 넘침) |
| 고정소수점 | FX(8,3)·FX(6,0)·FX(7,6) **전수**(모든 쌍의 MUL·DIV, 모든 값의 SQRT) + FX(64,32) 동점·범위 끝 |
| 판정기 자체 검증 | (1) 독립 원천인 하드웨어 결과를 전부 받아들여야 함 (2) 정답의 한 칸 이웃을 **전부** 거부해야 함 — 동점 사례 포함(동점에서는 짝수 규칙만이 둘을 가른다). 비공허 검사: 연산별 동점·근접 동점 수, 넘침 경계 양쪽 결과 수를 하한으로 고정 |

**결과: VM은 전부 통과**(하드웨어 비트 일치 포함, SUM은 `math.fsum`과도 일치 — fsum이 정의되는 사례만).

**결함 주입 10종 전부 검출.** 옛 sha256 시험(`tests/test_a_numeric_vm.py`)은 그중 **3종을 놓쳤다:**

| 결함 | 옛 시험 | R1-0 |
|---|---|---|
| M1 동점을 0에서 멀리 / M2 버림 / M3 64비트 거쳐 이중 반올림(x87식) / M5 넘침 대신 최대값 / M7 제곱근 sticky 없음 / M8 FX 동점을 멀리 / M10 FX MUL 내림 | 잡음 | 잡음 |
| **M4 비정규 결과를 53비트로 먼저 반올림한 뒤 격자로 다시 반올림** | **놓침** | 363건 |
| **M6 반올림 전에 넘침 판정**(MAX와 넘침 경계 사이 값이 MAX로 가야 하는데 멈춤) | **놓침** | 9건 |
| **M9 FX DIV 동점을 0 쪽으로** | **놓침** | 338건 |

결함은 시험 안에서 monkeypatch로 넣는다(원본 파일을 바꾸지 않으므로 `VERIFICATION_LIMITS_AND_LESSONS.md`에 기록된 바이트코드 캐시 사고가 생길 수 없다). "옛 시험이 놓침"은 같은
결함을 넣고 옛 시험 파일을 돌려 확인한 1회 실측이며, 시험으로 고정하지는 않았다.

**한계 (공개):**
- 입력은 **구성한 것**이지 증명이 아니다. 제곱근의 진짜 최악 사례(Lefèvre식 전수 탐색으로 찾는 중점에 가장 가까운 입력)는 찾지 않았다 —
  중점² 근처라는 구성만 썼다.
- 판정기는 CPython의 `float → Fraction` 변환과 `float(Fraction)`(입력 생성용)을 믿는다. 판정 자체는 전자만 쓴다.
- 하드웨어 대조는 여전히 **이 PC의 CPU 하나**.
- VM의 `SUM`·`DOT` 영(0) 부호 규칙은 IEEE에 없는 **A의 규칙**이라 판정기가 VM 명세 문장을 그대로 옮겨 적었다 — 여기서는 독립 판정이 아니다.

### 4.1 B0·B1·B2 구현 결과 (2026-09-25)

**범위(설계자 지시):** C0 세계 엔진이 아니라 **수치 backend 검증 틀**. VM 0.1의 의미를 바꾸지 않는다. 퍼텐셜은 **고르지 않는다**.
코드: `a_numeric_native/`. 시험: `tests/test_a_numeric_native_b0.py`(11개), `tests/test_a_numeric_native_b1.py`(9개), `tests/test_a_numeric_native_b2.py`(8개).

**구조:** 네이티브 실행기는 VM과 **같은 명령 형식의 직선 프로그램**(CONST ADD SUB MUL DIV NEG ABS SQRT CMP SUM DOT)을 받아
실행한다. `harness.py`가 같은 프로그램을 VM과 실행기에 보내고 레지스터·분기 기록(`represented_margin` 포함)·멈춤(위치·이유)을
비교한다. 실행기는 기대값을 받지 않는다. 네이티브 소스에 VM 호출이 없다는 것도 시험한다.

| | 방법 |
|---|---|
| binary64 사칙·제곱근 | 하드웨어(x64 SSE2, MSVC `/fp:strict`) — 정확 반올림이 보장되는 연산. 결과가 유한하지 않으면 `overflow` 멈춤, 0으로 나누기·음수 제곱근은 먼저 멈춤 |
| SUM·DOT | 작은 임의 정밀도 정수로 **정확 합 → 1회 반올림**(부동소수점 합산으로 대체하지 않음). 영(0) 부호 규칙 포함 |
| CONST | 유리수 → 정확 나눗셈 → 1회 반올림 |
| FX(W, F) | 전부 정확 정수(넓은 곱, 최근접 짝수, 범위 검사 1회) |
| B1 병렬 | 프로그램을 T개 스레드에 나눠 실행(출력은 입력 순서), SUM·DOT 항을 T개 연속 조각으로 나눠 조각별 **정확** 부분합 → 정확히 합침 → 1회 반올림. 정수 덧셈은 결합 법칙이 성립하므로 T가 값을 바꿀 수 없다 |
| B2 CUDA | 프로그램 하나 = 블록 하나. 스레드 0이 해석, SUM·DOT은 블록의 모든 스레드가 항을 건너뛰며 나눠 **4,480비트 2의 보수 정확 누적기**에 더하고 스레드 0이 부분합을 정확히 합쳐 1회 반올림. binary64 사칙·제곱근은 `__dadd_rn` 등 정확 반올림 내장 함수(축약 없음). FX는 128비트 정수(W ≤ 64). 장치 산술은 `anvm_core.hpp`와 **별도로 새로 작성**. nvcc `-fmad=false --prec-div=true --prec-sqrt=true -ftz=false -arch=sm_89` |

**사례 모음 9개(~100,000 프로그램):** R1-0 경계 사례 15,896 · sha256 계열 사칙/비교/단항 12,070 · SUM/DOT(동점·영 부호·역순
포함) 3,134 · CONST 유리수 1,517 · FX(6,2) 전수 + FX(7,3) MUL/DIV/SQRT 전수 53,568 · FX(64,32) 동점·범위 끝·SUM/DOT 12,661 ·
거리 `d`와 `r²=DOT(d,d)`(binary64·FX) 1,500 · 퍼텐셜 능력 탐침 1,413 · 긴 합산(길이 2~2,049, T로 나누어떨어지지 않는 길이 포함) 70.

**능력 조사 — 퍼텐셜은 선택하지 않았다(우선순위 4):**

| | P-a (r² 다항식, 매끄러운 차단) | P-b (r⁻¹²계열, WCA형) | P-c (지수 반발) |
|---|---|---|---|
| 필요 연산 | SUB MUL CMP | DIV MUL SUB ADD CMP | SQRT DIV + **EXP** |
| A-Binary64-Finite | 표현 가능, 멈춤 없음(333) | 표현 가능, 멈춤 없음(333) | **지수 인자까지만.** VM 0.1에 EXP 없음 |

- P-b의 FX 넘침은 σ=1에서 `(1/r²)⁶ < 2³¹`이 깨지는 r² ≲ 0.03 근처다. **탈락 판정이 아니라** N9(동적 범위 증명)의 입력.
- P-c는 A가 `deterministic_exp_v1`을 **VM 명세로 먼저 정의**해야 네이티브에도 넣을 수 있다. 지금 네이티브에 `exp`를 넣으면
  실행기가 의미를 정하는 것이 되므로 넣지 않았다.

**공개 — 한계와 숨은 조건:**
- **B0과 B1은 산술 핵심(`anvm_core.hpp`)을 공유한다.** B0=B1 일치는 "스레드 수가 결과를 바꾸지 않는다"의 증거일 뿐, 산술 핵심이
  맞다는 **독립** 증거가 아니다. 핵심의 정확성은 VM과의 비교가 지킨다. B2(CUDA)는 장치 코드로 다시 써야 하므로 이 공유가 깨진다.
- binary64 사칙·제곱근은 **하드웨어를 믿는다**(이 PC의 CPU 하나, MSVC `/fp:strict /O2`). R1-0 경계 사례에서 VM과 일치를 확인했을 뿐
  다른 CPU·컴파일러는 미확인.
- **실행 전 검증 없음:** 네이티브 실행기는 VM이 받아들이는 프로그램만 받는다고 가정한다(`VMRejected`에 해당하는 거부를 구현하지 않음).
- EXACT 프로필은 네이티브에 없다(기준용).
- 성능은 재지 않았다. B1은 SUM·DOT마다 스레드를 새로 만든다 — 느리고, 의도적으로 최적화하지 않았다.
- **B2의 CONST는 호스트에서** `anvm_core.hpp`로 계산해 올린다(프로그램 적재 단계). 그래서 CONST 의미는 B0·B1·B2가 공유한다 — 독립 확인은 VM 비교뿐. CONST가 멈추면 그 명령의 pc에서 멈추는 것은 장치가 한다.
- B2의 FX는 **W ≤ 64만**(128비트 정수). 더 넓은 형식은 거부하고 끝난다.
- FMA 축약: 해석기 구조라 VM 명령 하나가 장치 연산 하나이고, 두 명령이 합쳐질 자리가 없다. **나중에 커널을 명령 단위가 아니라 식 단위로 컴파일하면** `-fmad=false`가 실제로 필요해진다 — 그때 이 결함(FMA 합성)을 주입해 시험해야 한다. 지금은 시험하지 않았다.
- E9에서 바꾼 것은 **블록 크기**뿐이다. 한 번에 띄우는 블록 수(격자)는 블록 크기에서 정해지며 따로 바꿔 보지 않았다.
- 컴파일: 140칸 고정 루프를 컴파일러가 전부 펼치느라 `cicc`가 5분 넘게 끝나지 않아 `#pragma unroll 1`·`__noinline__`을 넣었다(6초). 의미가 아니라 컴파일 시간 문제. `-arch=sm_89`(RTX 4060) 고정.
- GPU 한 대(RTX 4060, 드라이버 CUDA 13.4, 툴킷 13.4)만 확인. 다른 GPU·드라이버는 미확인.
- 시험 시간: 전체 스위트 약 4분 → 약 5분 30초.
