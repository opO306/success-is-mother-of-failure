## 0. 한 문장

> **어떤 계산기도 A를 직접 정의하지 않는다.** A의 물리는 명세(Physics IR)가, A의 계산 의미는 **Evaluation IR**(정확히 어떤 수학적 양을
> 계산하고 어디서 반올림하는가)과 그 아래 **A-Numeric VM**(원시 수치 연산·반올림·구간 감싸기)이 함께 정의하고, Python·C++·CUDA는
> 모두 그것을 구현하는 실행기다. 실행기가 기준과 다르면 **실행기가 계약을 어긴 것**이다.
>
> (2026-09-26 수정. 원래 문장은 "A의 계산 의미는 A-Numeric VM 명세가 정의한다"였다 — C1에서 `round(V_real(√R²))`,
> `round(F_real(R)·Δx/R·Δt/2)`처럼 합성된 양 전체를 한 번 반올림하는 의미가 필요해졌고, 연산마다 반올림하는 VM만으로는 표현되지 않았다. 7.1절.)

환경이 부족하면 환경을 바꾼다 — 단, **특정 환경에서만 우연히 맞는 물리를 만들면 안 된다.** 그래서 여러 실행기를 동시에 유지하며 서로 검증한다.

## 1. 층

```
[L-A] A 물리 언어           물리만: 입자 종류, 질량, 상호작용, 경계, 시간
        ↓ 문법 해석 · 물리 의미 검사 · 금지 규칙 검사
[IR-P] Physics IR           애매함 없는 물리: 쌍 상호작용, 에너지 U(r), 힘 = −∇U, 보존 대상
        ↓ 숫자·결정론 계약 적용
[IR-N] Numeric IR           자료형, 반올림, 넘침 = 중단, 넓은 중간값, 정규 합산 트리, 시간 적분
        ↓
  ┌──────────┬───────────┬──────────┬─────────────┐
 A-VM       Python      C++         CUDA          (미래: HIP 등)
 기준 의미    연구·감사    CPU 직렬/병렬  GPU
```

| 층 | 들어가는 것 | **들어가면 안 되는 것** |
|---|---|---|
| L-A | 물리 | 스레드 수, 블록 크기, `float64`, `parallel_for`, `atomicAdd` — 계산 장치 구조가 세계 언어에 새면 안 됨 |
| IR-P | 물리 의미 | 반올림·자료형 |
| IR-N | 계산 의미 | 하드웨어 배치(스레드·블록) — 그것은 실행기 몫이고 결과를 바꾸면 안 됨(E9) |
| 실행기 | 배치·최적화 | 물리·계산 의미의 변경 |

**2026-09-26:** IR-P와 IR-N 사이에 반올림 경계를 명시하는 **Evaluation IR**이 필요하다 — 수정된 층 구조는 7.1절.

**B 언어와 별개다.** A 언어는 세계의 물리와 계산을 명세하고, B 언어는 B가 세계를 관측하고 가설·실험을 표현한다. 섞지 않는다.

## 2. 헌법을 집행하는 계층 — 금지는 "검출"보다 "부재"로

설계자 제안: A 컴파일러가 `particle_id`로 결과를 고르는 코드, 조용한 넘침, `random()`을 거부한다.

**구현자 보강:** 임의 코드가 "이름표가 결과에 영향을 주는가"를 일반적으로 **검출**하는 것은 원리적으로 불가능하다(프로그램의 의미 성질은
일반적으로 판정 불가). 그래서 **IR에 그런 기본 연산이 아예 없게** 만든다:

| 금지 | IR에서의 방법 |
|---|---|
| 이름표·ID가 결과에 영향 | IR에 이름표를 읽는 연산이 **없다**. 순서가 필요한 곳은 `CANONICAL_ORDER`(값 기준)만 존재 |
| 난수 | 난수 연산이 **없다** |
| 조용한 넘침·NaN | 모든 산술 연산의 의미에 "넘치면 `HALT(reason)`"이 포함 — 끌 수 있는 옵션이 없다 |
| 벽시계 시간·스레드 번호 | 읽는 연산이 **없다** |
| 비결정 합산 | 합산은 `CANONICAL_SUM`만 존재, 논리 트리가 명세에 고정 |

정적 검사는 L-A → IR-P 단계에서 추가로 한다(상태 층 위반, 보존 대상 누락 등). 그러나 1차 방어선은 **표현할 수 없게 만드는 것**이다.

**실행기 능력 선언:** 각 실행기는 지원 연산을 선언하고(`deterministic_exp_v1 = YES/NO` 등), 물리 명세가 요구하는 연산을 지원하지 않으면
**실행 전에 거부**한다.

## 3. A-Numeric VM — 원시 수치 의미의 기준 (2026-09-26: "계산 의미의 기준"에서 수정, 7.1절)

### 3.1 무엇인가
A의 숫자 연산이 정확히 무엇인지를 정의하는 **작고 느린 실행 가능한 명세**. `1 + 2`조차 호스트 언어의 `+`를 믿지 않고 "A에서 ADD란 무엇인가"를
먼저 정의한다. 물리 시뮬레이션은 하지 않는다(그것은 나중에 그 위에 얹는 A Physics VM).

```
A Physics VM (나중: DISTANCE_SQUARED, PAIR_FORCE, ACCUMULATE, UPDATE_MOMENTUM …)
      ↓ 전부 아래 연산으로 풀림
A Numeric VM (지금)
      ↓
CPU
```

### 3.2 수 체계에 대해 매개변수화 — 아직 숫자를 고르지 않았으므로

VM은 한 수 체계를 전제하지 않는다. **숫자 프로필**마다 같은 명령어의 의미를 정의한다:

| 프로필 | 뜻 |
|---|---|
| `FX(W, F)` | 폭 W비트, 소수부 F비트 고정소수점. 곱셈은 2W비트 중간값, 자리 이동 시 반올림 = 최근접 짝수, 넘침 = 중단 |
| `A-Binary64-Finite` (0단계 이름 `IEEE64-strict`) | 유한 binary64 값만, 연산마다 한 번 정확 반올림(최근접 짝수), FMA 합성 없음, 비정규 수 보존. IEEE 754와 달리 NaN·무한대를 만들지 않고 **중단** — 그래서 이름에서 IEEE를 뺐다 |
| `EXACT` | 정확 유리수 — 참고·검증용 |

### 3.3 VM은 호스트의 숫자도 믿지 않는다 (구현자 제안)

VM을 Python으로 쓰더라도 **Python 정수(정확한 임의 크기 정수)만** 사용하고, `IEEE64-strict`까지 정수 위에서 직접 구현한다(소프트웨어 부동소수점).
그러면 VM의 의미는 "정확한 정수 산술"에만 기대고, 호스트의 부동소수점·수학 라이브러리·컴파일러에 의존하지 않는다. 느리지만 기준에는 그게 맞다.

**교차 확인:** `IEEE64-strict`의 사칙·제곱근은 하드웨어 IEEE도 정확 반올림을 보장하므로, VM 결과와 하드웨어 결과가 **비트 단위로 같아야**
한다 — 다르면 VM 구현이나 하드웨어 경로 중 하나가 틀린 것. `exp` 같은 초월 함수는 하드웨어 보장이 없으므로 A가 알고리즘을 정의하고
(`deterministic_exp_v1`) 모든 실행기가 그 알고리즘을 그대로 구현한다.

### 3.4 명령어 0단계 (초안)

| 분류 | 명령 |
|---|---|
| 산술 | `ADD SUB MUL DIV NEG ABS` (프로필별 반올림·넘침 의미) |
| 넓은 곱 | `MUL_WIDE`(FX: 2W비트 결과), `SHIFT_ROUND` |
| 제곱근 | `SQRT` (정확 반올림; 음수 = 중단) |
| 비교 | `CMP` → 분기 기록(분기 감사: 여유 `|a−b|`를 함께 남김) |
| 합산 | `SUM` — **표현된 항들의 정확한 합, 마지막에 한 번 반올림**(0.1). 항 순서·스레드 수·블록 배치가 의미에 들어갈 자리가 없다 |
| 벡터 | `DOT` — **정확한 곱, 정확한 합, 한 번 반올림**(0.1). 축 순서와 무관 |
| 오류 | `HALT(reason)` — 넘침, 0으로 나눔, 정의역 밖 |

**없는 것(의도):** 이름표 읽기, 난수, 시간, 스레드 번호, 넘침 무시 옵션.

### 3.5 VM 자체의 검증 — 감사기도 신성하지 않다 (설계자 N5)

기준값의 우선순위: **해석해 → 정확 유리수로 계산 가능한 경우 → 고정밀 독립 계산(mpmath) → 구간 감사.** mpmath를 유일한 진실로 두지 않는다.
구간 감사기는 해석해가 있는 사례로 **"정말 참값을 감싸는가"를 결함 주입으로 먼저 검증**한다.

### 3.6 0단계 구현 결과 (2026-09-24)

- **프로필 3개:** `FixedPoint(W, F)`, `IEEE64Strict`, `Exact`. 모든 연산은 **정확한 값을 먼저 계산하고 규칙대로 한 번 반올림**한다. 호스트의
  부동소수점·수학 라이브러리를 쓰지 않는다(정수와 분수만).
- **명령 11개:** `CONST ADD SUB MUL DIV NEG ABS SQRT CMP SUM DOT` — 시험이 이 집합을 동결한다. 이름표·난수·시간·스레드를 읽는 명령은 없다.
  제어 흐름 없음(직선 프로그램만). `CMP`는 정확한 여유 `|a−b|`를 분기 기록으로 남긴다.
- **검증 3방향:** (1) 하드웨어 IEEE와 비트 비교 — 사칙·제곱근 각 1,507쌍, 비정규 수·넘침 근처·1 근처·작은 정규 수 포함, 전부 일치.
  (2) VM과 **다른 반올림 방법**(이웃 값 사이 중점 비교, Python의 최근접 짝수 반올림)으로 정확 유리수 대조. (3) 손 계산 사례.
  입력은 sha256 카운터로 만든다(난수 모듈 없음).
- **구현 중 잡은 버그 1개:** 반올림 판단에서 확대한 나눗수 대신 원래 나눗수를 비교 — 하드웨어 대조가 즉시 잡았다(비정규 수 곱에서 0 대신 최소값).
- **결함 주입 11종 전부 검출.** 처음엔 2종을 놓쳤다: (a) 제곱근 여유 비트가 60개라 반올림 표시 비트가 사실상 결과에 영향이 없었음 → 여유를
  최소(2비트)로 줄여 표시 비트가 실제로 결정하게 함, (b) `DOT` 순서 시험 값이 순서를 뒤집어도 같은 결과 → 순서에 따라 0과 2로 갈리는 값으로 교체.
- **아직 없음:** `MUL_WIDE`/`SHIFT_ROUND`(3.4 초안의 넓은 곱 — FX의 `MUL`이 이미 2W비트 중간값을 쓰므로 필요해지면 추가), `deterministic_exp_v1`,
  제어 흐름, 구간 산술 기준 계산기(R1), 해석해 대조. 하드웨어 대조는 **이 PC의 CPU 한 대**뿐이다.

### 3.7 VM 0.1 — 설계자 검토 반영 (2026-09-24)

**0단계의 잘못 (설계자 지적):** 문서는 "모든 연산은 정확한 값을 구한 뒤 한 번 반올림"이라고 했지만 `SUM`은 정렬 후 **두 개씩 더할 때마다
반올림**했고, `DOT`은 **곱마다·덧셈마다 반올림하는 왼쪽 접기**였다. 0단계 시험은 `DOT`이 축 순서에 따라 0과 2로 갈리는 것을 **정답 의미로
고정**하고 있었다 — x·y·z 축 순서만 바꿔도 내적이 달라지는 의미다.

| 수정 | 내용 |
|---|---|
| `SUM` | 표현된 항들의 **정확한 합 → 한 번 반올림.** FX는 넓은 정수 합 후 범위 검사 한 번(중간 넘침이 없으므로 순서가 멈춤 여부도 못 바꿈). binary64는 모든 항을 가장 작은 지수에 맞춘 정확한 정수 합. 영(0)의 부호: 모든 항이 −0일 때만 −0 |
| `DOT` | **정확한 곱, 정확한 합, 한 번 반올림.** 축 순서 무관. 0단계의 `[2⁵³, 1, 1, −2⁵³]` 사례는 이제 모든 축 순서에서 2 |
| `CMP` | 기록 이름 `margin` → **`represented_margin`**: 반올림된 **표현값 사이**의 정확한 거리일 뿐, 반올림 전 수학적 값의 거리가 아니다. 반올림이 분기를 뒤집었는지는 R1(고정밀 계산기)의 오차 한계와 함께 봐야 판정 가능: 여유 ≫ 오차 한계 → 안정 / 여유 ≈ 오차 한계 → 위험 / 여유 < 오차 한계 → 그 정밀도에서 인과 판정 주장 금지 |
| 검증기 | 실행 전에 **완전히** 거부 — 인자 개수, 정의되지 않은 레지스터 읽기, `CMP`의 목적지, `DOT` 벡터 길이, 레지스터 형태, 리터럴(float·bool·0으로 나눈 분수), 입력값(FX 범위 밖, binary64의 NaN·무한대 패턴, 64비트 밖). 전부 **한 종류의 거부 `VMRejected(code)`**로 끝나고 호스트 언어 오류(KeyError 등)가 A의 의미를 대신할 수 없다 |
| 판·해시 | `ANVM_VERSION = "0.1"`, 의미 명세 문장 모음 `SPEC`의 해시 `SPEC_HASH`. 모든 결과에 VM 판·명세 해시·프로필(매개변수 포함)·프로그램 digest·입력 digest를 넣는다. 시험이 해시를 동결 → 의미 문장을 바꾸면 시험이 깨져 판을 올리게 강제 |
| 이름 | `IEEE64Strict` → `Binary64Finite`("A-Binary64-Finite") |

**결함 주입 20종 전부 검출** — 0단계 8종 + 새 12종(binary64 SUM 순차 반올림, DOT 곱마다 반올림(binary64·FX), FX SUM 단계마다 범위 검사,
영 부호 규칙, 검증기 4종, 판 표시 누락, 해시 갱신 없이 의미 문장 수정, 능력 검사 생략).

**공개 — 0.1이 새로 떠안은 것:**
- **네이티브 실행기의 비용:** C++/CUDA가 같은 의미를 내려면 **정확 누적기**가 필요하다. binary64의 `SUM`은 지수 범위 전체(약 2,100비트),
  `DOT`은 곱의 지수 범위까지(약 4,200비트) 담는 누적기 — GPU에서 무겁다. FX의 `DOT`은 `2W + log₂(항 수)`비트 정수(W=64면 128비트 이상).
  이것은 숫자 후보 비교의 **비용 항목**으로 들어간다(의미는 바꾸지 않는다).
- `SUM`·`DOT` 안의 중간값은 무한 정밀도라 **넘침은 최종 결과에서만** 판정한다(의미 문장에 명시).
- `ADD`를 여러 번 이어 쓰면 여전히 두 번 반올림된다 — **순서와 무관해야 하는 누적은 반드시 `SUM`/`DOT`으로** 써야 한다. 물리 커널
  명세(IR-N)의 규칙으로 넣을 것.
- `SPEC_HASH`는 **의미 문장**의 해시다. 구현 코드가 문장과 다르게 바뀌어도 해시는 그대로다 — 그래서 구현 소스의 digest(`IMPLEMENTATION_DIGEST`)를
  따로 계산해 두었다. 단 **이 digest는 아직 결과에 기록되지 않고**, 문장과 구현이 같은 의미라는 것은 해시가 아니라 **동작 시험(59개)과 결함 주입**이 지킨다. 해시는 "다른 의미의 결과를 같은 것처럼 비교하지 않기" 위한 표지일 뿐 구현을 증명하지 않는다.
- **아직 IEEE 의미가 "증명"된 것은 아니다.** 하드웨어 대조는 이 PC의 CPU 하나, 무작위 계열 입력 위주다. R1 단계에서 반올림 경계 바로 양옆,
  비정규/정규 경계, 최대 유한값 근처의 **어려운 입력**, 특히 제곱근의 경계 사례를 일부러 만들어 대조한다.
- 구현 중 제 실수 1건: 시험 기대값 손계산 오류(1+1+3−2.5를 1.5로 적음) — VM이 아니라 시험이 틀렸고 즉시 드러났다.

### 3.8 R1-0 — 어려운 입력 감사 (2026-09-24)

3.7의 공개 항목 "하드웨어 대조가 무작위 계열 입력 위주"를 먼저 처리했다. 네이티브 도구 설치 없이 할 수 있는 부분이다.
**mpmath 고정밀 기준 계산기(R1 본체)는 아직 아니다** — 사칙·제곱근은 참값이 유리수(또는 그 제곱이 유리수)라서 정확 유리수로 판정할 수
있고(N5 우선순위 2번), mpmath가 필요해지는 것은 초월 함수·물리 커널의 이산화 오차를 볼 때다.

| 부분 | 내용 |

  중점² 근처라는 구성만 썼다.
- 판정기는 CPython의 `float → Fraction` 변환과 `float(Fraction)`(입력 생성용)을 믿는다. 판정 자체는 전자만 쓴다.
- 하드웨어 대조는 여전히 **이 PC의 CPU 하나**.
- VM의 `SUM`·`DOT` 영(0) 부호 규칙은 IEEE에 없는 **A의 규칙**이라 판정기가 VM 명세 문장을 그대로 옮겨 적었다 — 여기서는 독립 판정이 아니다.

### 3.9 VM 0.2 — `EXP` = `deterministic_exp_v1` (2026-09-25, N3 결정에 따라)

**의미:** 표현된 입력 x의 **정확한 수학적 e^x를 프로필 규칙대로 한 번 반올림**(최근접 짝수). 넘침은 멈춤, 가장 작은 칸의 절반보다 작으면
+0, `exp(±0) = 1`. EXACT 프로필은 EXP가 없다(결과가 무리수) → 실행 전 `unsupported_operation`.

**구현자 결정 — 공개:** 3.3절 초안은 "`exp`는 A가 **알고리즘**을 정의하고 모든 실행기가 그 알고리즘을 그대로 구현"이라고 적었다. 나는
대신 **값**으로 정의했다(정확한 e^x를 한 번 반올림). 이유: VM 0.1의 일반 규칙("모든 명령은 정확한 값을 한 번 반올림")과 같고,
알고리즘에 따라 마지막 비트가 달라질 여지가 없으며, 실행기가 어떻게 계산하든 답은 하나다. 대가: 네이티브 실행기가 **정확 반올림**을
해야 한다(아래 비용). → **설계자 승인(2026-09-25, C0 계획 11.3).** 표현: EXP 의미 확정 · VM 구현은 강한 검증 통과 · 어려운 사례 탐색은 계속 확장.

**왜 정확히 계산 가능한가:** x ≠ 0이 유리수이면 e^x는 초월수다(린데만–바이어슈트라스 정리). 모든 프로필의 반올림 경계는 유리수다. 따라서
e^x는 **절대 경계 위에 있지 않고**, 참값을 감싸는 구간을 좁혀 가다 보면 양 끝이 같은 값으로 반올림되는 때가 반드시 온다(Ziv 방식).

**VM 구현(`a_numeric/exp.py`, 정수만):** x는 이진 유리수 → y = x/2^k(|y| ≤ 2^−8)를 2^−M 격자로 **바깥쪽** 반올림(e^y는 증가 함수) →
Taylor 합을 항마다 내림/올림으로 감싸고 나머지 상한을 더함 → k번 제곱(내림/올림) → `lo ≤ e^x·2^M ≤ hi`. 두 끝을 반올림해 같으면 끝,
다르면 M을 늘려 다시. 확실한 범위는 먼저 결정: binary64에서 x > 1024·0.6932이면 넘침, x < −1076·0.6932이면 +0(0.6932 > ln 2는
시험이 같은 감싸기로 e^0.6932 > 2를 확인). 판 `0.2`, 명세 해시 갱신(시험이 동결).

**R1 독립 판정기(`audit/independent_numeric/exp_judge.py`, `a_numeric` import 금지):** mpmath의 **구간** exp로 [a, b]를 얻고, 구간 전체가
주장된 결과 하나로 반올림되는지 본다. 경계에 걸치면 정밀도를 올리고, 상한(4,096비트)에서도 걸치면 "판정 불가"(틀렸다고 하지 않음).

**판정기 검증 중 발견한 판정기 버그:** 구간 끝값을 `mpmath.mpf`로 바꿔 분수로 만들었는데, 그 변환이 **전역 정밀도(200비트)로 반올림**한다 —
끝값이 **안쪽으로** 움직일 수 있어 판정기가 엄밀하지 않았다. 판정기 자체 시험(알려진 e의 자릿수)이 잡았다 → 원시 값에서 정확히 변환하도록
고침. 그 시험을 만들며 **내 시험도 틀렸다**: 98자리에서 자른 e를 "e"로 썼는데 그것은 e의 하한이다 → [자른 값, 자른 값 + 10⁻⁹⁸]과
겹치는지로 고침.

**판정기 자체 검증:** e의 자릿수 포함, exp(x)·exp(−x) ∋ 1, 범위 문턱(e^710 > 2^1024, e^−746 < 2^−1076) 증명, 정답의 한 칸 이웃을
전부 거부(1,500건 이상).

**어려운 입력 1,278건 + 고정소수점:**

| 모음 | 내용 |
|---|---|
| 구성한 중점 근처 400 | 작은 \|x\|에서 x = ln(중점)에 가장 가까운 binary64 — 가장 가까운 것은 중점에서 **2.8×10⁻¹⁷ ulp**(판정에 약 110비트 필요) |
| 찾은 중점 근처 150 | sha256 표본 6,000개 중 중점에 가장 가까운 것(최근 3.6×10⁻⁴ ulp, \|x\| 최대 745) |
| 경계 128 | 넘침 경계 2^1024 − 2^970, 2^1023, 최소 비정규 수의 절반(+0 경계), 비정규/정규 경계, \|x\| ≈ 2^−53, ±0, VM의 조기 결정 문턱 |
| 넓은 범위 600 | 유한 binary64 전 범위 |
| 고정소수점 | FX(8,3)·FX(12,6)·FX(6,0) **전수**, FX(64,32) 335 |

**결과: VM은 전부 정확 반올림**(판정기 기준). C 라이브러리 `exp`는 구성한 400건 중 204건에서 VM과 다르고, 판정기로 보면 **C 라이브러리가
틀린 것**(시험은 50건 이상 틀림을 요구 — 이 입력들이 "잘 만든 것만으로는" 통과 못 할 만큼 어렵다는 확인).

**결함 주입 6종 전부 검출:** 한 번의 고정 정밀도(정제 없음) · 제곱 한 번 더 · Taylor를 약 48비트에서 끊고 나머지 상한 없음 · 넘침 문턱
709 · +0 문턱 −700 · 플랫폼 `exp`(C 라이브러리) 사용.

**한계 (공개):**
- Taylor를 **약 64비트**에서 끊는 결함은 **못 잡았다**: 그 오차(≈ 6×10⁻⁵ ulp)가 찾은 사례의 중점 거리(≥ 3.6×10⁻⁴ ulp)보다 작다. 구성한
  사례는 훨씬 가깝지만 \|x\|가 작아 Taylor가 금방 수렴한다. 즉 **큰 \|x\|에서 아주 가까운 사례**가 부족하다. 문헌의 최악 사례(Lefèvre 등의
  전수 탐색 결과)는 쓰지 않았다 — 필요하면 다음 단계에서 찾기를 늘린다.
- VM의 EXP는 한 번에 약 1ms(기준용이라 느려도 됨).
- **네이티브 비용:** B0/B1/B2도 정확 반올림을 내야 하므로 Ziv 방식(필요하면 정밀도 증가)이 필요하다. GPU에서는 고정폭이므로 B2 누적기처럼
  **최대 정밀도 계약**(넘으면 실행 전·중 명시 거부)이 필요할 것이다 — 네이티브 단계에서 설계.

### 4.1 B0·B1·B2 구현 결과 (2026-09-25)

**범위(설계자 지시):** C0 세계 엔진이 아니라 **수치 backend 검증 틀**. VM 0.1의 의미를 바꾸지 않는다. 퍼텐셜은 **고르지 않는다**.
코드: `a_numeric_native/`. 시험: `tests/test_a_numeric_native_b0.py`(11개), `tests/test_a_numeric_native_b1.py`(9개), `tests/test_a_numeric_native_b2.py`(8개 → 4.2 후 25개).

**구조:** 네이티브 실행기는 VM과 **같은 명령 형식의 직선 프로그램**(CONST ADD SUB MUL DIV NEG ABS SQRT CMP SUM DOT)을 받아
실행한다. `harness.py`가 같은 프로그램을 VM과 실행기에 보내고 레지스터·분기 기록(`represented_margin` 포함)·멈춤(위치·이유)을
비교한다. 실행기는 기대값을 받지 않는다. 네이티브 소스에 VM 호출이 없다는 것도 시험한다.

| | 방법 |
|---|---|
| binary64 사칙·제곱근 | 하드웨어(x64 SSE2, MSVC `/fp:strict`) — 정확 반올림이 보장되는 연산. 결과가 유한하지 않으면 `overflow` 멈춤, 0으로 나누기·음수 제곱근은 먼저 멈춤 |
| SUM·DOT | 작은 임의 정밀도 정수로 **정확 합 → 1회 반올림**(부동소수점 합산으로 대체하지 않음). 영(0) 부호 규칙 포함 |
| CONST | 유리수 → 정확 나눗셈 → 1회 반올림 |
| FX(W, F) | 전부 정확 정수(넓은 곱, 최근접 짝수, 범위 검사 1회) |
| B1 병렬 | 프로그램을 T개 스레드에 나눠 실행(출력은 입력 순서), SUM·DOT 항을 T개 연속 조각으로 나눠 조각별 **정확** 부분합 → 정확히 합침 → 1회 반올림. 정수 덧셈은 결합 법칙이 성립하므로 T가 값을 바꿀 수 없다 |

FX는 128비트 정수(W ≤ 64). 장치 산술은 `anvm_core.hpp`와 **별도로 새로 작성**. nvcc `-fmad=false --prec-div=true --prec-sqrt=true -ftz=false -arch=sm_89` |

### 4.2 E9 완료와 B2 누적기 폭 계약 (2026-09-25, 설계자 지시)

**E9 — 격자·발사 배치·프로그램 순서.** 4.1에서는 블록 크기만 바꿨다. B2를 고쳐 한 번의 발사(launch)가 프로그램 C개를 맡고,
그 발사의 블록 G개가 격자 보폭(grid-stride)으로 나눠 실행하게 했다(블록 b가 b, b+G, b+2G, …번째). 이제 블록 크기 B, 격자 블록 수 G,
발사 묶음 C를 따로 줄 수 있다.

| 배치 (B, G, C) | 뜻 |
|---|---|
| (64, 기본, 기본) | 발사 하나에 프로그램 = 블록(기존) |
| (64, 1, 기본) | **블록 하나가 모든 프로그램** |
| (64, 7, 기본), (128, 5, 7), (256, 64, 333) | 프로그램 수가 G·C로 나누어떨어지지 않음 |
| (32, 3, 1000), (32, 기본, 997) | 마지막 발사가 덜 찬 묶음 |
| (64, 1, 1) | 발사 하나에 프로그램 하나 |
| + 프로그램 순서 섞기 2가지 | 입력 파일 순서를 sha256으로 섞어 보내고 결과를 원래 순서로 되돌려 비교 |

**결과:** 9개 사례 모음 전부, 8개 배치 전부, 섞은 순서 전부에서 B2 = VM.

**배치 의존 결함 3종 주입 — 각각 어떤 배치에서는 숨는다(그래서 배치를 바꿔야 한다):**

| # | 결함 | 숨는 곳 | 잡히는 곳 |
|---|---|---|---|
| 208 | "블록 하나 = 프로그램 하나" 가정(격자 보폭 무시) | **기본 배치(G = C) — 4.1 시험이 쓰던 바로 그 배치** | G < C인 배치 전부, 약 10만 건 |
| 209 | 덜 찬 마지막 발사를 건너뜀 | C = 1 | C가 프로그램 수를 나누지 못하는 배치 |
| 210 | `blockIdx.x == 1`인 블록이 항 하나를 빠뜨림 — 결과가 **어느 블록이 실행했는가**에 의존 | G = 1 | G ≥ 2 |

**B2 정확 누적기 폭 계약.** VM의 SUM·DOT은 항 수와 무관하게 정확하다. B2는 고정폭(4,480비트 2의 보수)이므로 한계를 계약으로 둔다.

| 항목 | 값 |
|---|---|
| binary64 DOT 한 항 | `m_a·m_b·2^(e_a+e_b)`, `m < 2^53`, `e ∈ [−1074, 971]`. `2^−2148` 단위로 이동량 `∈ [0, 4090]`, `m_a·m_b < 2^106` → **\|항\| < 2^4196** |
| N항 합 | `< N·2^4196 ≤ 2^(4196 + ⌈log₂N⌉)`, 2의 보수 부호 1비트 추가 |
| **`NATIVE_MAX_REDUCTION_TERMS`** | **65,536 = 2^16** |
| 필요 폭 | 4196 + 16 + 1 = **4,213비트 ≤ 4,480** (여유 267비트). 소스의 `static_assert`가 컴파일 때 확인 |
| 다른 누적 | binary64 SUM 항 < 2^2098(단위 2^−1074), FX(W ≤ 64) 곱 ≤ 2^126 — 더 적게 필요. CMP 여유 < 2^2099 ≤ 2,176비트 버퍼 |
| 넘으면 | 실행 전에 **배치 전체를 거부**(종료 코드 6, `REJECTED native_reduction_too_long`, 결과 파일 없음). A의 의미가 아니라 실행기 능력 한계 — VM은 그 프로그램을 실행한다 |

4,480비트로는 이론상 2^283항까지 안전하지만, **시험한 것만 계약한다** — 그래서 2^16.

**시험:** N = 65,536항에서 VM과 일치(평범한 값 · MAX×MAX N개 → 넘침 멈춤 · +MAX²/−MAX² 상쇄 후 최소 비정규 수만 남음 · SUM 같은 둘 ·
**감김 탐침**), N + 1에서 B2는 거부, B0·B1은 한계가 없어 N + 1도 VM과 일치.

**구현 중 발견 — 감김(wraparound)은 모듈러 산술이다.** 누적기를 4,192비트로 줄인 결함(211)을 처음에는 **못 잡았다**: 2의 보수 감김은
2^W를 법으로 한 정확 산술이라, **최종 합이 폭 안에 들어오면 중간에 넘쳐도 답이 맞는다.** 상쇄 사례·넘침 사례로는 드러나지 않는다.
드러내는 것은 "참값은 거대하지만 2^W를 법으로는 작은" 합이다 → **감김 탐침:** `2^15 × (2^1023·2^1023) + 2^−1074`, 참값 = 2^4209 + 1
(단위 2^−2148). W ≤ 4,209비트면 "+1"만 보여 최소 비정규 수를 답하고(참값은 넘침 멈춤), 이것으로 211을 잡았다.

### 4.3 L2 수치 구조 — 퍼텐셜 없이 (2026-09-25)

퍼텐셜이 계산할 힘 대신 **시험용 충격량 J를 입력으로** 준다(`a_numeric_native/l2.py`, `tests/test_a_numeric_native_l2.py`).
운동량을 상태로 두고, 쌍 (a, b)마다 a는 +J, b는 −J(`NEG`, 정확)를 받으며, 입자·축마다 새 운동량은 **옛 운동량과 모든 기여를 하나의
`SUM`으로**(순서 무관, 1회 반올림) 만든다. 계 156개(입자 4,724, 쌍 6,306): 2입자 한 쌍, 3·5·8·16입자 전쌍, 64입자 400쌍, **한 입자에
2,049쌍**이 몰리는 별 모양 — binary64·FX(64,32) 각각.

| 확인 | 결과 |
|---|---|
| +J / −J가 정확히 같은 크기 | 모든 쌍에서 `−J`가 정확히 J의 부호 반전. FX 2입자: Δp_a = +J, Δp_b = −J 비트 단위 |
| 여러 쌍의 힘을 한 입자에 합산 | 최대 2,050항 SUM |
| 쌍 순서 · 쌍 방향 (a,b,J)→(b,a,−J) · 입자 재명명 | 새 운동량 **비트 동일** |
| B0 / B1(T=1·2·4·8·12) / B2(블록 1·32·256, 격자·묶음 3가지, 순서 섞기) | 전부 VM과 비트 동일 |
| **구조 결함 주입:** SUM 대신 ADD를 이어 붙여 누적(항마다 반올림) | 실행기들은 **서로 일치**(같은 프로그램이므로) → 실행기 비교로는 못 잡음. **불변성 검사가 잡음**(binary64 계에서 15건). 실행기 차등 시험과 불변성 시험이 서로 다른 것을 지킨다 |
| **총 운동량** | **FX: 모든 계·축에서 정확히 보존**(정수 합은 결합 법칙). **A-Binary64-Finite: 234개 축 합계 중 214개에서 정확 잔차 ≠ 0** — 입자마다 새 운동량을 한 번 반올림하므로. 잔차는 항상 그 반올림들의 반-ulp 합 이하(시험이 경계를 확인). 실행기 결함이 아니라 **수 체계의 성질**이다 |

### 4.5 네이티브 EXP — B0 · B1 · B2 (2026-09-25)

VM 0.2의 `EXP`(정확한 e^x를 한 번 반올림)를 세 실행기에 넣었다. 정확 반올림 값은 하나뿐이므로 **방법이 달라도 옳으면 비트가 같다** —
그래서 VM을 베끼지 않고 따로 썼다.

| | 방법 |
|---|---|
| B0 · B1 (`anvm_core.hpp`) | 임의 정밀도 정수로 e^x를 감쌈(바깥쪽 반올림 Taylor + 제곱) → 양 끝이 같게 반올림될 때까지 정밀도 증가(상한 없음). **확실한 범위는 VM과 다른 문턱**으로 결정: x ≥ 710 → 넘침, x ≤ −746 → +0(판정기가 증명한 사실), FX는 x ≥ W → 넘침, x ≤ −(F+2) → 0 |
| B2 (`b2_cuda.cu`) | 장치 코드로 별도 작성(고정폭 5,632비트 정수, 블록별 전역 메모리 작업 공간, 스레드 0이 계산). **정밀도 상한 계약 `NATIVE_EXP_MAX_ATTEMPTS = 4`**(추가 정밀도 64·128·256·512비트) — 넘으면 틀린 답 대신 **배치 전체 거부**(종료 코드 7, `native_exp_precision_exhausted`) |

**결과:** EXP 사례 6,029건(R1 어려운 입력 1,278 + FX(8,3)·(12,6)·(6,0) 전수 + FX(64,32) 335)과 P-c 연쇄(가짜 매개변수 — C0 물리 아님)에서
**B0 = B1(T=1·4·12) = B2(블록·격자 배치 전부) = VM** 비트 일치. 기존 사례 모음 9개와 함께 E9 배치 시험 전체에 들어감.

**결함 주입 5종 전부 검출:** B0 플랫폼 `exp()`(233건) · B0 정제 없는 낮은 정밀도(1,068) · B2 CUDA `exp()`(198) · B2 정제 없는 낮은
정밀도(593) · B2 정밀도 상한 도달 → 거부 경로 동작.

**구현 중 같은 실수 두 번:** "낮은 정밀도" 결함을 만들 때 M을 **절대 눈금**으로 잡아 1 근처 결과에는 여전히 1,100비트가 넘는 정밀도가
남아 결함이 결함 노릇을 못 했다(VM 시험 때 한 번, B2에서 또 한 번). 결함 주입이 "잡혔다/안 잡혔다"만이 아니라 **결함이 실제로 결과를
바꾸는가**를 먼저 봐야 한다는 교훈([VERIFICATION_LIMITS_AND_LESSONS.md](VERIFICATION_LIMITS_AND_LESSONS.md)의 기존 교훈과 같은 종류).

**E7 — EXP에 대해:** P-c(N3-A)가 요구하는 연산 중 새로 필요했던 것은 EXP뿐이다(SQRT·DIV·MUL은 이미 있음). F1 고정소수점과 F2a binary64
모두 **VM이 정의한 한 가지 값을 직렬 CPU · 병렬 CPU · GPU가 같은 비트로 낸다** → **E7(EXP) 통과**, 단 B2는 위 정밀도 상한 계약 안에서.
N3-B(A·ρ·r_min·차단)가 정해지면 그 식 전체로 다시 확인해야 한다(예: 차단 함수가 새 연산을 요구할 수 있음).

**한계 (공개):**
- B2의 정밀도 상한이 실제로 부족한 입력은 **찾지 못했다**(모든 사례가 첫 시도에서 결정됨). 상한은 증명이 아니라 **선언**이고, 부족하면
  조용히 틀리지 않고 거부한다는 것만 시험했다.
- B2 EXP는 느리다 — 격자 1블록 배치에서 EXP 6,029건에 약 18초. 최적화 안 함. 네이티브 시험 전체가 약 5분으로 늘었다.
- 어려운 사례 탐색 확장(큰 |x|에서 중점에 아주 가까운 입력)은 설계자 지시대로 계속 과제.

## 7. Physics IR / DSL 요구사항 — C1에서 드러난 수정사항 (설계자, 2026-09-26)

**지위:** 요구사항 기록. **DSL·compiler는 아직 구현하지 않는다**(7.6). 근거는 C1-A(Ar–Ar 기준 평가기·B0/B1/B2)와 C1-B1(두 원자 동역학) 작업이다.

### 7.1 A-Numeric VM의 역할 수정

C1에서 실제로 필요했던 의미:

```
round_profile( V_real( sqrt(R²) ) )                    -- C1-A 동결 V, C1-B1의 대수적 입력 확장
round_profile( F_real(R) · Δx / R · Δt/2 )              -- C1-B1 충격량 J
```

원시 연산마다 반올림하는 것이 아니라 **합성된 수학적 양 전체의 참값을 평가한 뒤 지정된 지점에서 한 번 반올림**해야 한다. VM의 명령(ADD·MUL·EXP …,
정확 합산은 SUM·DOT뿐)으로는 이것이 표현되지 않아 C1-A·C1-B1은 **VM 밖에서** 구현했다. 역할을 다음처럼 나눈다.

```
Physics IR                연속적인 물리 의미 (종, 질량, 상호작용 에너지, 힘 = −∇E, 보존 대상, 경계, 시간 진화)
   ↓
Evaluation / Semantic IR  정확히 어떤 수학적 양을 계산하며 어디에서 quantize하는가
   ↓
A-Numeric VM              원시 숫자 연산, 반올림, 구간 감싸기 등 하위 수치 의미
   ↓
실행기                     위 의미의 Python(기준) / C++(B0·B1) / CUDA(B2) 구현
```

A-Numeric VM은 **폐기하지 않는다.** 원시 수치 의미의 검증된 바닥(결함 주입·R1 어려운 입력 감사 통과)으로 유지하되, A 전체 계산 의미의 유일한
최상위 정의자로 보지 않는다.

### 7.2 Evaluation IR은 반올림 경계를 명시해야 한다

`round(a·b·c)`와 `round(round(a·b)·c)`는 **같은 IR로 내려가면 안 된다.** (C1-B1 D5가 금지한 "반올림한 힘 × Δt → 재반올림"이 바로 이 차이다 —
`tests/test_c1b1_two_atom.py`가 두 경로의 비트가 다른 입력이 있음을 보인다.)

IR이 최소한 표현해야 하는 의미:

| 의미 | C1의 예 |
|---|---|
| 정확한 합성식 (exact composite expression) | Δr = r_j − r_i, R² = Δr·Δr, drift 우변 r + p·Δt/m |
| 식 전체를 정확히 한 번 반올림 (correctly-rounded whole expression) | V(√R²), F(R), J_k |
| 연산마다 반올림 (operation-by-operation quantization) | VM 프로그램의 ADD·MUL … |
| 정확 누적 후 한 번 반올림 (exact accumulation then one rounding) | VM의 SUM·DOT |
| 적용 영역 감시 (domain guard) | r_min, drift 선분 최소 거리 |
| 결정 불가 시 거부 (undecided / refusal) | `ReferenceUndecided`, B0 `refuse undecided`, B2 `device_precision_cap` |
| 출처 고정 상수 (source-versioned constants) | CODATA 2018 a₀(C1-A), ⁴⁰Ar 질량 NIST + mₑ CODATA 2022(C1-B1) |

**Ziv 방식·구간 정밀화는 이 의미를 구현하는 backend 전략**이지 물리 식에 박는 알고리즘이 아니다(C1-A: 기준은 분수 연산, B0는 정수 구간,
B2는 고정폭 장치 구간 — 모두 같은 비트).

### 7.3 상태별 숫자 표현은 계약에 포함한다

위치·운동량 등의 저장 profile은 **실행기가 고르는 최적화 항목이 아니다.** C1-B1에서 binary64 절대 위치가 표현 보존 평행이동에서도 상대 궤적을
바꿨다(12판에서 탈락). IR은 물리 상태마다 최소한 다음을 선언할 수 있어야 한다.

- 저장 표현 (storage representation)
- quantization 지점 (어느 대입에서 반올림하는가)
- 넘침·거부 규칙 (overflow / refusal)
- **동점(tie) 규칙까지 포함한 반올림 지점** — C1-B1 사례(2026-09-26): `round(r + p·Δt/m)`의 짝수 반올림은 정확한 동점에서 r의 홀짝을 따라
  평행이동 불변성을 깬다. `r + round(p·Δt/m)`은 같은 비트(동점 제외)이면서 깨지 않는다. 어디서 반올림하는지가 의미의 일부다.
- 파생량의 정확 평가 여부 (예: Δr·R²는 반올림 없이)

상태 표현은 연속 물리 법칙 자체와 구분하지만, **A의 이산 세계 의미(discrete world semantics)의 일부**로 취급한다. 물리량별 profile 분리
(위치·운동량·에너지·누적기)는 12판 5항대로 아직 허용 후보일 뿐이다.

### 7.4 DSL 원본은 실행기에서만 단일화한다

장기 목표: **하나의 Physics IR/DSL 원본**에서 기준 실행기, C++ B0/B1, CUDA B2를 생성해 같은 물리식을 실행기마다 손으로 옮겨 적는 구조를 없앤다.

근거(측정 사실): Lang 2024의 V·F 식은 지금 **다섯 번** 따로 옮겨 적혀 있다 — 동결 기준(`a_reference/ar2_lang2024.py`, 분수), C1-B1 구간 모듈
(`a_reference/c1b1_two_atom.py`, 정수), B0/B1(`a_physics_native/ar2_core.hpp`), B2(`a_physics_native/ar2_b2.cu`), 감사
(`audit/independent_physics/ar2_lang2024.py`, mpmath). 앞의 넷이 실행기 쪽이다. 퍼텐셜 하나에 네 번이면 종·상호작용이 늘 때 감당할 수 없다.

### 7.5 독립 감사는 compiler와 독립성을 유지한다

DSL/compiler가 생성하는 **self-check**와 **독립 감사**를 구분한다.

| 구분 | 예 | 지위 |
|---|---|---|
| compiler 생성 self-check | 보존량 검사, CPU/GPU 차등 검사, domain 검사, fingerprint 검사 | 허용하고 적극 활용. **독립 감사가 아니다** |
| 독립 감사 | 원 논문·원 데이터·원 Fortran → 별도의 수학적 구현 | DSL에서 생성하지 않는다 |

이유: DSL 원본이나 lowering 오류는 **모든 실행기에 공통으로 복제**되어 실행기끼리 비교해서는 잡히지 않는다("검사기가 검사 대상과 같은 함수를 쓰면
자기 결함을 못 잡는다", 2026-09-21 `verify_trace()` 사례의 확대판). 식을 한 번만 쓰는 곳은 실행기 쪽이고, 검증 쪽은 일부러 따로 쓴다.
**compiler 자체도** 차등 시험·결함 주입·독립 기준 계산의 대상이다.

### 7.6 DSL을 지금 구현하지 않는다

C1-A/B1만 보고 만들면 **쌍 거리 퍼텐셜에 과적합된 언어**가 될 위험이 있다. 지금은 요구사항만 축적한다.

- C1-A/B1: 2체 거리 기반 상호작용
- **C1-C**: 3체 비가산 상호작용과 배치 의존성 — 두 번째 상호작용 구조

**첫 구현 시점 후보 = C1-C.** 최소 Physics IR/DSL v0를 설계해 2체와 3체를 모두 자연스럽게 표현하는지 확인한다. **C2-N 진입 전에** 각도·여러 종·
배치 의존 반응성까지 고려해 언어 구조를 다시 검토한다.

### 7.7 DSL에 생명 현상 자체를 넣지 않는다

DSL의 표현 대상은 **물질, 에너지, 상호작용, 상태, 경계, 시간 진화**다. `cell`, `DNA`, `divide`, `metabolism`, `bond_if_close` 같은 생명·현상
전용 명령을 물리 기본 문법으로 만들지 않는다(헌법 제4조, RULES "고수준 명령 금지"). 그 현상은 하위 물리에서 결과로 나타나야 한다 —
"배치 → 에너지 → 기울기에서 힘 → 이동"은 되고, "IF 가까우면 THEN 결합 생성"은 안 된다.

### 7.8 C1에서 모은 나머지 요구사항 (구현자 추가 제안 — 설계자 판정 아님)

- **적용 영역과 거부를 언어 수준에서:** `physics_domain_exceeded`(물리)와 실행기 능력 한계(`beyond_native_range`, `device_width` …)를 구분해 선언.
- **계약 판과 출처:** 매개변수 지문, 계약 판 이름, 원자료 해시, fixture와 그 생성 커밋 — 동결과 재현의 단위.
- **불변성은 입력 단계와 동역학 단계를 따로:** 교환·회전·평행이동을 IR이 선언된 상태 표현 위에서 검증 가능해야 한다(7.3).
- **결정론 = 배치 독립:** 스레드 수·블록·발사 묶음이 결과를 바꾸지 않는다는 것은 IR의 정확 누적·한 번 반올림 의미에서 나온다(C1-A B1/B2 E9).
