# 01. 프로젝트가 이해하기 어려워진 이유

*복잡성의 원인을 분리하고, 무엇을 단순화해야 하는지 다시 정의한다*

| **\[출발점\]** 프로젝트를 직접 만들고 있는데 설명을 들을수록 “내가 뭘 만들고 있는지 모르겠다”는 느낌이 생겼다. 이것은 세계의 목표가 틀렸다는 뜻보다, 물리 엔진·버전·검증·문서·거버넌스가 한꺼번에 설명되면서 핵심 그림이 묻혔다는 신호로 해석했다. |
|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|

# 1. 복잡해진 것은 세계 자체만이 아니었다

초기에는 입자가 움직이고, 만나고, 결합하고, 구조를 만드는 문제를 다뤘다. 이후 실제 결과를 왜곡하는 ID 순서, 상태 소실, 운동량 보존 문제, 기하 부족 등이 발견되면서 이를 막기 위한 문서·버전·테스트·감사 구조가 급격히 늘어났다.

```text
원래 관심

입자 → 충돌 → 결합 → 구조 → 더 복잡한 현상


점점 함께 따라온 것

버전 / digest / known defects / legacy semantics / governance /

fault injection / AST 검사 / relabel invariance / 문서 동기화
```

각 장치는 생긴 이유가 있었지만, 어느 순간 “세계가 어떻게 작동하는가”보다 “프로젝트를 어떻게 보존하고 검증하는가”가 설명의 앞자리를 차지했다. 그래서 사용자인 설계자가 세계의 직관을 잃기 시작했다.

# 2. 잘못된 단순화와 필요한 단순화

| **\[잘못된 단순화\]** 현실과 비슷한 법칙을 표현하려는 목표를 포기하고, 몇 가지 충돌 결과나 규칙을 하드코딩하여 세계를 작은 틀 안에 가두는 것. |
|-----------------------------------------------------------------------------------------------------------------------------------------------|

| **\[필요한 단순화\]** 세계의 표현력은 유지하되, 사람이 머릿속에 들고 있어야 하는 관리 규칙·버전 세부사항·테스트 철학은 문서와 자동화에 맡기는 것. |
|---------------------------------------------------------------------------------------------------------------------------------------------------|

# 3. 앞으로 사람이 기억해야 하는 핵심

1.  A는 세계를 계산한다. 결과를 미리 정하는 것이 아니라, 세계 언어로 선언된 법칙과 현재 상태에서 다음 상태를 계산한다.

2.  B는 세계를 연구한다. 관찰하고, 가설을 만들고, 실험을 제안하고, 실패와 이상치를 기억한다.

3.  World Language는 결과 목록이 아니라 세계의 구성 요소·상태·관계·법칙·사건을 표현하는 언어가 되어야 한다.

4.  기존 버전·digest·호환성은 테스트가 지킨다. 설계자가 매번 머릿속으로 관리할 필요는 없다.

5.  새 자유도는 “그 결과를 만들기 위해” 추가하는 것이 아니라, 현재 상태로 구분할 수 없는 물리적 차이를 표현하기 위해 추가한다.

# 4. 프로젝트를 설명하는 가장 짧은 문장

| **\[현재 핵심\]** 현실의 법칙을 표현할 수 있는 세계 언어를 만들고, 그 언어로 정의된 세계에서 A가 실제 상태 변화를 계산하며, B가 그 세계를 연구하고 새로운 세계·가설·실험을 제안하게 만든다. |
|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|

# 5. 복잡성이 다시 커질 때 확인할 질문

- 지금 복잡해진 이유가 세계 표현력 때문인가, 아니면 관리 절차 때문인가?

- 새 규칙이 결과를 직접 박아 넣는가, 아니면 결과를 갈라놓는 조건을 표현하는가?

- 이 세부사항을 사람이 외워야 하는가, 아니면 테스트·문서·검증기가 대신 관리할 수 있는가?

- 새 기능이 프로젝트의 원래 목표를 넓히는가, 아니면 특정 예시 하나에 맞춰 틀을 좁히는가?

| **\[정리\]** “프로젝트를 단순하게”는 “물리를 단순하게”가 아니다. 앞으로는 세계의 자유도는 넓히고, 관리 복잡도는 자동화·문서화로 뒤로 보낸다. |
|----------------------------------------------------------------------------------------------------------------------------------------------|
