# B0.6 인과 시간축 및 Evidence 해석 규칙

**문서 상태:** 필수 규칙 / 구현 호환성 계약  
**적용 범위:** B0.4 Trace, B0.5 Mechanism Test, B0.6 Causal Path Builder 및 이후 B 계열  
**목적:** 시간 순서 오해, 동시 사건의 잘못된 인과 직렬화, role 의미 혼동을 방지한다.

---

# 1. 핵심 원칙

B0.6 이후의 인과 분석은 다음 세 가지 규칙을 반드시 지킨다.

```text
1. observation_seq는 "한 trace 내부의 실제 관측 순서"로만 사용한다.

2. 같은 AtomicChangeGroup 안의 변화끼리는
   근거 없이 인과 순서를 만들지 않는다.

3. MechanismCandidate의 시작 role과
   실제 관찰 대상 role을 혼동하지 않는다.
```

이 세 규칙은 단순 구현 편의가 아니라
B가 잘못된 인과관계를 학습하지 않게 하기 위한 필수 계약이다.

---

# 2. 규칙 1 — observation_seq의 의미

`observation_seq`는 KernelObserver가 실제로 호출된 순서를 나타내는
단조 증가 번호다.

예:

```text
seq=0
seq=1
seq=2
seq=3
...
```

이 값은 다음 목적에 사용한다.

```text
한 trace 내부에서
무엇이 먼저 관측되었는지 판단
```

즉:

```text
seq=10
↓
seq=11
↓
seq=12
```

라는 순서는 신뢰할 수 있다.

---

# 3. observation_seq를 사용하면 안 되는 경우

서로 다른 실행의 `observation_seq`를 직접 비교해서는 안 된다.

예:

```text
Baseline:
seq=4

Intervention:
seq=4
```

라고 해서 두 시점이 동일한 물리적 순간이라는 뜻은 아니다.

각 trace의 seq는 독립적이다.

금지:

```text
baseline.seq == intervention.seq
→ 같은 물리 순간
```

---

# 4. 서로 다른 실행을 비교할 때

Baseline과 Intervention을 비교할 때는 다음과 같은 구조적 대응을 사용한다.

```text
- 같은 실험 단계
- 같은 role
- 같은 field
- 같은 engine phase
- 같은 비교 목적
- 필요한 경우 동일한 시작 상태 digest
```

`observation_seq`는 각 trace 내부 순서를 보존하는 용도이며,
cross-run timestamp로 사용하지 않는다.

---

# 5. tick / phase의 의미

`tick`과 `phase`는 시간 정렬의 절대 기준이 아니다.

역할:

```text
tick
= A가 기록한 simulation tick 정보

phase
= kernel이 어떤 처리 단계에 있었는지 설명

observation_seq
= 실제 observer 호출 순서
```

따라서 실제 시간 정렬은:

```text
observation_seq
```

를 기준으로 한다.

---

# 6. 규칙 2 — AtomicChangeGroup 내부 순서 금지

같은 `AtomicChangeGroup`에 포함된 변화들은
현재 관찰 해상도에서 동일한 관측 순간에 함께 확인된 변화들이다.

예:

```text
AtomicChangeGroup

- heated_cell.energy: 2 → 0
- target_bond.exists: true → false
- particle_a.kinetic_energy: 0 → 3
- particle_b.kinetic_energy: 0 → 3
```

이 경우 B가 알 수 있는 것은:

```text
이 변화들이 같은 관측 순간에 함께 나타났다.
```

까지다.

---

# 7. AtomicChangeGroup에서 금지되는 추론

다음처럼 임의의 순서를 만들면 안 된다.

```text
heat 소비
→ bond 제거
→ particle 방출
```

또는:

```text
bond 제거
→ heat 소비
```

현재 evidence가 내부 순서를 제공하지 않는다면
둘 다 근거 없는 추론이다.

---

# 8. AtomicChangeGroup의 올바른 표현

다음과 같이 공통 사건 또는 동시 변화 묶음으로 표현한다.

```text
        [Atomic Event]
          /    |    \
         /     |     \
heat 소비   bond 제거   particle 방출
```

즉:

```text
AtomicEvent
→ effect A
→ effect B
→ effect C
```

형태는 가능하다.

하지만 effect끼리 직접 causal edge를 만들려면
별도의 evidence가 필요하다.

---

# 9. AtomicChangeGroup을 분해할 수 있는 경우

후속 실험 또는 더 세밀한 instrumentation을 통해
내부 순서가 실제로 확인되면 분해할 수 있다.

예:

```text
새로운 관측:

A
↓
B
↓
C
```

가 명확히 실측되면 기존 atomic group을
더 세밀한 인과 경로로 갱신할 수 있다.

단, 과거 기록은 삭제하지 않고
새 evidence에 의해 해상도가 높아졌음을 기록한다.

---

# 10. 규칙 3 — MechanismCandidate의 role 의미 구분

현재 B0.4 구조에서 `MechanismCandidate.source_role`은
"이 candidate가 실제로 분석하는 role"과 동일하지 않을 수 있다.

현재 의미는 대략 다음과 같다.

```text
source_role
= 탐구가 시작된 개입/관심 출발 role

candidate.path의 role
= 실제 candidate가 관찰한 role
```

이 둘을 같은 의미로 사용하면 안 된다.

---

# 11. 잘못된 사용 예

금지:

```text
candidate.source_role
→ 이 MechanismCandidate가 다루는 실제 관찰 role
```

이라고 가정하는 것.

이 가정은 B0.6에서 실제로 잘못된 role 간 causal edge를 만들 수 있다.

---

# 12. 현재 안전한 사용 규칙

현재 구조를 유지하는 동안,
MechanismCandidate가 실제로 관찰하는 role은
candidate의 path/evidence를 통해 확인한다.

예:

```text
candidate.path[0].role
```

또는 path 전체가 동일 role이라는 기존 계약을 검증한 뒤 사용한다.

단, 빈 path에서는 이를 사용할 수 없으므로
명시적인 실패 처리가 필요하다.

---

# 13. 권장 후속 리팩터링

장기적으로는 의미를 명확히 분리하는 필드를 권장한다.

예:

```text
investigation_source_role
observed_role
```

의미:

```text
investigation_source_role
= 조사가 시작된 원인/개입 측 role

observed_role
= 이 MechanismCandidate가 실제로 분석하는 role
```

이름은 구현자가 기존 코드 스타일에 맞게 정할 수 있다.

중요한 것은 두 의미를 분리하는 것이다.

---

# 14. 이 리팩터링은 즉시 필수는 아님

현재 코드가 다음 조건을 만족한다면
B0.6 완료를 위해 즉시 구조를 바꿀 필요는 없다.

```text
- candidate.path를 통해 실제 role을 정확히 찾을 수 있음
- 빈 path를 안전하게 처리함
- source_role을 observed_role로 잘못 사용하지 않음
- 테스트가 이 계약을 고정함
```

대신 기술 부채 문서에 기록한다.

---

# 15. causal_timeline 정규화 규칙

Raw trace는 원본 evidence이므로 가능한 한 보존한다.

B0.6은 Raw trace를 바로 causal path로 사용하지 않는다.

순서:

```text
Raw Trace
↓
observation_seq 기준 정렬
↓
인접하고 동일한 state digest의 중복 관측 병합
↓
CanonicalMoment
↓
실제 상태 변화 추출
↓
StateChangeEvent
↓
같은 moment의 변화 그룹화
↓
AtomicChangeGroup
↓
CrossRoleTimeline
↓
Causal Path Builder
```

---

# 16. 동일 순간 병합 규칙

두 snapshot을 같은 `CanonicalMoment`로 합치려면 최소한:

```text
1. observation_seq상 인접
2. full state digest 동일
```

을 만족해야 한다.

`tick`이나 `phase` 이름만 보고 병합하지 않는다.

---

# 17. full state digest를 사용하는 이유

추적 중인 몇 개 field만 같다고 해서
실제 세계 전체 상태가 같은 것은 아니다.

따라서:

```text
tracked values equal
```

만으로 병합하지 않는다.

반드시 가능한 경우:

```text
CausalWorldState 전체 digest
```

를 비교한다.

---

# 18. 실제 변화만 사건으로 만든다

다음은 사건이 아니다.

```text
energy = 2
energy = 2
energy = 2
```

값이 유지된 것뿐이다.

다음은 실제 변화 사건이다.

```text
energy
2 → 0
```

따라서 `StateChangeEvent`는
직전 canonical moment와 비교해 실제 값이 바뀐 경우에만 만든다.

---

# 19. 같은 field의 반복 변화

같은 `(role, field)`가 여러 번 등장한다는 이유만으로
중복 제거하지 않는다.

예:

```text
energy:
2 → 0
0 → 3
3 → 1
```

은 세 개의 실제 변화다.

반면:

```text
2
2
2
2
```

는 반복 상태이므로 새로운 변화 사건을 만들지 않는다.

---

# 20. FirstResponse 규칙

`FirstResponse`는 가장 작은 `(tick, phase)`가 아니다.

다음 기준을 사용한다.

```text
ENDOGENOUS_RESPONSE 중
가장 이른 observation_seq / CanonicalMoment
```

같은 moment에 여러 변화가 있다면
하나만 임의로 "최초 원인"으로 뽑지 않는다.

예:

```text
FirstResponseMoment

- heat 소비
- bond 제거
- particle release
```

처럼 묶어서 유지한다.

---

# 21. B0.6 causal edge 생성 규칙과의 연결

B0.6은 다음 순서로 판단한다.

```text
CrossRoleTimeline
+
B0.5 intervention evidence
        ↓
causal edge 후보
```

단:

```text
같은 AtomicChangeGroup 내부 변화끼리
직접 causal edge 생성 금지
```

이다.

서로 다른 canonical moment 사이의 관계도
시간 순서만으로 `SUPPORTED`가 되지는 않는다.

---

# 22. 자동/수동 causal edge 모두 동일 규칙 적용

B0.6의 기본 자동 생성:

```text
build_from_evidence
```

과 사람이 특정 관계를 검토 요청하는 보조 경로:

```text
evaluate_requested_relation
```

모두 동일한 relation validation을 통과해야 한다.

사람이 요청했다고 evidence 규칙을 우회하지 않는다.

---

# 23. 테스트 계약

최소 다음 테스트를 유지한다.

## 테스트 A — observation_seq 순서

```text
실제 observer 호출 순서
==
observation_seq 증가 순서
```

## 테스트 B — tick/phase 정렬 금지

실제 호출 순서와 `(tick, phase)` 정렬 결과가 다른 사례에서도
causal timeline은 observation_seq를 따라야 한다.

## 테스트 C — 중복 순간 병합

```text
인접 snapshot
+
same full state digest
→ 하나의 CanonicalMoment
```

## 테스트 D — 다른 state 보존

추적 field가 같더라도 full state digest가 다르면
병합하지 않는다.

## 테스트 E — atomic ordering 금지

같은 AtomicChangeGroup의 변화들 사이에
자동 causal edge가 생성되지 않아야 한다.

## 테스트 F — role 의미

`source_role`과 실제 observed role이 다른 MechanismCandidate에서도
B0.6이 올바른 observed role을 사용해야 한다.

## 테스트 G — 결정론

```text
same raw evidence
→ same timeline
→ same causal structure
→ same digest
```

---

# 24. 기술 부채 기록

다음 항목을 기술 부채로 기록한다.

```text
MechanismCandidate.source_role의 이름/의미가
실제 observed role과 혼동될 수 있음
```

권장 해결:

```text
investigation_source_role
observed_role
```

또는 동등하게 의미가 분리된 구조로 리팩터링.

이 리팩터링은 B0.6의 현재 동작을 깨지 않는 별도 변경으로 수행한다.

---

# 25. B0.7로 넘길 정보

B0.6이 다음처럼 설명하지 못한 경로를 발견하면:

```text
A
↓
?
↓
C
```

`?`를 임의로 채우지 않는다.

대신 B0.7에 다음 정보를 넘긴다.

```text
- A와 C의 evidence
- 두 사건의 timeline 위치
- 적용 domain
- 실패한 causal edge 후보
- contradiction evidence
- 현재 관측한 field 목록
```

B0.7은 이를 바탕으로
"왜 이 구간을 설명하지 못하는가?"를 조사한다.

---

# 26. 구현자에게 전달할 최종 규칙

```text
1. observation_seq는 trace 내부의 유일한 실제 관측 순서다.

2. tick/phase는 설명용 메타데이터이며
   시간 정렬 키로 사용하지 않는다.

3. 서로 다른 trace의 observation_seq를 직접 대응시키지 않는다.

4. Raw trace는 provenance로 보존한다.

5. causal_timeline은 full state digest를 이용해
   동일 순간의 중복 관측을 정규화한다.

6. 실제 값이 변한 경우만 StateChangeEvent로 만든다.

7. 같은 canonical moment의 변화는 AtomicChangeGroup으로 묶는다.

8. AtomicChangeGroup 내부 변화의 인과 순서를 추측하지 않는다.

9. MechanismCandidate.source_role과 observed role을 혼동하지 않는다.

10. 모든 causal edge 생성은 기존 evidence와 validation을 거친다.
```

---

# 27. 최종 한 문장

> **B는 기록된 이름이나 번호를 시간이라고 믿지 않고 실제 관측 순서를 따르며, 동시에 본 변화에는 임의의 순서를 만들지 않고, 자신이 실제로 관찰한 대상의 의미를 정확히 구분해야 한다.**
